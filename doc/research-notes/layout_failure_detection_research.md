## Responsive layout failures (Walsh, McMinn, Kapfhammer; Althomali, Kapfhammer, McMinn)

### Takeaway
The Sheffield/Allegheny line models a responsive page as a Responsive Layout Graph (RLG): the X-PERT alignment graph (parent-child and sibling edges labelled with justification, position and edge-alignment attributes) extended so that every node fact and edge fact carries the inclusive range of viewport widths over which it holds. Failures are found either by diffing two RLGs (regression mode) or by matching five "failure signatures" in one RLG without an explicit oracle; later work adds screenshot-based verification (Viser, Verve) to remove non-observable reports and automated CSS repair (Layout DR). The public ReDeCheck code shows concrete pixel tolerances (3 px for alignment, 5 px for "fill", overlap only if the intersection is more than 1 px each way, elements under 5x5 px dropped, small-range under 5 px of viewport width).

Representation (RLG):
- The underlying single-width model is X-PERT's alignment graph, formally a 5-tuple AG = (E, R, T, Q, F): E = elements, R = element pairs in a relationship of type T = {pc, s} (parent-child, sibling), Q = alignment attributes, F maps edges to attribute sets. Nodes come from the DOM; positions and sizes come from each element's minimum bounding box, found by XPath. ([STVR 2020](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf))
- Parent-child edges are created when an element is contained in the bounding box of another element; sibling edges connect elements with the same parent. Only one of the two symmetric sibling edges is stored ("X above Y" and "Y below X" are treated as the same), and no transitive edges are stored. ([STVR 2020](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf))
- The RLG "assumes that the tightest element encompassing another element is its intended container", and hard-codes `body` as the root container. ([Althomali thesis, ch. 6](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))
- Edge labels. Parent-child: LJ (left justified), RJ (right), CJ (centre), TJ (top), BJ (bottom), MJ (middle). Sibling "positioning": L (left of), R (right of), A (above), B (below). Sibling "alignment": with L/R an element may also be TE (top edge aligned) and/or BE (bottom edge aligned); with A/B it may be LE (left edge) and/or RE (right edge). ([STVR 2020](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf))
- For failure detection the ISSTA 2017 RLG adds an overlap attribute "O" on sibling edges. ([Althomali thesis, sec. 2.4](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))
- Definition 1, visibility constraint: a pair (x1, x2), an inclusive range of viewport widths over which a node is present in the DOM and visible. Definition 2, alignment constraint: a 4-tuple (x1, x2, t, P) with t in {pc, s} and P a set of attributes holding between two nodes over widths x1..x2. An edge can carry several alignment constraints, one per width range, e.g. (wmin, 767, s, {A}) and (768, wmax, s, {L}) for "div[1] is above div[2] below 768 px and left of it from 768 px". ([STVR 2020](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf))
- Extraction: build one alignment graph per sampled width, then binary-search between two sampled widths where a node's visibility or an edge's attribute set changes, to find the exact boundary width. ([STVR 2020](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf))
- Sampling strategies compared: exhaustive (every width), interval sampling, and interval sampling plus widths mined from CSS media queries (both sides of each breakpoint, e.g. 991 and 992 px for a rule at 992 px). Best trade-off reported: interval sampling with 80 px steps plus CSS breakpoint widths. ([STVR 2020](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf))
- ReDeCheck's default test range in these studies is 320 to 1400 px; the thesis states a step size of 60 "was shown to be ideal by Walsh". (Note: this differs from the 80 px figure in STVR 2020, which may refer to a different configuration or study.) ([Althomali thesis](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf); [STVR 2020](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf))

Exact relation definitions and tolerances in the ReDeCheck code (commit d3f2364):
- Siblings ([Sibling.java](https://github.com/redecheck/redecheck/blob/d3f2364960aa7398f7085a502576da70759f5ed0/src/main/java/shef/layout/Sibling.java)): deltaW = deltaH = 3 px. Edge alignment (leftEdge, rightEdge, topEdge, bottomEdge) and midpoint alignment (xMid, yMid) hold if the coordinates differ by at most 3 px. leftOf holds if `midx1 <= node2.x1 && node1.x2 < node2.x2`; rightOf if `node2.x2 <= midx1 && node1.x1 > node2.x1`; above if `node1.y2 <= midy2` (bottom of 1 at or above the vertical midpoint of 2); below if `node2.y2 <= midy1`. Stricter edge-to-edge versions (`node1.y2 <= node2.y1`) are present but commented out. overlapping holds only if the rectangles intersect and the intersection is wider than 1 px and taller than 1 px.
- Parent-child ([ParentChild.java](https://github.com/redecheck/redecheck/blob/d3f2364960aa7398f7085a502576da70759f5ed0/src/main/java/shef/layout/ParentChild.java)): hFill if centres and both x edges are within 5 px; otherwise CJ if centres within 3 px, else LJ if left edges within 3 px, else RJ if right edges within 3 px (an exclusive priority order). Vertically the same with vFill, MJ, TJ, BJ.
- Tolerance check is `a <= b + delta && a >= b - delta` on integer coordinates ([Relationship.java](https://github.com/redecheck/redecheck/blob/d3f2364960aa7398f7085a502576da70759f5ed0/src/main/java/shef/layout/Relationship.java)); coordinates are read with `getInt` from the captured JSON ([LayoutFactory.java](https://github.com/redecheck/redecheck/blob/d3f2364960aa7398f7085a502576da70759f5ed0/src/main/java/shef/layout/LayoutFactory.java)).
- Small-range threshold: a constraint is a small-range candidate if `max - min < 5` (comment: "the bounds width is less than the threshold, in this case, 5 pixels") and a different constraint exists just before and just after it. ([RLGAnalyser.java](https://github.com/redecheck/redecheck/blob/d3f2364960aa7398f7085a502576da70759f5ed0/src/main/java/shef/analysis/RLGAnalyser.java))

Element selection (ReDeCheck code):
- Elements are dropped if their coordinates are all zero, if width or height is under 1 px and overflow is 0, if not visible, if width or height is under 5 px, or if the tag is on an ignore list of mostly inline or non-layout tags (I, G, PATH, AREA, B, BLOCKQUOTE, BR, CANVAS, CENTER, DD, EM, EMBED, FIELDSET, FONT, HEAD, HR, IFRAME, INS, LEGEND, LINK, MAP, and others). Descendants of non-visible elements are dropped too. ([LayoutFactory.java](https://github.com/redecheck/redecheck/blob/d3f2364960aa7398f7085a502576da70759f5ed0/src/main/java/shef/layout/LayoutFactory.java))

Failure taxonomy (ISSTA 2017) and how each is detected from the RLG ([Althomali thesis, sec. 2.4](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf)):
- Element collision: two elements overlap unintentionally. Detected as an "O" attribute on a sibling edge at a narrower viewport that is absent at a wider viewport.
- Element protrusion: an element is no longer confined to its intended parent. Detected as overlap plus a change from sibling to parent-child relationship at the immediately wider viewport.
- Viewport protrusion: an element protrudes outside `body`. Detected as a visible element whose parent-child relationships do not cover its whole visibility range.
- Element wrapping: an element breaks its row and wraps to a new line. Detected when at least two siblings are left-of/right-of each other, others are above/below, and those above/below relations become left-of/right-of at the adjacent wider viewport.
- Small-range layout: a layout between two elements that holds only over a few widths compared with neighbouring widths ("five or fewer viewports"; elsewhere in the same thesis "less than five"), with a different alignment on both sides. Can duplicate a report of the other four types.
- The class names in the code also include a MisalignedFailure type not in the published five-type taxonomy. ([reporting/inconsistencies](https://github.com/redecheck/redecheck/tree/d3f2364960aa7398f7085a502576da70759f5ed0/src/main/java/shef/reporting/inconsistencies))

Regression mode (RLG differencing, STVR 2020):
- Nodes match across versions only if their absolute XPaths are identical; unmatched nodes are reported. Then unmatched visibility constraints, unmatched edges, and alignment-constraint mismatches are reported. A partial match is classified as a bounds difference (same attributes, different width range; reported widths = symmetric difference of the two ranges), an attributes difference (same range, different attributes or relationship type), or a compound difference (both). ([STVR 2020](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf))
- Evaluation: 15 real-world pages, mutation operators on HTML and CSS; with 60 mutants (4 per page) the tool had no false negatives and one false positive (a subtle shift "not readily apparent" to a developer or visitor). It classified 12.5% and 18.75% more true positives than manual spot-checking and than alignment-graph differencing at single widths. On a pool of 450 mutants, alignment-graph spot-checking missed 20 of 36 subtle changes, while RLG differencing stayed effective regardless of subtlety. ([STVR 2020](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf))

Oracle-free detection results (ISSTA 2017):
- ReDeCheck found responsive layout failures in 16 of 26 pages, producing 328 reports of which 197 were true positives. ([STVR 2021](https://eprints.whiterose.ac.uk/165542/8/stvr.1756.pdf))
- The tool reported 137 viewport ranges for 33 distinct failures, so a developer would study on average 4.2 widths per distinct failure. Non-observable issues include elements that "protruded invisibly out of their container". ([ReDeCheck demo](https://eprints.whiterose.ac.uk/116991/1/c49.pdf))
- Walsh et al.'s manual classification found 83 non-observable issues among 118 reports from 26 pages (about 70%); the thesis elsewhere gives 117 reports from 20 subjects with 83 NOIs. These counts are inconsistent within the thesis. ([Althomali thesis](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))

Verification, classification and repair:
- Viser (ICST 2019) classifies each report as true positive (TP), non-observable issue (NOI) or false positive (FP). It first re-checks the DOM (e.g. a collision is FP if the two boxes do not overlap), then computes an "area of concern" from the reported elements' coordinates, changes the `opacity` of the elements to reveal the layer underneath, and compares pixel colours across layers. Agreement with the manual baseline: 86.3%; under one second per report; the narrowest width in the failure range gave the best agreement. ([Althomali thesis, 6.1.2](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))
- Verve (STVR 2021) extends this to wrapping (opacity layers) and small-range failures (colour-histogram distances between areas of concern in three screenshots: one inside the failure range and the bordering narrower and wider widths; TP if the distance exceeds a tuned threshold). Agreement: 78.6% for wrapping; up to 98.5% for small-range on 25 subjects (Intersection measure); 87.5% on all 45 subjects (Chi-Square measure); on 20 new subjects collision 100%, element protrusion 92.2%, viewport protrusion 80%, wrapping 64.7%; average 4 s per report over 469 reports. ([Althomali thesis, 6.1.3-6.1.4](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))
- One Verve false positive arose because ReDeCheck saw a 1 px viewport protrusion that Verve did not, since ReDeCheck reads the DOM with injected JavaScript and Verve uses Selenium. Some human disagreements were "subjective" because the discrepancy amounted "to a few pixels". ([STVR 2021](https://eprints.whiterose.ac.uk/165542/8/stvr.1756.pdf))
- Layout DR (ICST 2022) reimplements ReDeCheck's detection, then repairs a failure by copying the layout code of the bordering narrower or wider width (assumed failure-free) into a media-query range covering the failure, and re-runs detection to confirm. On 31 pages and 398 reports: wider-source repairs worked for 100%, narrower-source repairs for 96% when valid (valid for 50%); 72% of 55 definite failures had a failure-free repair; users preferred the repaired page 91% of the time; under one minute per repair. ([Althomali thesis, 6.1.5](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))

Known weaknesses stated by the authors:
- Out-of-flow elements (fixed or floating as the user scrolls) move when the viewport changes, leave the container the RLG assigned them, and are wrongly reported. Proposed fix: assign out-of-flow elements to the root container. ([Althomali thesis, 6.2.1](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))
- `body` is assumed never wider than the viewport, which miscounts viewport protrusions; proposed fix: a pseudo "page" root as wide as the viewport with infinite height. ([Althomali thesis, 6.2.1](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))
- Pixel tolerance: DOM coordinates can be fractional; a fractional overlap forces a choice, the choice may not match the browser's rendering, and "changing the tolerance value can change the output of the tool significantly". Proposed fix: infer relations using readings from several or all widths rather than one. ([Althomali thesis, 6.2.1](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))
- Dynamic pages: the model only supports layouts that are static in relative position, size and structure; JavaScript that changes elements breaks it. Proposed fix: developer-provided unique identifiers for elements. ([Althomali thesis, 6.2.1](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))

### Inferences
- The RLG's key idea for onionskin is "facts with a validity range": store each derived fact (e.g. `[:left-of a b]`) with the set of viewport widths where it holds, found by sampling plus binary search on the change points. Comparing two versions then becomes set arithmetic on ranges (bounds, attributes, compound differences), which maps directly onto Clojure data.
- The RLG relation vocabulary is deliberately small and asymmetric (only parent-child and sibling pairs, one edge per pair). onionskin's developer-written expectations will name arbitrary pairs, so it needs relations defined on any two boxes, not only on tree neighbours; the RLG's restriction is a scaling device for whole-page diffs.
- ReDeCheck's "above" and "left of" are lenient (they allow overlap up to the other element's midpoint). onionskin should define each relation precisely and document it, and probably offer both a strict (edge-to-edge) and a lenient form, since the published tools disagree.
- The 3 px / 5 px / 1 px constants are an existence proof that small fixed tolerances work in practice, but the thesis warns the output is sensitive to them. Making tolerance an explicit, per-assertion parameter (with a documented default) addresses that warning.
- Viser's lesson: DOM-derived overlap is not the same as a visible defect. onionskin could report "overlaps" and separately offer an "occludes" or "visibly overlaps" check (e.g. via screenshots or hit-testing), rather than conflating them.
- Container assignment by tightest bounding box fails for positioned elements; onionskin can avoid this by using the DOM parent or containing block from computed `position` rather than geometry alone.

## Cross-browser inconsistencies (WebDiff, CrossT, CrossCheck, X-PERT, Browserbite, XFix)

### Takeaway
Cross-browser work moved from screenshot comparison per DOM element (WebDiff) and DOM/state-graph comparison (CrossT), through a learned classifier over geometric and visual features (CrossCheck), to X-PERT's alignment graph, which compares relative layout (parent-child and sibling relations) rather than absolute positions and is the direct ancestor of the RLG. XFix shows how to turn relation violations into a numeric fitness (position, size and neighbour displacement) for search-based CSS repair. Browserbite argues the opposite direction: pure image processing without the DOM.

### Cited Findings
- [PR] Roy Choudhary, Versee, Orso. "WEBDIFF: Automated identification of cross-browser issues in web applications". ICSM 2010, pp. 1-10. DOI 10.1109/ICSM.2010.5609723. ([DOI](https://doi.org/10.1109/ICSM.2010.5609723))
- WebDiff, as described by Althomali: opens the page in several browsers with one as reference; collects DOM data and a screenshot per browser; takes a second screenshot to find elements with changing content and paints them a common colour so they match; matches elements across browsers; compares each element's screenshot region with colour histograms and uses Earth Mover's Distance so "any small shift in the position of elements is ignored"; reports HTML tags. ([Althomali thesis, sec. 2.4](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))
- [PR] Mesbah, Prasad. "Automated cross-browser compatibility testing". ICSE 2011, pp. 561-570. DOI 10.1145/1985793.1985870 (CrossT). ([DOI](https://doi.org/10.1145/1985793.1985870))
- CrossT, as described by Althomali: crawls the app in several browsers with Crawljax into a navigation model (states are screens, transitions are user actions), then compares models at trace level (event sequences) and screen level (DOM), ignoring case, whitespace and attribute order to cut false positives; reports mismatched screen pairs with two screenshots, a DOM diff and the action sequence. Input includes a list of HTML elements to include or exclude. ([Althomali thesis, sec. 2.4](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))
- [PR] Roy Choudhary, Prasad, Orso. "CrossCheck: Combining Crawling and Differencing to Better Detect Cross-browser Incompatibilities in Web Applications". ICST 2012, pp. 171-180. DOI 10.1109/ICST.2012.97. ([DOI](https://doi.org/10.1109/ICST.2012.97))
- CrossCheck, as described by Althomali: combines WebDiff (visual) and CrossT (functional); replaces WebDiff's hand-made heuristics with a decision-tree classifier trained on manually labelled XBIs from ten apps. Features: size difference ratio, displacement (Euclidean distance between positions), minimal area of the two elements (used as a threshold for the other features), a text-difference flag for DOM leaf nodes, and colour-histogram distance (without EMD). Mismatches are clustered before reporting. ([Althomali thesis, sec. 2.4](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))
- [PR] Roy Choudhary, Prasad, Orso. "X-PERT: Accurate identification of cross-browser issues in web applications". ICSE 2013, pp. 702-711. DOI 10.1109/ICSE.2013.6606616. ([DOI](https://doi.org/10.1109/ICSE.2013.6606616); preprint listed at [Orso's site](https://faculty.cc.gatech.edu/~orso/papers/icse13main-p426-p-15744-preprint.pdf), which returned HTTP 404 to a direct download in this session)
- [snippet] X-PERT reports precision of 76% and recall of 95% "with negligible duplication in the XBI reports", outperforming a state-of-the-art detector; over 50% of websites with XBIs contained layout XBIs. ([preprint via search](https://faculty.cc.gatech.edu/~orso/papers/icse13main-p426-p-15744-preprint.pdf))
- X-PERT XBI types, as described by Althomali: structural (layout, e.g. relative alignment rearranged), content (text-content and visual-content), and behaviour. The alignment graph is directed, with parent-child edges (child's XPath has the parent's as prefix and the child's rectangle lies within the parent's) and sibling edges (same parent), labelled with relative position attributes. ([Althomali thesis, sec. 2.4](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))
- The alignment graph's formal definition (5-tuple; attributes such as A = above, L = left of; CJ, LJ, RJ for children in parents) is given in the Walsh STVR 2020 background section, citing X-PERT. ([STVR 2020](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf))
- [PR-text] Mahajan, Alameer, McMinn, Halfond. "Automated Repair of Layout Cross Browser Issues Using Search-Based Techniques" (XFix). ISSTA 2017. DOI 10.1145/3092703.3092726. ([author PDF](https://viterbi-web.usc.edu/~halfond/papers/mahajan17issta.pdf); [White Rose copy](https://eprints.whiterose.ac.uk/116990/7/c48.pdf))
- XFix uses X-PERT for detection; each XBI is a tuple of a label and two XPaths, where the label names the correct layout relation of e1 that was violated in the test browser, e.g. a top-align label means "e1 is pinned to the top edge of e2" in the reference browser but not in the test browser. ([XFix](https://viterbi-web.usc.edu/~halfond/papers/mahajan17issta.pdf))
- XFix fitness (minimised): weighted sum of dpos (sum of Euclidean distances between the top-left and bottom-right corners of the element's bounding box in reference vs test browser), dsize (sum of width and height differences), and dnpos (dpos summed over neighbours within Nr hops in the DOM: Nr = 1 gives parent and children; Nr = 2 adds siblings, grandparent, grandchildren). ([XFix](https://viterbi-web.usc.edu/~halfond/papers/mahajan17issta.pdf))
- XFix results: 15 real-world subjects; resolved 86% of XBIs reported by X-PERT and 99% of XBIs observed by humans. ([XFix](https://viterbi-web.usc.edu/~halfond/papers/mahajan17issta.pdf)); tool paper: [PR-text] "XFix: An Automated Tool for the Repair of Layout Cross Browser Issues", ISSTA 2017 demo, pp. 368-371, DOI 10.1145/3092703.3098223 ([PDF](https://eprints.whiterose.ac.uk/116992/7/c47.pdf))
- [PR] Semenenko, Dumas, Saar. "Browserbite: Accurate Cross-Browser Testing via Machine Learning over Image Features". ICSM 2013, pp. 528-531. DOI 10.1109/ICSM.2013.88. [PR] Saar, Dumas, Kaljuve, Semenenko. "Browserbite: cross-browser testing via image processing". Software: Practice and Experience 46(11):1459-1477, 2016. DOI 10.1002/spe.2387. ([ICSM DOI](https://doi.org/10.1109/ICSM.2013.88); [SPE DOI](https://doi.org/10.1002/spe.2387))
- Browserbite, as described by Althomali: deliberately avoids the DOM; phases are screenshot capture, segmentation into regions of interest by intensity change, image comparison, and machine-learning classification; claimed to perform as well as X-PERT in its basic configuration; offered as a commercial service until end of 2017. ([Althomali thesis, sec. 2.4](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))

### Inferences
- X-PERT's move from absolute positions to relative relations is the core justification for onionskin's symbolic layer: absolute coordinates differ across browsers and versions for harmless reasons, relations change only when the layout actually changes.
- XFix's tuple (relation label, e1, e2) is a good shape for an onionskin failure report: "expected `:top-aligned` between A and B, not found", plus a numeric deviation such as XFix's dpos and dsize.
- CrossCheck's features (size ratio, displacement, minimal area as a gate) show that "how big is the element" should scale tolerances: a 3 px shift matters more for a 10 px icon than a 1000 px panel. onionskin could support relative tolerances (percent of size) next to absolute pixels.
- WebDiff's reload-and-compare to find changing regions is a cheap, automatic way to mark legitimately varying elements before comparing two versions.

### Gaps
- X-PERT full text was not read (the preprint URL returned 404 to direct download), so its exact label set, any pixel thresholds used for alignment, and its element matching method are not verified first-hand. The label names "top-align" etc. are confirmed only via XFix.
- WebDiff, CrossT, CrossCheck and Browserbite details come from the Althomali thesis literature review, not the primary papers; their precision and recall numbers were not collected.

## Internationalization presentation failures (GWALI, IFix)

### Takeaway
GWALI compares a baseline page with its translated version using a Layout Graph: a complete graph over element nodes and separate text nodes, with edges labelled by direction (North, South, East, West), alignment (top, bottom, left, right) and containment (contains, intersects). It limits comparison to spatial neighbourhoods (k nearest neighbours), filters expected changes with explicit heuristics (text growth inside a container, direction changes under 45 degrees, wrapped inline items), and ranks suspicious elements. IFix converts each violated relation into a pixel distance needed to restore it and uses that as a search fitness.

### Cited Findings
- [PR-text] Alameer, Mahajan, Halfond. "Detecting and Localizing Internationalization Presentation Failures in Web Applications" (GWALI). ICST 2016, pp. 202-212. DOI 10.1109/ICST.2016.36. ([author PDF](https://viterbi-web.usc.edu/~halfond/papers/alameer16icst.pdf); [DOI](https://doi.org/10.1109/ICST.2016.36))
- LG definition: a complete graph <V, F>, F : V x V -> P(R). A node is <t, c1, c2, x>: type "Element" (HTML tag) or "Text" (text inside a tag), upper-left and lower-right corners of the minimum bounding rectangle (MBR), and XPath. R has three categories: direction (North, South, East, West), alignment (top, bottom, left, right), containment (contains, intersects). Unlike the alignment graph and R-trees, the LG includes text as nodes, because translation changes the text. Text nodes get the parent XPath plus "/text()" and an MBR around the text itself. ([GWALI](https://viterbi-web.usc.edu/~halfond/papers/alameer16icst.pdf))
- Relations are computed from MBR coordinates, e.g. North if v.y2 <= w.y1; Bottom-Aligned if v.y2 = w.y2; Contains if v.x1 <= w.x1, v.y1 <= w.y1, v.x2 >= w.x2 and v.y2 >= w.y2. No pixel tolerance is stated for these comparisons in the paper. ([GWALI](https://viterbi-web.usc.edu/~halfond/papers/alameer16icst.pdf))
- Element selection: both pages are rendered at the same predefined viewport size (which can be varied). Three exceptions: (1) invisible tags, including unofficial hiding (zero height or width, `clip` to a zero rectangle, large `text-indent` with `overflow: hidden`), detected from computed properties; (2) tags that do not affect the layout, by heuristics: containers with no border and background similar to the parent's, tags with very small dimension, text-styling tags (`font`, `strong`, `b`), unselected options of a select menu; (3) tags embedded in another tag's text (e.g. inline links) are grouped into one "Text" node whose MBR surrounds them all, because their relative positions change unavoidably after translation. ([GWALI](https://viterbi-web.usc.edu/~halfond/papers/alameer16icst.pdf))
- Matching between versions: XPaths may not match because translation frameworks add tags, so GWALI adapts WebDiff's probabilistic matching on attributes, tag names and Levenshtein distance between XPaths; matching was "close to perfect" on their subjects. ([GWALI](https://viterbi-web.usc.edu/~halfond/papers/alameer16icst.pdf))
- Neighbourhoods: pair-wise comparison of all edges produced too many reports, so for each node GWALI takes the four MBR corners and the centre, finds the k nearest nodes to each point (distance from the point to the other MBR's area), and compares only edges in the union. k works best set proportional to the number of nodes. For each edge it computes the symmetric difference delta between F(e) and F(e'); a non-empty delta is a potential issue. ([GWALI](https://viterbi-web.usc.edu/~halfond/papers/alameer16icst.pdf))
- Heuristic 1: on Text/Element and Text/Text edges, alignment changes are dropped, since text growing inside a container with room is expected. Heuristic 2: for direction changes the angle between the two nodes is computed; if it changed by less than a tester-set alpha the direction labels are dropped; alpha = 45 degrees "provided a reasonable balance". Heuristic 3: when a directional relation changes, the lowest common ancestor's text children are added as a suspect (e.g. a menu item pushed to a new row by its siblings' longer text). ([GWALI](https://viterbi-web.usc.edu/~halfond/papers/alameer16icst.pdf))
- Localization: each node's suspiciousness = number of flagged edges it appears in plus |delta| of those edges; output is a ranked list. ([GWALI](https://viterbi-web.usc.edu/~halfond/papers/alameer16icst.pdf))
- Evaluation: 30 pages with real IPFs and 24 internationalized pages without. GWALI detected IPFs with 91% precision and 100% recall; WebSee and X-PERT also had 100% recall but lower precision (55% each, as read from a garbled table extraction; FLB appears as 73% precision and 55% recall in the same table). Faulty element median rank 3; 9.75 s per page versus 8.97 s for X-PERT. ([GWALI](https://viterbi-web.usc.edu/~halfond/papers/alameer16icst.pdf))
- [PR-text] Mahajan, Alameer, McMinn, Halfond. "Automated repair of internationalization presentation failures in web pages using style similarity clustering and search-based techniques" (IFix). ICST 2018. DOI 10.1109/ICST.2018.00030. ([White Rose PDF](https://eprints.whiterose.ac.uk/131041/1/c53.pdf))
- IFix fitness = amount of layout inconsistency + sigmoid(amount of change). Layout inconsistency is the number of pixels needed to make the LG relations match again, summed over every inconsistent relation reported by GWALI: for a lost top-alignment, |e1.y - e2.y|; for a lost "West", the distance e2 must move to be west of e1; for a lost containment, the expansion of each side of e1's MBR needed to bound e2. Amount of change is the sum of squared percentage changes of each modified CSS property. ([IFix](https://eprints.whiterose.ac.uk/131041/1/c53.pdf))
- IFix clusters stylistically similar elements with DBSCAN so repairs apply to whole groups (e.g. all menu items); the style distance uses width, height, edge-alignment matches, tag name, matched CSS values and XPath Levenshtein similarity, as described by Althomali. ([Althomali thesis](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))
- IFix results: resolved 98% of reported IPFs for 23 real-world pages; over 70% user approval of repairs. ([IFix](https://eprints.whiterose.ac.uk/131041/1/c53.pdf))
- [PR] Follow-ups listed in the Halfond lab bibliography: Alameer, Halfond, "An Empirical Study of Internationalization Failures in the Web", ICSME 2016; Alameer, Chiou, Halfond, "Efficiently Repairing Internationalization Presentation Failures by Solving Layout Constraints", ICST 2019, pp. 172-182; Mahajan et al., STVR journal version of IFix, DOI 10.1002/stvr.1746. ([Halfond bib file](https://viterbi-web.usc.edu/~halfond/softwarequalitylab.bib); [Althomali thesis bibliography](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))

### Inferences
- GWALI's three relation families (direction, alignment, containment/intersection) on a complete graph are close to the vocabulary onionskin wants (left-of, above, inside, aligned, overlaps). Its definitions are strict (edge-to-edge, exact equality), the opposite of ReDeCheck's lenient ones.
- Treating text runs as their own boxes (MBR of the text, not the element) is directly useful: "label text fits inside its button" is a text-box vs element-box fact. onionskin can get text boxes from DOM Range client rects.
- GWALI's heuristics are a catalogue of "expected change" rules that onionskin could expose as named, opt-in filters when diffing two versions: ignore alignment changes on text edges, ignore direction changes under an angle, collapse inline runs into one node.
- The angle test is a neat coarse quantity: instead of "west vs south", compare the bearing between box centres with a tolerance in degrees.
- IFix's "pixels needed to restore the relation" is the natural magnitude for an onionskin failure message ("A is 7 px below the top of B; expected top-aligned within 2 px").
- k-NN neighbourhoods are a cheap way to keep whole-page diffs focused on spatially related pairs.

### Gaps
- Exact GWALI Table I values were reconstructed from a text extraction that lost the table layout; the 91%/100% GWALI figures are confirmed in the abstract, the others should be checked against the PDF.
- The ICST 2019 constraint-solving repair paper (Alameer, Chiou, Halfond) was not read; its DOI was not verified.

## Visual presentation failures and mobile-friendly problems (WebSee, FieryEye, MFix)

### Takeaway
WebSee compares a screenshot with an oracle image (mockup or earlier version) using perceptual image differencing with a tolerance, clusters difference pixels, and maps clusters to elements via an R-tree of element boxes to produce a ranked suspect list; tester-declared "special regions" handle dynamic content. FieryEye builds on it for regression after refactoring. MFix reuses a graph-of-relations idea (Segment Model and Intra-Segment Model with intersection, containment and direction labels) to measure layout distortion, and only counts intersections inside a segment, which encodes "movement inside a group is acceptable, overlap is not".

### Cited Findings
- [PR-text] Mahajan, Halfond. "Detection and Localization of HTML Presentation Failures Using Computer Vision-Based Techniques" (WebSee). ICST 2015, pp. 1-10. DOI 10.1109/ICST.2015.7102586. ([author PDF](https://viterbi-web.usc.edu/~halfond/papers/mahajan15icst.pdf); [DOI](https://doi.org/10.1109/ICST.2015.7102586)). Earlier idea paper: [PR] Mahajan, Halfond, "Finding HTML presentation failures using image comparison techniques", ASE 2014 New Ideas, pp. 91-96, DOI 10.1145/2642937.2642966 ([DOI](https://doi.org/10.1145/2642937.2642966)).
- WebSee inputs: the page under test and an oracle image O (mockup or screenshot of a correct version) plus a set of special regions (SR) for dynamic text, ads and similar. Detection uses perceptual image differencing (PID), which models human spatial, luminance and colour sensitivity, with a threshold Delta and field-of-view, luminance and colour parameters. Difference pixels inside special regions are handled separately; the rest are clustered with DBSCAN; each cluster is mapped to the elements whose rendered bounding rectangles (stored in an R-tree) contain the pixels; elements are ranked. ([WebSee](https://viterbi-web.usc.edu/~halfond/papers/mahajan15icst.pdf))
- The earlier pixel-perfect comparison was "impractical for real-world mockups"; simulating it (Delta = 0) flagged over 84% of the page as different for several subjects, while a tuned PID setting (Delta of 10%, with other parameters) worked. ([WebSee](https://viterbi-web.usc.edu/~halfond/papers/mahajan15icst.pdf))
- WebSee results on seeded faults: detected the failure in all test cases with a perceptible difference; localization accuracy 93% (faulty element in the result set); median result set 23 elements (about 10% of elements); average median rank 4.8 (about 2% of elements); 87 s per test on average. ([WebSee](https://viterbi-web.usc.edu/~halfond/papers/mahajan15icst.pdf))
- [PR] Mahajan, Li, Behnamghader, Halfond. "Using Visual Symptoms for Debugging Presentation Failures in Web Applications" (FieryEye). ICST 2016, pp. 191-201. DOI 10.1109/ICST.2016.35. ([DOI](https://doi.org/10.1109/ICST.2016.35))
- FieryEye, as described by Althomali: input is a snapshot of the previous version, a list of regions to exclude (dynamic content raises false positives) and the URL; it detects visual differences with WebSee's PID approach and feeds them into a probabilistic model that maps visual symptoms to likely faulty HTML attributes or CSS properties, from a manually identified subset of properties that can change appearance. ([Althomali thesis, sec. 2.4](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))
- [PR-text] Mahajan, Abolhassani, McMinn, Halfond. "Automated Repair of Mobile Friendly Problems in Web Pages" (MFix). ICSE 2018, pp. 140-150. DOI 10.1145/3180155.3180262. ([White Rose PDF](https://eprints.whiterose.ac.uk/127563/8/paper.pdf))
- MFix models: a Segment Model (SM) is a directed complete graph whose nodes are segments (groups of elements found by a clustering-based partitioning of the DOM) and whose edge labels are intersection, containment, or direction (above, below, left, right), computed from each segment's MBR (min and max coordinates of its elements). An Intra-Segment Model (ISM) is the same graph per segment over its HTML elements. ([MFix](https://eprints.whiterose.ac.uk/127563/8/paper.pdf))
- MFix layout distortion = sum over SM edges of the size of the symmetric difference of labels (original vs patched), plus the same over ISM edges but counting only the intersection relationship, because movement of elements within a segment, other than intersection, is "an acceptable change". ([MFix](https://eprints.whiterose.ac.uk/127563/8/paper.pdf))
- MFix uses Google's Mobile-Friendly Test to localize problems and score pages; on 38 real-world subjects, 95% (36 of 38) passed the test after repair; the best repair had a layout distortion score 55% lower than the worst; runs took 2 to 10 minutes; users preferred the repaired pages and rated them more readable. ([MFix](https://eprints.whiterose.ac.uk/127563/8/paper.pdf))
- [PR] Tanno, Adachi. "Support for finding presentation failures by using computer vision techniques". ICSTW 2018, pp. 356-363: segments screenshots into rectangles (Sobel, Canny, KAZE features) and lets the developer add rules such as ignoring movement of 20 px or less and scaling up to 3%, as described by Althomali. ([Althomali thesis, sec. 2.5](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))

### Inferences
- MFix's ISM rule is a clean, reusable policy for onionskin's version comparison: within a declared group, ignore changes in direction and alignment, but always report new intersections. That is a coarse-granularity diff that tolerates reflow.
- WebSee's special regions and FieryEye's exclusion regions confirm that any page-level comparison needs a first-class way to mark dynamic regions. In onionskin these can be selectors excluded from fact extraction or from the diff.
- WebSee's R-tree mapping from pixels to boxes is the reverse of onionskin's direction (boxes first), but it shows how a pixel-based check can be reported in terms of elements.
- The 84% false difference rate of pixel-perfect matching is a strong argument for onionskin's choice to work on measured boxes and derived relations rather than screenshots.

### Gaps
- The FieryEye paper was not read; its description comes from the Althomali thesis.
- WebSee's full PID parameter setting beyond "Delta of 10%" was cut off in the text extraction.
- Tanno and Adachi's DOI was not verified.

## Layout oracles generally (oracle problem, declarative layout specifications, formal layout reasoning)

### Takeaway
The general framing is the test oracle problem (Barr et al., TSE 2015). The web layout literature uses three oracle kinds: a previous version or reference browser (differential: WebDiff, X-PERT, GWALI, RLG regression), an implicit oracle of "things that are always wrong" (ReDeCheck's failure signatures), and explicit developer-written layout constraints (Hallé et al.'s Cornipickle, ICST 2015 and JLAMP 2016). Formal approaches (Cassius, VizAssert) verify layout properties across all viewport sizes by encoding CSS in SMT. onionskin's developer-written expectations put it closest to Cornipickle, with RLG-style facts and version diffing on top.

### Cited Findings
- [PR] Barr, Harman, McMinn, Shahbaz, Yoo. "The Oracle Problem in Software Testing: A Survey". IEEE Transactions on Software Engineering 41(5):507-525, 2015. DOI 10.1109/TSE.2014.2372785. ([DOI](https://doi.org/10.1109/TSE.2014.2372785)). Content not read in this session.
- The ISSTA 2017 paper's title frames ReDeCheck as detection "without an explicit oracle". ([DOI](https://doi.org/10.1145/3092703.3092712))
- [PR] Hallé, Bergeron, Guerin, Le Breton. "Testing Web Applications Through Layout Constraints". ICST 2015, pp. 1-8. DOI 10.1109/ICST.2015.7102635. [PR] Hallé, Bergeron, Guérin, Le Breton, Beroual. "Declarative layout constraints for testing web applications". Journal of Logical and Algebraic Methods in Programming 85:737-758, 2016. DOI 10.1016/j.jlamp.2016.04.001. ([ICST DOI](https://doi.org/10.1109/ICST.2015.7102635); [JLAMP DOI](https://doi.org/10.1016/j.jlamp.2016.04.001))
- Cornipickle, as described by Althomali: a declarative language for constraints over DOM and CSS properties that express correct layout or forbid a known failure, suited to regression testing; supports events and temporal operators; users can extend the vocabulary with new definitions, inspired by Cucumber. The authors identified six layout-disrupting bug kinds (element position, element size, element visibility, number of elements, resource files used to style the page, encoding) and four behavioural ones. Althomali's criticism: writing constraints is manual and another language on top of HTML and CSS. ([Althomali thesis, sec. 2.5](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))
- [PR] Panchekha, Torlak. "Automated reasoning for web page layout" (Cassius). OOPSLA 2016, pp. 181-194. DOI 10.1145/2983990.2984010. As described by Althomali: formalizes a large part of CSS layout in quantifier-free linear real arithmetic for SMT solvers; used to build a verifier (e.g. that a layout contracts or expands as intended for all viewports), a debugger that localizes violations to stylesheet parts, and a CSS synthesizer; tested on 2075 conformance tests with Firefox as oracle, where six failed only due to Firefox rounding errors. ([DOI](https://doi.org/10.1145/2983990.2984010); [Althomali thesis](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))
- [PR] Panchekha, Geller, Ernst, Tatlock, Kamil. "Verifying that web pages have accessible layout" (VizAssert). PLDI 2018, pp. 1-14. DOI 10.1145/3192366.3192407. Not read. ([DOI](https://doi.org/10.1145/3192366.3192407))
- [PR] Ryou, Ryu. "Automatic Detection of Visibility Faults by Layout Changes in HTML5 Web Pages" (VFDetector). ICST 2018, pp. 182-192. DOI 10.1109/ICST.2018.00027. As described by Althomali: detects loss of functionality when layout changes (resize or user interaction) make elements with any of 26 user event types invisible, comparing pairs of layouts that should have consistent functionality. ([DOI](https://doi.org/10.1109/ICST.2018.00027); [Althomali thesis](https://etheses.whiterose.ac.uk/id/eprint/31157/1/althomali-thesis.pdf))
- Related, not covered in depth: Stocco, Yandrapally, Mesbah, "Visual web test repair", ESEC/FSE 2018, DOI 10.1145/3236024.3236063 (cited in STVR 2021). ([DOI](https://doi.org/10.1145/3236024.3236063))

### Inferences
- onionskin sits between Cornipickle (explicit, developer-written constraints over DOM/CSS) and the RLG (automatically extracted relational facts with viewport ranges). The literature suggests both modes are useful: explicit expectations for intent, extracted fact diffs for catching unintended side effects of a change (the STVR 2020 motivating example: a fix at one width breaks another).
- Althomali's criticism of Cornipickle (a separate language) supports embedding expectations as plain Clojure data and functions instead of a new syntax.
- Cassius and VizAssert verify for all widths symbolically; onionskin samples a real browser. The RLG's sampling plus binary search is the practical middle ground.

### Gaps
- Barr et al.'s survey text was not read; any claim about its taxonomy of oracles (from prior knowledge: specified, derived, implicit oracles and human oracle cost) is unverified here.
- No dedicated peer-reviewed survey of web layout or presentation testing was found in this session. The literature reviews in the Althomali thesis (ch. 2) and in STVR 2020 and STVR 2021 serve as the best available overviews.
- Cornipickle's actual syntax and predicates were not examined; VizAssert's assertion language was not examined. Both are worth a follow-up read because they are the closest prior art to developer-written layout expectations.
- Non-peer-reviewed tools with similar specs (e.g. the Galen Framework) were out of scope and not researched.

## Tolerances, noise, and elements that legitimately move (cross-cutting)

### Takeaway
Every representation needs some slack, and the published tools handle it in four ways: small fixed pixel tolerances on relation predicates (ReDeCheck: 3 px, 5 px, overlap over 1 px, minimum element size 5 px), coarse relations that absorb small moves (lenient "above"; GWALI's angle threshold of 45 degrees), perceptual or distribution metrics on pixels (WebSee's PID Delta, WebDiff's EMD, Verve's histogram threshold), and explicit rules about which changes are expected (GWALI's text heuristics, MFix's intra-segment rule, special/exclusion regions, WebDiff's reload test). No paper reports a principled method for choosing tolerances; the Althomali thesis says the output is sensitive to them.

- Failure reporting styles: failure type + element XPaths + viewport range (ReDeCheck, per Viser input description); ranked suspicious elements (GWALI, WebSee); relation label + element pair (X-PERT via XFix); numeric deviation for repair (XFix dpos/dsize/dnpos; IFix pixels to restore relation). ### Inferences
- onionskin's three granularities line up with the literature: symbolic relations (RLG, GWALI, MFix labels), coarse quantities (GWALI's bearing angle, CrossCheck's size ratio and displacement), and exact values with tolerance (ReDeCheck's +-3 px; IFix's pixel distance). Each published tool fixes one granularity; letting the developer choose per assertion is the main new contribution onionskin can claim.
- Concrete defaults to borrow, all documented and overridable: alignment tolerance 3 px; "fills" tolerance 5 px; overlap counted only above 1 px in each axis; ignore boxes smaller than 5 x 5 px when extracting whole-page facts; flag layouts that exist over fewer than 5 px of viewport width.
- Measure once, in one place, and keep fractional values; round or apply tolerance only when deriving facts. This avoids the JavaScript-vs-Selenium 1 px disagreement and makes tolerance an explicit, visible choice.
- For diffs between versions, report three kinds of change like the RLG (range changed, relation changed, both), match elements by developer-chosen keys (selector or data attribute) before falling back to XPath, and provide named "expected change" filters (text growth, angle under N degrees, movement inside a group, excluded dynamic regions).
- Every failure should carry the relation, the element pair, the viewport widths where it fails, and the size of the miss in pixels (IFix style), which is what makes reports actionable.

### Gaps
- No source compared different tolerance values systematically; the effect of the 3 px / 5 px constants on precision and recall is unknown.
- None of the papers read addresses sub-pixel layout from device pixel ratio or browser zoom; whether tolerances should scale with devicePixelRatio is open.
- Whether X-PERT's alignment computation uses a pixel threshold could not be verified.
