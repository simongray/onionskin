# CSS refactoring, dead CSS, and checking that a change preserves presentation (prior art for onionskin)

Source labels used below:
[PR] peer-reviewed paper; [THESIS] graduate thesis; [SPEC] W3C/WHATWG spec or editor's draft; [REF] vendor reference docs (MDN, Chrome DevTools Protocol); [BOOK] trade book; [NPR] non-peer-reviewed (package docs, wiki pages, mailing lists, slides, search snippets).

Method note: the full text of the FSE 2014, ASE 2016, ICSE 2012, PLDI 2018 and ISSTA 2017 (ReDeCheck tool) papers was read from the authors' own PDFs. All DOIs below were checked against Crossref unless marked otherwise.

## 1. Mazinanian, Tsantalis and Mesbah: how they defined and preserved "presentation semantics" (FSE 2014, ASE 2016, SANER 2016)

### Takeaway
None of the three papers checks presentation by rendering. FSE 2014 defines presentation as "the property values that are eventually applied to the target document elements". It protects them with a static precondition: refactorings must keep every *order dependency*, computed against DOM states that a crawler captured. ASE 2016 compiles the generated Less back to CSS and checks static per-rule "style maps", with value equivalence such as red ≡ #F00. The authors call rendering-based comparison "the ultimate approach" but rejected it as too slow and error-prone. Onionskin would do exactly that rendering-based comparison, which these papers left undone.

### Cited Findings
- **Citation, FSE 2014** [PR]: D. Mazinanian, N. Tsantalis, A. Mesbah, "Discovering refactoring opportunities in cascading style sheets", Proc. 22nd ACM SIGSOFT Int. Symp. Foundations of Software Engineering (FSE 2014), pp. 496-506, DOI 10.1145/2635868.2635879. [Crossref](https://doi.org/10.1145/2635868.2635879); [author PDF](https://people.ece.ubc.ca/amesbah/resources/papers/fse14.pdf)
- FSE 2014 behaviour definition (Sec. 4.6): "Within the context of CSS, the notion of behavior corresponds to the presentation of the target documents (i.e., the property values that are eventually applied to the target document elements)." [FSE14 PDF](https://people.ece.ubc.ca/amesbah/resources/papers/fse14.pdf)
- FSE 2014 defines an **order dependency** from (selector s_i, declaration d_k) to (s_j, d_l) on property p when all four hold: (a) s_i and s_j select at least one common element that has property p in the target document; (b) d_k and d_l both set p with the same importance (both !important or neither); (c) d_k comes before d_l in the style sheet; (d) s_i and s_j have the same specificity. The precondition is that extracting a grouping selector "should preserve all order dependencies". Placing the new rule is a constraint satisfaction problem with pos(s_i) < pos(s_j) for each dependency. An unsatisfiable problem means the refactoring is "excluded as non presentation-preserving". [FSE14 PDF](https://people.ece.ubc.ca/amesbah/resources/papers/fse14.pdf)
- FSE 2014 duplication types: Type I is identical declarations (value order does not matter, e.g. `border: solid 1px transparent` vs `border: transparent solid 1px`). Type II is equivalent values: named, hex, rgb/rgba and hsl/hsla colours are all normalised to rgba(), and cm/in/pt are converted to px. Type III is a set of longhand declarations that equals a shorthand declaration. Before comparing, they also expand implied shorthand values (`margin: 2px 4px` becomes `margin: 2px 4px 2px 4px`), add "virtual" shorthand declarations, and consider defaults that apply when explicit values are missing. [FSE14 PDF](https://people.ece.ubc.ca/amesbah/resources/papers/fse14.pdf)
- FSE 2014 DOM states came from the Crawljax crawler, and order dependencies were extracted from those states. Only external CSS files were refactored. Inline `<style>` and JS-generated CSS were out of scope. [FSE14 PDF](https://people.ece.ubc.ca/amesbah/resources/papers/fse14.pdf); Crawljax: A. Mesbah, A. van Deursen, S. Lenselink, "Crawling Ajax-based web applications through dynamic analysis of user interface state changes", ACM TWEB 6(1), 2012, DOI [10.1145/2109205.2109208](https://doi.org/10.1145/2109205.2109208) [PR]
- FSE 2014 threat to validity: the captured DOM states "may be insufficient to extract all possible order dependencies ... since for some dynamic web applications the number of DOM states is practically infinite". Refactorings could therefore be "non presentation-preserving for this particular set of unvisited DOM states". [FSE14 PDF](https://people.ece.ubc.ca/amesbah/resources/papers/fse14.pdf)
- FSE 2014 numbers: 38 web systems and 91 CSS files. On average 66% of declarations are duplicated at least once (median 68%). On average there were 165 refactoring opportunities per file, of which 62 were presentation-preserving and applied. Files had 79 order dependencies on average. Average size reduction was 8% (max 35%). A Poisson GLM shows that applicable refactorings go up with file size and down with the number of order dependencies. [FSE14 PDF](https://people.ece.ubc.ca/amesbah/resources/papers/fse14.pdf)
- The FSE 2014 text never mentions "computed" styles or getComputedStyle (0 occurrences in the extracted text), so it did no rendering-based or computed-style check. [FSE14 PDF](https://people.ece.ubc.ca/amesbah/resources/papers/fse14.pdf). ASE 2016 confirms it: "in contrast to this work, we did not use a testing approach in [30] for assuring that the presentation semantics of style sheets will be preserved". [ASE16 PDF](https://users.encs.concordia.ca/~nikolaos/publications/ASE_2016.pdf)
- **Citation, ASE 2016** [PR]: D. Mazinanian, N. Tsantalis, "Migrating cascading style sheets to preprocessors by introducing mixins", Proc. 31st IEEE/ACM Int. Conf. Automated Software Engineering (ASE 2016), pp. 672-683, DOI 10.1145/2970276.2970348. [Crossref](https://doi.org/10.1145/2970276.2970348); [author PDF](https://users.encs.concordia.ca/~nikolaos/publications/ASE_2016.pdf)
- ASE 2016 states the presentation-preservation conditions for an original file C and a migrated file C': (1) a one-to-one mapping between style rules; (2) the same relative order of mapped rules ("cascading is preserved"); (3) each mapped pair (a) selects the same DOM elements, (b) defines exactly the same set of individual style properties (ISPs, i.e. longhands), and (c) assigns equal or equivalent values to each one. Conditions 1, 2 and 3a hold by construction. Conditions 3b and 3c are tested. [ASE16 PDF](https://users.encs.concordia.ca/~nikolaos/publications/ASE_2016.pdf)
- ASE 2016 test oracle: apply the migration to C to get Less code, transpile it back to C', then assert that style-map(s) ≡ style-map(s') for every pair of rules with an identical selector. A style map sends each ISP to "the final style value assigned ... after all possible overrides" within the rule. Values are equivalent if they are "alternative representations for the same style value (e.g., red ≡ #F00)". [ASE16 PDF](https://users.encs.concordia.ca/~nikolaos/publications/ASE_2016.pdf)
- ASE 2016 results: 9,585 migration opportunities were each applied separately and tested. The tests found real bugs in the authors' own value inference. Example: "when a shorthand property is assigned with the value none, only one of the ISPs is actually assigned with none, while the remaining ISPs are assigned with default values", and their code inferred those defaults wrongly. After fixes, 100% of tests passed. 1,227 cases needed the order-dependency precondition (one was unsatisfiable, so it was not migrated), and 1,190 needed the precondition on declaration order inside the mixin. The approach recovered 189 of 193 developer-written mixins (97.9% recall). [ASE16 PDF](https://users.encs.concordia.ca/~nikolaos/publications/ASE_2016.pdf)
- ASE 2016 on rendering-based checking: "The ultimate approach for testing presentation preservation would be to compare the target documents, before and after applying migration transformations, as they are rendered in the browser. However, a visual comparison would be time-consuming and error-prone." Screenshot differencing is "computationally intensive" (they cite WebDiff, WebSee and X-PERT), so they "developed a lightweight static analysis method, based on preconditions derived from CSS specifications". [ASE16 PDF](https://users.encs.concordia.ca/~nikolaos/publications/ASE_2016.pdf)
- ASE 2016 handles omitted values (e.g. `font` takes up to 7 values): "for every omitted value we actually compute a virtual value". It also covers vendor-prefixed properties and !important in mixin arguments. Some advanced parameterisations are not supported. [ASE16 PDF](https://users.encs.concordia.ca/~nikolaos/publications/ASE_2016.pdf)
- **Citation, SANER 2016** [PR]: D. Mazinanian, N. Tsantalis, "An empirical study on the use of CSS preprocessors", Proc. IEEE 23rd SANER, Suita, Japan, 2016, pp. 168-178, DOI 10.1109/SANER.2016.18. [Crossref](https://doi.org/10.1109/SANER.2016.18). The authors' slides [NPR] report that developers write small mixins (median 3 declarations, median 1 parameter). [slides](https://www.slideshare.net/slideshow/an-empirical-study-on-the-use-of-css-preprocessors/59780968). ASE 2016 cites this study for the finding that the median mixin is called twice. [ASE16 PDF](https://users.encs.concordia.ca/~nikolaos/publications/ASE_2016.pdf)
- Follow-ups by the same group [PR]: D. Mazinanian, "Refactoring and migration of cascading style sheets: towards optimization and improved maintainability", FSE 2016 doctoral symposium, pp. 1057-1059, DOI [10.1145/2950290.2983943](https://doi.org/10.1145/2950290.2983943); D. Mazinanian, N. Tsantalis, "CSSDev: Refactoring duplication in cascading style sheets", ICSE-C 2017, pp. 63-66, DOI [10.1109/ICSE-C.2017.7](https://doi.org/10.1109/ICSE-C.2017.7). (Only the existence of these two was checked, via Crossref; their content was not read.)

### Inferences
- The FSE 2014 order-dependency definition is a reduced model of the cascade. It covers only same-specificity, same-importance conflicts on elements seen in captured states. It leaves out origin, `@layer`, `@scope`, inheritance and media/supports conditions. A per-element comparison of resolved values does not need such a model, because the browser applies the whole cascade. That is the main argument for onionskin's dynamic approach over static preconditions.
- The ASE 2016 bug with shorthand `none` resetting the other longhands to initial values shows that comparison must be done on **longhands**. This is the same failure a hand refactor that turns longhands into a shorthand (or back) can cause.
- ASE 2016 matches rules by identical selector. That fails when a refactor renames or merges selectors. Onionskin matches elements, not rules, so selector renames and merges are fine as long as the DOM is the same.
- FSE 2014's threat to validity applies to onionskin too: the result only covers the states that were captured.

### Gaps
- No peer-reviewed paper was found that validates a CSS refactoring by diffing getComputedStyle (or element boxes) of every element across a page corpus. ASE 2016 explicitly chose static checking instead. Mazinanian's 2017 Concordia PhD thesis, which may extend this work, was not checked.
- Order dependencies in pseudo-class or media-query contexts are not discussed in the extracted FSE 2014 text. Its model groups declarations by media type ("foreach m in mediumTypes"), but how `:hover` rules are matched against crawled DOMs is not stated.

## 2. Dead CSS, CSS smells, redundancy and minification (Mesbah and Mirshokraie 2012; Gharachorlu 2014; Hague et al. 2015 and 2019; Genevès, Layaïda et al.)

### Takeaway
There are two families. Dynamic tools (CILLA) crawl DOM states and find unmatched or ineffective selectors. They are useful but unsound, because states can be missed. Static or formal tools (tree logics; tree rewriting; SATCSS) prove equivalence over all documents, or all documents a program can produce. They do this by modelling CSS semantics as "which declarations apply to which node". Both families use the same notion of equivalence: the same declarations (property values) reach each node.

### Cited Findings
- **Citation** [PR]: A. Mesbah, S. Mirshokraie, "Automated analysis of CSS rules to support style maintenance", Proc. 34th ICSE, 2012, pp. 408-418, DOI 10.1109/ICSE.2012.6227174. [Crossref](https://doi.org/10.1109/ICSE.2012.6227174); [author PDF](https://people.ece.ubc.ca/amesbah/resources/papers/icse12.pdf); tool [CILLA on GitHub](https://github.com/saltlab/cilla/)
- CILLA "analyzes the runtime relationship between the CSS rules and DOM elements" across a set of visited DOM states. It reports *unmatched* selectors (no element in any state), *matched but ineffective* selectors (match elements but have no effect), *overridden* declaration properties, and *undefined class values* (classes in the DOM with no matching selector). Selectors are translated to XPath and evaluated on each DOM state (e.g. `#news span` becomes `./descendant::*[@id='news']/descendant::SPAN`). [ICSE12 PDF](https://people.ece.ubc.ca/amesbah/resources/papers/icse12.pdf)
- CILLA results: 15 open-source and industrial systems, with on average 60% unused selectors and 52% unused properties. Recall was 100% and precision 80-100%, judged by manually checking sampled rules. Analysing 7K lines of CSS over 100 DOM states took minutes. Older industrial tools (Dust-Me Selectors, CSS ESS) "produce a high rate of false positives and false negatives". [ICSE12 PDF](https://people.ece.ubc.ca/amesbah/resources/papers/icse12.pdf)
- **Citation** [THESIS]: G. Gharachorlu, "Code smells in cascading style sheets: an empirical study and a predictive model", MASc thesis, University of British Columbia, 2014. It catalogues 26 CSS smells and errors with automated detection and studies 500 websites (5,060 CSS files, more than 10M lines of CSS). It builds a model that predicts a site's total smell count and includes a study of unused CSS on 187 websites. [UBC Open Collections](https://open.library.ubc.ca/collections/24/items/1.0167067)
- **Citation** [PR]: M. Hague, A. W. Lin, C.-H. L. Ong, "Detecting redundant CSS rules in HTML5 applications: a tree rewriting approach", Proc. OOPSLA 2015, pp. 1-19, DOI 10.1145/2814270.2814288. [Crossref](https://doi.org/10.1145/2814270.2814288); preprint [arXiv:1412.5143](https://arxiv.org/abs/1412.5143) (v4, 18 Aug 2015). The abstract says dynamic analysis (testing) is the only earlier method that accounts for JavaScript-driven DOM changes, but it "cannot soundly prove redundancy of CSS rules". They model HTML5 applications as monotonic tree-rewriting systems. Deciding redundancy ranges from P to EXP for the subproblems, and the algorithm reduces it to symbolic pushdown systems. [arXiv abstract](https://arxiv.org/abs/1412.5143)
- **Citation** [PR]: M. Hague, A. W. Lin, C.-D. Hong, "CSS minification via constraint solving", ACM TOPLAS 41(2), 2019, pp. 1-76, DOI 10.1145/3310337. It was presented at POPL 2019 as a journal-first paper. [Crossref](https://doi.org/10.1145/3310337); [POPL 2019 listing](https://popl19.sigplan.org/details/POPL-2019-Research-Papers/6/CSS-Minification-via-Constraint-Solving); [arXiv:1812.02989](https://arxiv.org/abs/1812.02989); tool [SATCSS](https://github.com/matthewhague/sat-css-tool)
- SATCSS semantics: a CSS file is a "covering" of a CSS-graph (selectors, properties, selector/declaration edges, and an order ≺ on edges), with last-occurrence semantics. Two files are equivalent if they cover the same graph, meaning they "specify the same property declarations on any node of any given DOM". So equivalence is over all DOM trees, not one document. The order ≺ is needed when two selectors can match the same node (selector intersection) and specificity does not settle the conflict. Within a rule, property order matters, because of fallbacks such as `color: red; color: rgba(...)`. [ar5iv full text](https://ar5iv.labs.arxiv.org/html/1812.02989)
- SATCSS limitations (from the parts read): pseudo-elements are left out of the main model ("relegated into the appendix"). A fixed set of pseudo-classes (`:hover`, `:focus`, `:enabled`, `:nth-child`, ...) is modelled. Some pseudo-classes are rewritten or dropped (`:lang()`, `:indeterminate`), and default namespaces are not supported. Results: median 3.79% and third-quartile 6.90% size savings alone. Run after other minifiers, the third quartile is 8.26% and the median 4.70%. [ar5iv full text](https://ar5iv.labs.arxiv.org/html/1812.02989)
- **Citation** [PR]: P. Genevès, N. Layaïda, V. Quint, "On the analysis of cascading style sheets", Proc. WWW 2012, pp. 809-818, DOI 10.1145/2187836.2187946. It applies tree logics to analyse style sheets statically and flag errors, going beyond syntax validators. [Crossref](https://doi.org/10.1145/2187836.2187946); [INRIA PDF](https://wam-guernesey.inrialpes.fr/publications/2012/WWW2012.pdf)
- **Citation** [PR]: M. Bosch, P. Genevès, N. Layaïda, "Automated refactoring for size reduction of CSS style sheets", Proc. ACM DocEng 2014, pp. 13-16, DOI 10.1145/2644866.2644885. A static analyser built on tree logics that removes redundant declarations and rules. [Crossref](https://doi.org/10.1145/2644866.2644885); [HAL](https://hal-univ-tlse3.archives-ouvertes.fr/INRIA/hal-01021332). The companion IJCAI 2015 abstract "Reasoning with Style" says the method removes redundant and inaccessible rules "without affecting the layout of any document the style sheet is applied to". [IJCAI 2015](https://www.ijcai.org/Abstract/15/315)
- **Citation** [PR]: L. Punt, S. Visscher, V. Zaytsev, "The A?B*A pattern: undoing style in CSS and refactoring opportunities it presents", Proc. ICSME 2016, pp. 67-77, DOI 10.1109/ICSME.2016.73, with a tool paper at pp. 613, DOI 10.1109/ICSME.2016.90. [Crossref](https://doi.org/10.1109/ICSME.2016.73)

### Inferences
- CILLA's selector coverage idea (which selectors matched any element in any captured state) works as a **coverage metric for onionskin's state corpus**. If a refactor touches a rule whose selector never matched in any captured page or state, the diff says nothing about that rule. Onionskin should report such rules as "unverified", not "neutral".
- Hague et al. formalise why a crawl-based check is unsound. A JS-reachable DOM that was never captured can expose a difference. Onionskin's claim should be scoped as "visually neutral on this corpus of pages × states × widths".
- SATCSS treats property order within a rule as significant (fallback declarations) and uses the same last-occurrence cascade model as FSE 2014. A hand refactor that reorders declarations is a classic way to break fallbacks. A resolved-value diff in a modern browser will not show the problem, because that browser picks the same winner either way. The breakage shows only in browsers that need the fallback. **Hence single-engine diffs cannot validate fallback or vendor-prefix changes.**

### Gaps
- The titles "Sound, complete and efficient minification of CSS" and an "UNCOVER" tool could not be verified. The POPL 2019 Hague-Lin-Hong paper is "CSS Minification via Constraint Solving" (TOPLAS). The tool name for the OOPSLA 2015 paper was not confirmed from the sources read, and neither were its evaluation numbers.
- How SATCSS treats shorthand vs longhand, !important, media queries and value equivalence (e.g. `#f60` vs `#ff6600`) is in sections that were not read.
- Gharachorlu's list of 26 smells and the Punt et al. paper content were not read.
- How CILLA handles state-dependent pseudo-classes (`:hover`, `:focus`) in its XPath translation is not stated in the passages read.

## 3. Formal semantics and symbolic reasoning about layout (Cassius, VizAssert, Troika; attribute grammars)

### Takeaway
Panchekha and colleagues formalised a large fragment of CSS 2.1 block, inline and float layout as SMT constraints in linear real arithmetic. VizAssert states layout properties in a "visual logic": universally quantified formulas over rendered boxes, with tree navigation, geometry and colours. It proves them over bounded ranges of rendering parameters, or returns a counterexample with concrete width and font size. This is the closest prior art for stating layout properties symbolically. Its limits are no JavaScript, no tables, no vertical-align or RTL, and a known, fixed CSS file and DOM.

### Cited Findings
- **Citation, Cassius** [PR]: P. Panchekha, E. Torlak, "Automated reasoning for web page layout", Proc. OOPSLA 2016, pp. 181-194, DOI 10.1145/2983990.2984010. It presents "the first mechanized formalization of a substantial fragment of the CSS semantics", reduces it to quantifier-free linear real arithmetic, and prototypes tools for verifying, debugging and synthesising CSS. [Crossref](https://doi.org/10.1145/2983990.2984010); [SPLASH listing](https://2016.splashcon.org/details/splash-2016-oopsla/22/Automated-Reasoning-for-Web-Page-Layout); code [uwplse/Cassius](https://github.com/uwplse/Cassius)
- **Citation, VizAssert** [PR]: P. Panchekha, A. T. Geller, M. D. Ernst, Z. Tatlock, S. Kamil, "Verifying that web pages have accessible layout", Proc. PLDI 2018, pp. 1-14, DOI 10.1145/3192366.3192407. [Crossref](https://doi.org/10.1145/3192366.3192407); [PDF](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-pldi2018.pdf)
- VizAssert motivation: guidelines "must hold on the infinitely many possible renderings ... generated by differing screen sizes, fonts, and other user preferences". In practice they are tested "by manual inspection of a few renderings" or by pixel comparison (Selenium, Sikuli, Raven), which "only consider a particular subset of rendering parameters". [PLDI18 PDF](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-pldi2018.pdf)
- Visual logic grammar (Fig. 3): an assertion is ∀ b1, ... ∈ B : cond, where B is the set of boxes in a rendering. Conditions are boolean combinations of real equalities and inequalities, box equality, box type (window, inline, line, text, block) and whitespace. Real terms are box edges (top, right, bottom, left), colour channels, and sums and constant multiples. Colours are a box's fg/bg (with a blending operator). Box terms navigate parent, first-child, last-child, next, prev and ancestor(cond). Only linear arithmetic and universal quantification are allowed, with no recursion, so that queries stay quantifier-free for the SMT solver. [PLDI18 PDF](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-pldi2018.pdf)
- The 14 encoded assertions include: text at least 14px tall, text resizable to 200%, lines no longer than 80 characters, screen-reader-only elements off-screen, no horizontal scrolling, headings forming a visual hierarchy, no overlapping text, appropriate line spacing, sufficient contrast, text not overlapping images, dropdowns hidden when not selected, and columns vertically aligned. [PLDI18 PDF](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-pldi2018.pdf)
- VizAssert evaluation: every assertion was verified for all screen widths 1024-1920 px, heights 800-1080 px and default font sizes 16-32 px. Across 502 page/assertion pairs on 62 professionally designed pages there were 414 verifications, 64 true violations, 13 false positives and 11 timeouts (30 min limit, Z3 4.5.1). Counterexamples name the boxes and the rendering parameters (window size, font size), so the developer can reproduce them in a browser. [PLDI18 PDF](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-pldi2018.pdf)
- VizAssert design: it assumes a known CSS file, so "selector matching and cascading [run] outside the SMT solver". That allows descendant, child and pseudo-class selectors, and sound handling of em/ex units. "Finitization reductions" turn the standard's arbitrary-size sets into finite forms for line height (a running max of ascent and descent around the baseline), margin collapsing and floats. Against W3C conformance tests (sections 8.3, 9.5, 10.8), it passes all but 91 tests, and those 91 use unsupported features (vertical alignment, right-to-left text, SVG). [PLDI18 PDF](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-pldi2018.pdf)
- Subpixel note: "Minute rounding errors sometimes cause Firefox's rendering of the conformance tests to differ from that mandated by the standard by a fraction of a pixel", so the authors compared against Firefox "up to an accuracy of a sixth of a pixel". [PLDI18 PDF](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-pldi2018.pdf)
- VizAssert limitations (Sec. 6): it "currently handles only HTML and CSS". JavaScript-modified pages would need a JS analysis to list the possible DOMs, and temporal operators could express dynamic properties. Tables "present significant research challenges". [PLDI18 PDF](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-pldi2018.pdf)
- **Citation, Troika** [PR]: P. Panchekha, M. D. Ernst, Z. Tatlock, S. Kamil, "Modular verification of web page layout", PACMPL 3 (OOPSLA 2019), pp. 1-26, DOI 10.1145/3360577. A search-result summary describes it as a proof assistant for using VizAssert modularly; the paper was not read. [Crossref](https://doi.org/10.1145/3360577)
- **Attribute grammars** [PR]: L. A. Meyerovich, R. Bodik, "Fast and parallel webpage layout", Proc. WWW 2010, pp. 711-720, DOI [10.1145/1772690.1772763](https://doi.org/10.1145/1772690.1772763); L. A. Meyerovich, M. E. Torok, E. Atkinson, R. Bodik, "Parallel schedule synthesis for attribute grammars", Proc. PPoPP 2013, pp. 187-196, DOI [10.1145/2442516.2442535](https://doi.org/10.1145/2442516.2442535). The VizAssert paper says attribute-grammar formalisations cover a smaller CSS subset than VizAssert and are "not meant for verification, only rendering". [PLDI18 PDF](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-pldi2018.pdf)
- Panchekha's 2019 UW PhD dissertation, also titled "Automated Reasoning for Web Page Layout" (advisors Ernst and Tatlock), collects this work. [UW ResearchWorks](https://digital.lib.washington.edu/researchworks/handle/1773/44148)

### Inferences
- Visual logic maps closely onto a Clojure data DSL over captured box trees. Onionskin can borrow the vocabulary (box edges, type, fg/bg colour, parent/next/prev/ancestor navigation, universal quantification over boxes). It would check assertions over *sampled concrete renderings* instead of proving them symbolically. That trades soundness for coverage of the whole CSS and JS feature set.
- A refactor-neutrality check is a relational property (two renderings, before and after), while VizAssert checks single-rendering properties. Both can share one capture format: per box, the geometry and resolved style, keyed by element identity.
- VizAssert's parameter space (width range, height range, default font size) is a principled list of rendering parameters. Onionskin's matrix should include the **user default font size** as well as viewport width, because em/rem refactors (e.g. px to rem) can be neutral at 16px and not at 20px.

### Gaps
- Cassius's exact supported subset and Troika's specification method were not read in detail.
- No formal work was found that proves *equivalence of two style sheets with respect to layout* (as opposed to rule-level declaration equivalence, or single-page assertions).

## 4. Practitioner methods for verifying CSS refactors (visual regression, computed-style diffing) and related testing research

### Takeaway
Practitioners mostly rely on screenshot-based visual regression testing (Lindstrom's book recommends it). There are now a few tools that diff computed styles and boxes instead. The OCaml package **sosie** (Aug 2026) is near-direct prior art for onionskin. It captures `getBoundingClientRect` and `getComputedStyle` for a page, compares snapshots against an explicit property whitelist, excludes unreliable shorthands, and favours spurious diffs over missed ones. Peer-reviewed web-testing work adds DOM-and-image hybrids (WebDiff, X-PERT, WebSee) and a principled way to choose viewport widths (ReDeCheck).

### Cited Findings
- **Book** [BOOK]: S. Lindstrom, *CSS Refactoring*, O'Reilly, Nov 2016, 160 pp., ISBN 9781491906422. Chapter 5 "Testing" has sections "Visual Regression Testing", "Tips for Visual Regression Testing" and "Visual Regression Testing with Gemini", along with multi-browser testing and developer tools. ### Inferences
- sosie confirms the design space and supplies two concrete rules for onionskin: (1) compare longhands from an explicit, versioned whitelist, and treat the whitelist as the stated guarantee; (2) prefer false alarms to misses. Parse the media-query breakpoints, sample each side of every breakpoint (b-1, b, b+1), add a uniform grid, and binary-search between widths where the before/after diff appears or disappears. This finds the width range of a regression, not just one width.

## 5. What getComputedStyle actually returns: computed, used and resolved values, and other specification pitfalls

### Takeaway
`getComputedStyle` returns **resolved values**, a historical mix. For colours it is the used value. For width/height/margin/padding (when the element is rendered and the property applies) and for insets of positioned elements it is the used value, in px. For line-height it is "normal" or the used value. For everything else it is the computed value. The result is live and read-only, lists longhands in lexicographic order (plus custom properties), and can be deliberately false for `:visited`. `computedStyleMap()` returns true computed values (e.g. `50%`), but it is not Baseline.

### Cited Findings
- CSSOM §9 "Resolved Values" [SPEC]: getComputedStyle() "had to remain the same for compatibility with deployed scripts" when the CSS meaning of "computed value" changed, so the "resolved value" concept was introduced. Rules per longhand: (a) background-color, border colours, box-shadow, caret-color, color, outline-color give the **used value**; (b) line-height gives "normal" if the computed value is normal, otherwise the used value; (c) block-size, height, inline-size, width, margin-* and padding-* give the used value "if the property applies to the element or pseudo-element and the resolved value of display is not none or contents", otherwise the computed value; (d) inset properties (top/right/bottom/left, inset-*) give the used value only if the element is positioned, display is not none or contents, and the property is not over-constrained, otherwise the computed value; (e) any other property gives the computed value. [CSSOM ED §9](https://drafts.csswg.org/cssom/#resolved-values)
- CSSOM §7.2 getComputedStyle(elt, pseudoElt) [SPEC]: pseudoElt is parsed as a `<pseudo-element-selector>`, and CSS2 pseudo-elements accept the single- or double-colon form. On parse failure, or for `::slotted()`/`::part()`, the object is null and the declarations are empty. When the element is connected and rendered, the declarations are all supported **longhands in lexicographical order**, with resolved values, plus custom properties (their order is undefined, issue #4947). The object is live, with the readonly flag set. [CSSOM ED §7.2](https://drafts.csswg.org/cssom/#dom-window-getcomputedstyle). The spec text read says invalid pseudo-elements give empty declarations, while its change log and MDN say a TypeError is thrown. **These sources conflict.** [MDN getComputedStyle](https://developer.mozilla.org/en-US/docs/Web/API/Window/getComputedStyle)
- MDN [REF]: getComputedStyle "returns a live read-only CSSStyleProperties object containing the resolved values". During an animation it returns "the computed value at the current point in the animation". It works for `::before`, `::after`, `::marker` and others. sRGB colours serialise as `rgb()` when alpha is exactly 1 and `rgba()` otherwise, and other colour spaces as `lab()`, `lch()`, `oklab()`, `oklch()` or `color()`. Browsers "may lie about the computed styles for a visited link" to avoid history leaks. MDN says shorthands are present as entries too (e.g. `border-top` alongside its longhands). [MDN getComputedStyle](https://developer.mozilla.org/en-US/docs/Web/API/Window/getComputedStyle). This conflicts with the CSSOM declaration list (longhands only) and with sosie's finding that some shorthands do not serialise reliably. [sosie whitelist](https://ocaml.org/p/sosie/0.1.2/sosie.shared/Sosie_shared/Property_whitelist/index.html)
- MDN [REF]: `Element.computedStyleMap()` "contains computed values, not resolved values". For example, `width: 50%` stays a percentage there, while getComputedStyle gives post-layout pixels. Values are CSS Typed OM objects, not strings, and the API "is not Baseline". [MDN computedStyleMap](https://developer.mozilla.org/en-US/docs/Web/API/Element/computedStyleMap)
- Subpixel layout [NPR]: WebKit (and historically Blink) LayoutUnit represents layout values "as multiples of 1/64th pixel", and these are snapped to integer pixels at paint time. [WebKit wiki LayoutUnit](https://trac.webkit.org/wiki/LayoutUnit?format=txt). A 2015 www-style thread notes that Chromium kept older integer measurement APIs (offset*/client*) for web compatibility and points to getClientRects for precise values. [www-style 2015-02](https://lists.w3.org/Archives/Public/www-style/2015Feb/0332.html)
- Fonts [REF]: `document.fonts.ready` "will only resolve once the document has completed loading fonts, layout operations are completed, and no further font loads are needed". [MDN FontFaceSet.ready](https://developer.mozilla.org/en-US/docs/Web/API/FontFaceSet/ready)

### Inferences
- Because of the resolved-value mix, a getComputedStyle diff is partly a style diff and partly a layout diff. A change in `width` can mean the declared value changed, or that some ancestor's layout changed. Onionskin should label each property as "computed" or "used/layout-dependent" (per CSSOM §9) and report layout-dependent diffs together with box diffs, so that one root cause (e.g. a changed parent width) does not appear as hundreds of independent diffs.
- The browser's serialisation already performs the FSE 2014 / ASE 2016 "Type II" value normalisation (named, hex and hsl colours all become `rgb()`; lengths become px for used values). Comparing serialised strings is therefore mostly safe. Remaining traps: `currentcolor` vs explicit colours, the order of fields in values like `font-family` lists or `transform` matrices, and colour-space changes (an `oklch()` refactor serialises differently even if it looks identical). These need explicit equivalence rules or tolerance.
- For non-rendered elements (`display: none`, or `display: contents`), width, height, margin and padding fall back to computed values (e.g. `auto` or percentages). A refactor that changes hidden elements will show diffs there, but they say nothing about appearance until that state is shown.
- Since `computedStyleMap` gives true computed values (percentages kept), an optional "computed-only" capture would separate *style* changes from *layout* changes. It only works in engines that support it, which (per MDN) is not all major browsers.
- Box comparison needs a tolerance. A 1/64 px layout unit plus engine rounding means exact float equality of `getBoundingClientRect` gives noise across machines and zoom levels, but not within one engine and machine. VizAssert needed a 1/6 px tolerance against Firefox. A sensible default is exact comparison within one engine and machine run, and a configurable epsilon (e.g. 1/64 px, or rounding to device pixels) across runs.
- Capture must wait for `document.fonts.ready`. Animations and transitions must be disabled or settled, because getComputedStyle returns mid-animation values. Web fonts should be pinned to avoid fallback-font noise.

### Gaps
- Whether current Chromium returns getBoundingClientRect values snapped to 1/64 px was not verified from Chromium source.
- How browsers really serialise shorthands in getComputedStyle today (per property, per engine) was not established. The sources conflict, so test each target engine.

## 6. Lessons for onionskin: which equivalence notion, which pitfalls, which pages and states

### Takeaway
Use a layered equivalence. (1) Resolved longhand styles per element and per pseudo-element. (2) Box geometry: border-box rect, plus client rects for inline fragments. (3) Optionally pixels as a last resort. All are keyed by stable element identity and evaluated over a stated matrix of pages × UI states × viewport widths × user font sizes (× colour scheme and print). Report selector coverage so that "neutral" is scoped to what was actually exercised.

### Cited Findings
- All formal and static work defines presentation as the declarations or property values that reach each element: FSE 2014 ("property values that are eventually applied to the target document elements") and SATCSS ("same property declarations on any node of any given DOM"). [FSE14 PDF](https://people.ece.ubc.ca/amesbah/resources/papers/fse14.pdf); [SATCSS ar5iv](https://ar5iv.labs.arxiv.org/html/1812.02989)
- Computed-value equivalence alone misses layout effects that VizAssert-style properties capture (overlap, line length, alignment). Those depend on box geometry, which depends on rendering parameters (width, height, default font size). [PLDI18 PDF](https://homes.cs.washington.edu/~mernst/pubs/verify-layout-pldi2018.pdf)
- Dynamic approaches are only as good as the captured states. FSE 2014 names unvisited DOM states as a threat, and Hague et al. state that testing "cannot soundly prove redundancy". [FSE14 PDF](https://people.ece.ubc.ca/amesbah/resources/papers/fse14.pdf); [arXiv:1412.5143](https://arxiv.org/abs/1412.5143)
- Selector coverage across visited states (unmatched or ineffective selectors) is an established measure. [ICSE12 PDF](https://people.ece.ubc.ca/amesbah/resources/papers/icse12.pdf)
- Width sampling: uniform grid plus stylesheet breakpoints plus binary search. [ReDeCheck PDF](https://eprints.whiterose.ac.uk/116991/1/c49.pdf)
- Shorthand traps: shorthand `none` resets the other longhands to initial values (ASE 2016 bug), and some shorthands do not serialise reliably in getComputedStyle (sosie). [ASE16 PDF](https://users.encs.concordia.ca/~nikolaos/publications/ASE_2016.pdf); [sosie whitelist](https://ocaml.org/p/sosie/0.1.2/sosie.shared/Sosie_shared/Property_whitelist/index.html)
- Forced pseudo-classes and starting-style can be set through CDP. `:visited` styles may be falsified by the browser. [CSS.pdl](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/CSS.pdl); [MDN getComputedStyle](https://developer.mozilla.org/en-US/docs/Web/API/Window/getComputedStyle)

### Inferences
- **Equivalence levels (strict to loose)**:
  - (a) *Style-neutral*: every whitelisted resolved longhand is equal on every matched element and on its `::before`, `::after` and `::marker` (and `::placeholder`, `::selection`, `::first-line`, `::first-letter` where relevant).
  - (b) *Layout-neutral*: boxes are equal within epsilon.
  - (c) *Visually neutral*: pixels are equal.
  
  Level (a) is stricter than appearance in some ways: `color` changes on an element without text, or margins on an element that is `display: none` in that state, show up as diffs. It is weaker in others: properties outside the whitelist, images, canvas, scrollbars, `content` of pseudo-elements not queried, and fallback/prefix behaviour in other engines all go unchecked. Report (a) and (b) separately, and give a reason for each diff, such as "declared value changed" vs "layout-dependent value changed because of ancestor X".
- **Element identity**: refactors may rename classes, so match elements by DOM path or tag/index path (or by a stable data attribute), not by selector. If the HTML also changed, flag unmatched elements explicitly, never silently.
- **Inherited and initial values**: comparing every element (including text-bearing inline elements) captures inheritance shifts automatically. Moving `font-*` from `body` to `main` is neutral only if every element under `body` still resolves to the same values. Inherited custom properties should be captured too, because `var()` refactors move values through them.
- **Cascade-only changes that compare equal in one engine**: fallback declarations, vendor prefixes, `@supports` branches and `!important` reorders can be neutral in the engine under test and still break other engines. Treat a single engine as one point in the "rendering parameters" space, and allow a multi-engine matrix (Chromium, Firefox, WebKit) for such changes.
- **States to cover**: the static pages; each interactive state reachable by JS (menus open, dialogs, tabs, validation errors, empty and loading states); forced `:hover`/`:focus`/`:focus-visible`/`:focus-within`/`:active` on interactive elements; `:target`; `:checked`/`:disabled`/`:invalid` form states; `prefers-color-scheme` dark and light; `prefers-reduced-motion`; `print` media; and at least two user default font sizes (16px and 20px or more, following VizAssert). `:visited` cannot be checked through getComputedStyle.
- **Widths**: collect every `@media` and `@container` breakpoint from the before and after style sheets (a refactor may move breakpoints). Test b-1, b and b+1 for each, add a coarse uniform grid (ReDeCheck used 60 px), and binary-search where diffs start or stop.
- **Choosing pages**: pick the smallest set of pages and states that gives maximal selector coverage. Instrument the "before" CSS and greedily add pages and states until no new selectors match (CILLA-style matched sets). Report the selectors that are never matched, and flag a refactor that touches any of them as unverified.
- **Noise control**: wait for `document.fonts.ready` and pinned fonts; disable animations and transitions (or capture end states); fix the device pixel ratio and zoom; compare boxes exactly within one run and with epsilon across machines.
- **A symbolic layer later**: a VizAssert-like assertion DSL over captured box trees (∀ boxes, navigation, geometry, colours) can express invariants such as "no text overlaps", "no horizontal scroll" or "headings get smaller by level". These can be checked on every sampled rendering. Onionskin would then be a *bounded, sampled* version of VizAssert that covers the full CSS and JS of real pages.

### Gaps
- No empirical study was found on how often computed-style-neutral refactors are visually non-neutral, or the reverse, so the false-positive and false-negative trade-off of level (a) vs (b) vs (c) is unknown.
- No source was found that lists which CSS properties have visible effects but are not exposed through getComputedStyle (beyond sosie's whitelist choices). Onionskin's whitelist must be justified empirically.
