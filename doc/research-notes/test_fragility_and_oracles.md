# Fragility, flakiness and oracle design in GUI and visual tests (grounding for onionskin)

Tags used below: [PR] = peer-reviewed (journal, conference or workshop paper). [non-PR] = blog, documentation, thesis, or preprint not yet accepted anywhere. Where a number comes from a secondary summary or a search excerpt instead of the paper itself, that is stated.

Citation corrections found while checking:

## 1. Why do GUI and web tests break when the application changes, how often, and what locator strategies reduce breakage?

### Takeaway
Element locators cause most test breakage. Over 70% of record/replay web test breakages come from locators (Hammoudi et al.), and about 70% of changes to Android GUI test code are caused by GUI fragility (Coppola et al.). Robust locator choice (unique IDs, generated robust XPaths, contextual locators) and keeping locators out of the assertions cut that cost a lot. In one study Robula+ reduced locator fragility by 90% compared with absolute XPaths.

### Cited Findings
- [PR] Hammoudi, Rothermel, Tonella, "Why do Record/Replay Tests of Web Applications Break?", ICST 2016, pp. 180-190, doi:10.1109/ICST.2016.16. They built a taxonomy of breakages from 453 versions of popular web apps with 1,065 individual test breakages. [Source](https://doi.org/10.1109/ICST.2016.16)
- Hammoudi et al., numbers from a secondary summary (The Morning Paper blog, not the paper itself): the main study used 300 versions of five apps (722 breakages), and a validation used 153 versions of three more apps (343 breakages). The taxonomy covered all of the validation breakages without changes. The five top-level causes are locators, values and actions, page reloading, user session times, and popup boxes. "Locators caused over 73% of the test breakages", and over 50% of all breakages came from attribute-based locators (IDs, names), as opposed to structure-based ones (XPath, CSS, index). [Source](https://blog.acolyer.org/2016/05/30/why-do-recordreplay-tests-of-web-applications-break/)
- [PR] Coppola, Morisio, Torchiano, "Mobile GUI Testing Fragility: A Study on Open-Source Android Applications", IEEE Transactions on Reliability, 2019, doi:10.1109/TR.2018.2869227. This study covers six GUI testing frameworks on GitHub Android projects and defines 21 metrics. GUI test methods are modified often, and "a relevant portion (70% on average)" of those modifications comes from GUI-related fragility. More than 7% of all modified lines between releases are in these GUI test classes, which is more than for plain JUnit test code. [Source](https://doi.org/10.1109/TR.2018.2869227)

The authors write that web test scripts are fragile and "even small changes in the page layout can break a number of tests". - [PR] Grechanik, Xie, Fu, "Experimental assessment of manual versus tool-based maintenance of GUI-directed test scripts", ICSM 2009, doi:10.1109/ICSM.2009.5306345. In the same 45-person study, tool support helped programmers fix scripts faster. Experienced test engineers were about as productive by hand. [Source](https://doi.org/10.1109/ICSM.2009.5306345)
- [PR] Memon, "Automatically repairing event sequence-based GUI test suites for regression testing", ACM TOSEM, 2008, doi:10.1145/1416563.1416564. "A large number of test cases become unusable" after GUI changes. Some kinds of "dominator" events, when modified, make many test cases unusable. Many tests can be repaired automatically. [Source](https://doi.org/10.1145/1416563.1416564)
- [PR] Huang, Cohen, Memon, "Repairing GUI Test Suites Using a Genetic Algorithm", ICST 2010, doi:10.1109/ICST.2010.39. [Source](https://doi.org/10.1109/ICST.2010.39)
- [PR] Test repair tools for web tests: Roy Choudhary, Zhao, Versee, Orso, "WATER: Web Application TEst Repair", ETSE 2011, doi:10.1145/2002931.2002935. Hammoudi, Rothermel, Stocco, "WATERFALL: an incremental approach for repairing record-replay tests of web applications", FSE 2016, doi:10.1145/2950290.2950294. [Source](https://doi.org/10.1145/2002931.2002935); [Source](https://doi.org/10.1145/2950290.2950294)
- [PR] Stocco, Yandrapally, Mesbah, "Visual web test repair" (Vista), ESEC/FSE 2018, doi:10.1145/3236024.3236063. Web tests "are prone to break frequently". On 2,672 tests over 86 releases of four apps, the tool repaired 81% of breakages on average, 41% more than earlier techniques. [Source](https://doi.org/10.1145/3236024.3236063)

### Inferences
- In this literature, most breakage comes from finding the element, not from checking it. A layout library that adds relational assertions still inherits all the fragility of its selectors. So the selector layer deserves as much design care as the assertion vocabulary.
- Attribute locators (IDs, names) break most often in Hammoudi's data. But the blog author notes this may just reflect how widely they are used, and the base rate is unknown. Coppola's guideline is still to give widgets unique IDs. So the evidence favours explicit, stable, test-facing hooks over structural paths. It does not favour "attributes" in general.
- The WCRE 2013 result (higher writing cost, lower maintenance cost) supports writing layout tests as code with reusable named element definitions, instead of recorded or generated per-test selectors.

### Gaps
- Exact per-category counts from Hammoudi et al. (values/actions, page reloading, sessions, popups) and the split between attribute and structure locators come only from Figure 3 of the paper, which was not readable here. The 73% figure is from a secondary summary.
- Numbers and the cause taxonomy from Coppola et al. EMSE 2019 could not be retrieved (the PoliTO repository returned 403).
- Per-application robustness numbers from Leotta et al. ICWE 2014 could not be retrieved (the authors' server refused connections). Only the headline direction is reported.

## 2. What does industry experience with visual GUI testing (image recognition) show about breakage and maintenance?

### Takeaway
Visual GUI testing (VGT) works in industry and finds real defects. But it has many practical problems (58 kinds in one study), and Spotify dropped it after years of use for a more robust, non-visual test interface. In a direct comparison on a hybrid app, visual scripts were more fragile than layout-based ones (60% vs 47% of test methods changed). The visual suite also caught a display defect that the layout-based suite missed.

### Cited Findings
- [PR] Alégroth, Feldt, Ryrholm, "Visual GUI testing in practice: challenges, problems and limitations", Empirical Software Engineering 20, 2015, pp. 694-744, doi:10.1007/s10664-013-9293-5. This was a case study at two Swedish companies that build safety-critical software. Four test suites with more than 300 manual system tests were moved to VGT. The authors found 58 distinct challenges, problems and limitations, grouped into 26 types. Four high-level solutions would address about half of them. Nine defects were found, five of them unknown to experienced manual testers. VGT was judged "still valuable, flexible and considered cost-effective". (From the Chalmers abstract page.) [Source](https://research.chalmers.se/en/publication/218525)
- [PR] Alégroth, Feldt, "On the long-term use of visual GUI testing in industrial practice: a case study", Empirical Software Engineering, 2017, doi:10.1007/s10664-016-9497-6. Spotify adopted VGT, used it for several years, and then dropped it for an in-house "Test interface". That interface was "considered more robust and flexible" but "does not test the actual GUI as shown to the user like VGT does". Long-term VGT needs organisational change and engineering best practices. [Source](https://doi.org/10.1007/s10664-016-9497-6)
- [PR] Alégroth, Feldt, Olsson, "Transitioning Manual System Test Suites to Automated Testing: An Industrial Case Study", ICST 2013, doi:10.1109/ICST.2013.14. The VGT transition succeeded, but problems such as testing a distributed system and "tool volatility" had to be solved first. Maintenance costs were reported as feasible. [Source](https://doi.org/10.1109/ICST.2013.14)
- [PR] An earlier comparison of two VGT tools on a safety-critical system at Saab AB found that script maintenance costs and robust test execution were open problems. This is from a search excerpt of the Chalmers record "Automated system testing using visual GUI testing tools: A comparative study in industry". [Source](https://research.chalmers.se/en/publication/159702)
- [PR] Nass, Alégroth, Feldt, "Why many challenges with GUI test automation (will) remain", 2021. This is a literature review that identifies 24 challenges in GUI test automation (from a search excerpt; the venue was not confirmed here). [Source](https://research.chalmers.se/publication/524165)
- [PR] Coppola, Ardito, Torchiano, "Fragility of layout-based and visual GUI test scripts: an assessment study on a hybrid mobile application", A-TEST 2019 (10th ACM SIGSOFT workshop), doi:10.1145/3340433.3342824. The app was a Cordova app (about 40,000 users) studied over 25 releases, with 15 test methods per suite. Appium (layout-based) was compared with EyeAutomate (visual). Results for Appium vs EyeAutomate: 47% (7/15) vs 60% (9/15) of test methods modified at least once; average per-release modified-method ratio 2.8% vs 3.9%; releases needing changes 20.9% vs 29.2%. Causes for layout-based tests were text change (5), behaviour change (2), widget substitution (2) and widget removal (1). Causes for visual tests were graphic change (5), text change (3), widget arrangement (2), behaviour change (2) and widget addition (1). The paper recommends unique IDs for all widgets and combining the two kinds of suite, because the visual suite found a visual defect the layout suite missed. (The paper's abstract mixes up two of its metrics; the numbers here are from its tables.) [Source](https://ar5iv.labs.arxiv.org/html/1907.08164); [Source](https://doi.org/10.1145/3340433.3342824)

### Inferences
- The visual-test failures in Coppola's data (graphic change, widget arrangement) are the kind of change a symbolic layout test ("X is left of Y", "X is inside Y") is designed to tolerate or report precisely. The textual failures (text change) are a selector problem that onionskin should avoid by not selecting on visible text by default.
- Spotify's choice shows that teams accept losing "what the user sees" fidelity to get robustness. onionskin's design tries to keep both: it reads the real rendered layout (computed boxes and styles) but asserts on it symbolically.
- Combining layout-based and visual suites caught more defects in Coppola's study. This supports an opt-in exact or visual layer for the few places where exact appearance matters.

### Gaps
- The full list of the 58 problem types in Alégroth et al. 2015 (for example, how many concern image recognition false matches) was not available. Only the abstract was read.
- No quantitative maintenance-cost figures from the Spotify study were retrieved.

## 3. How common is test flakiness, and what makes UI tests flaky?

### Takeaway
Async waiting is the main cause of flaky tests in general and of flaky UI tests: 45% of 235 flaky UI tests in Romano et al. The largest single subcategory is acting or asserting before resources finish rendering. Animation timing, browser and platform rendering differences, and window-size layout differences are smaller but explicit categories. At Google, large and WebDriver tests are far flakier than small tests.

### Cited Findings
- [PR] Romano, Song, Grandhi, Yang, Wang, "An Empirical Analysis of UI-Based Flaky Tests", ICSE 2021, doi:10.1109/ICSE43902.2021.00141 (arXiv:2103.02669). They studied 235 flaky UI tests (152 web, 83 Android) from 62 projects. From Table IV, the root causes are:
  - Async Wait: 106 by the table, but the text says 105 (45.1%); 52.0% of web tests vs 32.5% of mobile. Subcategories: Resource Rendering 61, Animation Timing 26, Network Resource Loading 19.
  - Environment: 44. Platform Issue 34 and Layout Difference 10 (9 of them web).
  - Test Runner API Issue: 40. DOM Selector Issue 16 and Incorrect Test Runner Interaction 24.
  - Test Script Logic: 45. Incorrect Resource Load Order 22, Test Order Dependency 12, Unordered Collections 5, Randomness 5, Time 1.
  [Source](https://ar5iv.labs.arxiv.org/html/2103.02669); [Source](https://doi.org/10.1109/ICSE43902.2021.00141)
- Romano et al., details: Resource Rendering covers tests that touch elements before they render, and screenshot tests that show visual differences. One Platform Issue example is an Internet Explorer rendering artifact in ring-ui screenshot tests. One Layout Difference example is a dropdown cut off because default window sizes differ between browsers. Fixes (Table VI): refactor test logic 75, remove the test 73, fix the await mechanism 43, add or increase delay 21, change library version 7, fix API access 12, disable animations 4. The paper's text percentages for fixes do not match its own table counts. [Source](https://ar5iv.labs.arxiv.org/html/2103.02669)
- [PR] Luo, Hariri, Eloussi, Marinov, "An Empirical Analysis of Flaky Tests", FSE 2014, doi:10.1145/2635868.2635920. They studied 201 commits that likely fix flaky tests in 51 open-source projects. From the paper's introduction: at Google, the TAP system averaged 1.6M test failures per day, and 73K of them (4.56%) came from flaky tests. Google reruns a failing test 10 times and labels it flaky if any rerun passes. [Source](https://doi.org/10.1145/2635868.2635920)
- Luo et al.: the top three root-cause categories are Async Wait, Concurrency and Test Order Dependency (confirmed from a search summary). [Source](https://2024.esec-fse.org/details/fse-2024-plenary-events/10/An-empirical-analysis-of-flaky-tests)
- [PR] Parry, Kapfhammer, Hilton, McMinn, "A Survey of Flaky Tests", ACM TOSEM, 2022, doi:10.1145/3476105. This survey covers 76 papers on causes, costs, detection, and mitigation. It cites a developer survey in which 59% said they deal with flaky tests monthly, weekly or daily. [Source](https://doi.org/10.1145/3476105)
- [PR] Gruber, Fraser, "A Survey on How Test Flakiness Affects Developers and What Support They Need To Address It", ICST 2022, doi:10.1109/ICST53961.2022.00020. [Source](https://doi.org/10.1109/ICST53961.2022.00020)
- [non-PR] Listfield, "Where do our flaky tests come from?", Google Testing Blog, April 2017. Numbers are from search excerpts of the post. Google has about 4.2M tests, and about 63K have a flaky run in a week. The flaky share was 0.5% of small tests, 1.6% of medium tests, and 14% of large tests. Java WebDriver tests were flaky at 10.45% vs 1.65% for all tests, and made up 20.3% of flaky tests. The post argues that test size (binary size, RAM) predicts flakiness better than the tool does. [Source](https://testing.googleblog.com/2017/04/where-do-our-flaky-tests-come-from.html)
- [non-PR] Micco, "Flaky Tests at Google and How We Mitigate Them", Google Testing Blog, 27 May 2016. About 1.5% of all test runs report a flaky result (from a search excerpt). In the comments, a Google respondent notes "some skew toward UI testing". [Source](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)

### Inferences
- onionskin reads layout, so it will hit the Resource Rendering and Animation Timing causes directly. Reading boxes before web fonts load, images decode, or transitions end gives non-deterministic geometry. A built-in "settled" barrier is needed. This could include waiting for fonts to load, checking that no animations are running, and waiting a couple of animation frames with stable boxes.
- Viewport size should be an explicit, required test parameter. Romano's Layout Difference category comes from default window sizes differing between browsers.
- Disabling animations fixed only 4 of 235 tests, but the cause it targets (animation timing) is common. A test mode that turns off CSS transitions and animations is cheap insurance.
- Since size predicts flakiness, running many relational checks against one rendered page state, in-process, should be less flaky than many separate browser-driven steps.

### Gaps
- Luo et al.'s exact percentages per category could not be read from the PDF (text extraction failed beyond page 1). Widely repeated figures (Async Wait about 45%, Concurrency about 20%, Test Order Dependency about 12%) are not verified here and should be checked before use.
- No study was found that measures the flakiness of computed-style or geometry assertions specifically, as opposed to UI tests in general.

## 4. What does research say about snapshot (golden master, approval) testing and its maintenance?

### Takeaway
Snapshot tests are popular for front-end code. About 38% of Jest projects in one sample use them, and they add coverage and mutant detection. Their main reported drawback is fragility: whole-output comparison fails on small intended changes. Practitioners also report large hard-to-review diffs, lack of context, and the habit of updating snapshots without understanding the failure. The recommended fixes are small, focused snapshots, reviewing snapshot diffs as code, and blocking automatic updates in CI.

### Cited Findings
- [PR] Fujita, Kashiwa, Lin, Iida, "An Empirical Study on the Use of Snapshot Testing", ICSME 2023, pp. 335-340, doi:10.1109/ICSME58846.2023.00041. This preliminary study looks at which projects adopt snapshot testing and how snapshot tests are introduced and evolve. [Source](https://doi.org/10.1109/ICSME58846.2023.00041)
- Fujita et al. 2023, from a search excerpt of the Radboud repository copy: 1,487 Jest projects were studied, and 569 of them (about 38%) use snapshot testing. A later dissertation summarises the paper as finding frequent updates to snapshot files during development. [Source](https://repository.ubn.ru.nl/bitstream/handle/2066/300272/300272.pdf?sequence=1); [Source](https://homepages.dcc.ufmg.br/~mtov/diss/2024-victor.pdf)
- [PR] Cruz, Rocha, Valente, "Snapshot testing in practice: Benefits and drawbacks", Journal of Systems and Software 204, 2023, article 111797 (New Trends and Ideas track), doi:10.1016/j.jss.2023.111797. This is a grey literature review of 50 documents. [Source](https://doi.org/10.1016/j.jss.2023.111797)
- [non-PR] Cruz, "Understanding Snapshot Testing in Practice", MSc dissertation, UFMG, 2024 (contains the JSS material plus an empirical study).
  - Drawbacks named in the grey literature: fragility 28% (14 of 50 documents), lack of context 22%, large snapshots 16%, manual verification 12%, flaky behaviour 6%.
  - Best practices named: use snapshots in code review 26%, treat snapshot files as code 22%, write small snapshots 14%, write detailed test descriptions 6%.
  - Several documents warn that it is easy to update snapshots without fixing the code or understanding the failure, which can hide regressions.
  - The dissertation recommends Jest's `--ci` flag and not updating snapshots automatically.
  - Empirical part: 380 sampled tests from 569 projects. 47.6% test front-end components and 88.6% test normal behaviour. Snapshot formats are HTML (42.9%), JSON (33.2%) and string (23.9%). Median test size is 14 LOC (Q1 8, Q3 26, max 306), and 29 tests (7.6%) are outliers at 53 LOC or more. Two test smells were found, with refactorings for each.
  [Source](https://homepages.dcc.ufmg.br/~mtov/diss/2024-victor.pdf)
- [non-PR, preprint] Fujita, Tomizawa, Kashiwa, Lin, Iida, "On the Effectiveness of Snapshot Testing: An Empirical Study", arXiv:2610.29549, October 2026. This study covers 340 GitHub repositories and surveys 60 practitioners. Snapshot plus traditional tests reach a median statement coverage of 86.7%. The two kinds of test cover different code. Suites with snapshot tests detected 1.3 times more mutants than traditional-only suites. Practitioners named "reviewing large result sets and managing false positives" as significant hurdles. [Source](https://arxiv.org/abs/2610.29549)
- [PR, accepted ICSME 2025 per arXiv] Kaynak, Lami, Moslemi, Koyuncu, "LLMShot: Reducing snapshot testing maintenance via LLMs", arXiv:2507.10062, 2025. Snapshot testing for UI "suffers from substantial maintenance overhead" because frequent UI changes cause failures that need manual triage to separate regressions from intended design changes. They classify snapshot failures with vision-language models; the Gemma3 12B model reaches over 84% recall on root causes. Prompt-based "selective ignore" did not work well. [Source](https://arxiv.org/abs/2507.10062)

### Inferences
- Comparing computed styles between two page versions is a snapshot-style oracle, so onionskin will inherit snapshot testing's known failure modes: large diffs, false positives on intended changes, and approval by habit. The literature's mitigations translate directly:
  - scope each comparison to named elements and named properties instead of the whole page;
  - give each diff entry context (element, property, old value, new value);
  - never update baselines automatically in CI.
- The LLMShot work shows how much triage effort whole-output UI comparisons create. A property-level structured diff should be much easier to triage than an image diff. That is an argument for onionskin's style-diff approach, though no study tests it directly.
- Snapshot and traditional tests cover different code (Fujita 2026). This supports onionskin having both a version-diff mode and an assertion mode.

### Gaps
- No peer-reviewed study was found that measures how often developers approve snapshot updates without review (the "rubber-stamping" claim). The evidence is practitioner reports collected in grey literature reviews.
- The full text of Fujita et al. ICSME 2023 was not retrieved, so its figures on how often snapshot files change could not be checked.
- No academic study on "approval testing" as a separate practice was found in this session.

## 5. How noisy is screenshot comparison, and what does research say about DOM- or style-based comparison instead?

### Takeaway
Screenshots depend on the whole rendering stack. Playwright's documentation says rendering varies with host OS, browser version, settings, hardware, power source and headless mode, and that baselines must be made in the same environment. Pixel tolerances only trade false alarms for missed changes, and a large study of near-duplicate detection found that no threshold separates meaningful from insignificant page differences cleanly. The cross-browser testing literature (WebDiff, CrossCheck, X-PERT, XFix) has moved toward comparing DOM geometry and element relations, using screenshots only as a supplement.

### Cited Findings
- [non-PR] Playwright documentation, "Visual comparisons". It says browser rendering "can vary based on the host OS, version, settings, hardware", power source and headless mode, and that "Screenshots differ between browsers and platforms due to different rendering, fonts and more". It advises generating baselines in the same environment as the tests. The per-pixel colour `threshold` defaults to 0.2, `maxDiffPixels` sets how many pixels may differ, and Playwright uses the pixelmatch library. [Source](https://playwright.dev/docs/test-snapshots)
- [PR] Yandrapally, Stocco, Mesbah, "Near-duplicate detection in web app model inference", ICSE 2020, doi:10.1145/3377811.3380416. They labelled state pairs sampled from 493K page pairs from over 6,000 websites and evaluated 10 detection techniques from information retrieval, web testing and computer vision. "Even with the best thresholds, no algorithm is able to accurately detect all functional near-duplicates within apps, without sacrificing coverage." [Source](https://doi.org/10.1145/3377811.3380416)
- [PR] Roy Choudhary, Versee, Orso, "WEBDIFF: Automated identification of cross-browser issues in web applications", ICSM 2010, doi:10.1109/ICSM.2010.5609723. [Source](https://doi.org/10.1109/ICSM.2010.5609723)
- [PR] Roy Choudhary, Prasad, Orso, "CrossCheck: Combining Crawling and Differencing to Better Detect Cross-browser Incompatibilities in Web Applications", ICST 2012, doi:10.1109/ICST.2012.97. Some cross-browser issues are "tolerable cosmetic differences", while others block functionality. [Source](https://doi.org/10.1109/ICST.2012.97)
- [PR] Roy Choudhary, Prasad, Orso, "X-PERT: Accurate identification of cross-browser issues in web applications", ICSE 2013, doi:10.1109/ICSE.2013.6606616. Earlier detection techniques were "partial and imprecise, and thus prone to generating both false positives and false negatives". X-PERT uses a different differencing technique for each aspect of a page. [Source](https://doi.org/10.1109/ICSE.2013.6606616)
- [PR] Mahajan, Alameer, McMinn, Halfond, "XFix: An Automated Tool for the Repair of Layout Cross Browser Issues", ISSTA 2017 demo, doi:10.1145/3092703.3098223.
  - Layout cross-browser issues are "by far the most prevalent type", seen in over 56% of websites (citing X-PERT's study).
  - XFix measures layout deviation from the position and size of HTML elements and uses it as the fitness function for a search over CSS fixes.
  - On 15 real pages it fixed on average 86% (median 93%) of issues reported by X-PERT and 99% of human-observable issues.
  - Patches averaged 9 CSS properties, and 78% of human raters saw improved consistency.
  [Source](https://eprints.whiterose.ac.uk/116992/7/c47.pdf); [Source](https://doi.org/10.1145/3092703.3098223)
- [PR] Mahajan, Halfond, "Detection and Localization of HTML Presentation Failures Using Computer Vision-Based Techniques" (WebSee), ICST 2015, doi:10.1109/ICST.2015.7102586. It detects presentation failures by image comparison and then maps them back to the responsible HTML elements. [Source](https://doi.org/10.1109/ICST.2015.7102586)
- [PR] Alameer, Mahajan, Halfond, "Detecting and Localizing Internationalization Presentation Failures in Web Applications", ICST 2016, doi:10.1109/ICST.2016.36. It detects layout distortion caused by translated text growing or shrinking. It found problems in 54 web apps with high precision and recall. [Source](https://doi.org/10.1109/ICST.2016.36)
- [PR] Walsh, McMinn, Kapfhammer, "Automatic Detection of Potential Layout Faults Following Changes to Responsive Web Pages" (ReDeCheck), ASE 2015, doi:10.1109/ASE.2015.31. Existing tools "require manual screenshot inspection at specified viewport widths". ReDeCheck compares layouts automatically across viewport widths and found 91% of inserted layout faults on 5 sites. [Source](https://doi.org/10.1109/ASE.2015.31)
- [PR] Walsh, Kapfhammer, McMinn, "Automated layout failure detection for responsive web pages without an explicit oracle", ISSTA 2017, doi:10.1145/3092703.3092712. It checks that a page's layout stays consistent across a range of viewport widths, so no explicit oracle is needed. It found failures in 16 of 26 real production pages, 33 distinct failures in total. [Source](https://doi.org/10.1145/3092703.3092712)

### Inferences
- Comparing computed styles removes several noise sources that Playwright lists for screenshots: anti-aliasing, GPU and OS rasterisation, and sub-pixel colour. But it does not remove font differences. A missing or substituted font changes text metrics, so element boxes move even when every declared style is the same. onionskin should pin fonts in test runs, or treat geometry derived from text as tolerance-checked rather than exact.
- XFix uses element position and size deviation as its objective, and ReDeCheck and the ISSTA 2017 work compare layouts across viewports. Both show that element geometry, not pixels, is a workable and precise basis for layout regression checks. They also localise faults to elements, which pixel diffs do not do without extra work (WebSee).
- The near-duplicate study suggests that any single global threshold, whether pixel-based or DOM-based, will misclassify some changes. Per-property, per-element rules declared by the test author (exact, tolerant, or ignored) are likely to work better than a global threshold.

### Gaps
- X-PERT's internal layout model (often described as an "alignment graph" of parent-child and sibling relations) and ReDeCheck's layout graph could not be confirmed from full text in this session. Both PDFs were unreachable. Check before citing those details.
- No controlled study was found that directly measures false-positive rates of pixel comparison against computed-style comparison on the same changes.
- pixelmatch's anti-aliasing detection and the research it is based on were not checked here.

## 6. What does oracle research say about assertion design, partial oracles and asserting relations instead of values?

### Takeaway
Oracle research describes a trade-off. Detailed oracles find faults earlier and with fewer tests but cost more and break more easily. Oracles that check too much become brittle, and oracles that check too little miss failures. Relational oracles (metamorphic relations, cross-viewport consistency) are an established way to check correctness without exact expected values.

### Cited Findings
- [PR] Memon, Banerjee, Nagarajan, "What test oracle should I use for effective GUI testing?", ASE 2003, doi:10.1109/ASE.2003.1240304. They built 11 oracle types by varying the detail of the expected output and the comparison procedure, then ran 660,000 test runs (four systems, 100 seeded-fault versions, 600 tests). Faults "are detected early in the testing process when using detailed oracle information and complex oracle procedures, although at a higher cost per test case". Expensive oracles find many faults with relatively few test cases. [Source](https://doi.org/10.1109/ASE.2003.1240304)
- [PR] Huo, Clause, "Improving oracle quality by detecting brittle assertions and unused inputs in tests", FSE 2014, doi:10.1145/2635868.2635917. Developers write oracles that "check too little" and miss failures, or "check too much" and become brittle and hard to maintain. A brittle assertion depends on values derived from inputs the test does not control. Across more than 4,000 real tests, OraclePolish found 164 tests with brittle assertions and 1,618 with unused inputs. [Source](https://doi.org/10.1145/2635868.2635917)
- [PR] Barr, Harman, McMinn, Shahbaz, Yoo, "The Oracle Problem in Software Testing: A Survey", IEEE TSE, 2015, doi:10.1109/TSE.2014.2372785. It surveys oracle automation: modelling, specifications, contracts and metamorphic testing. When none of these is enough, the human remains the final oracle. [Source](https://doi.org/10.1109/TSE.2014.2372785)
- [PR] Chen, Kuo, Liu, Poon, Towey, Tse, Zhou, "Metamorphic Testing: A Review of Challenges and Opportunities", ACM Computing Surveys, 2018, doi:10.1145/3143561. Metamorphic relations are "necessary properties of the target function or algorithm in relation to multiple inputs and their expected outputs". [Source](https://doi.org/10.1145/3143561)
- [PR] Walsh, Kapfhammer, McMinn, ISSTA 2017 (cited above), applies the same idea to layout. Consistency across viewport widths replaces an explicit expected layout. [Source](https://doi.org/10.1145/3092703.3092712)
- [non-PR] Snapshot-testing practitioners recommend adding a few targeted non-snapshot assertions next to a snapshot, so that a failure points at a specific property. They also warn that too many targeted assertions cancel the snapshot's brevity (Cruz dissertation, discussion of "Non-Snapshot Assertions"). [Source](https://homepages.dcc.ufmg.br/~mtov/diss/2024-victor.pdf)

### Inferences
- onionskin's two tiers line up with Memon's and Huo and Clause's trade-off. Symbolic relations ("left of", "inside", "aligned with", "same width as") are partial oracles that check less but stay valid. Exact checks (12px, a colour value) are detailed oracles to use only where a requirement fixes that value.
- In Huo and Clause's terms, a pixel offset that comes from font metrics, browser defaults or viewport size is a value derived from an uncontrolled input. Asserting it exactly creates a brittle assertion. This is a direct, citable argument for relations over measured values.
- Spatial relations between elements work like metamorphic relations. They are properties that must hold across many valid renderings (viewports, fonts, content lengths). So one relational test can be run under several conditions, as ReDeCheck does across widths.

### Gaps
- Barr et al.'s internal taxonomy (specified, derived, implicit and human oracles) is not quoted here because only the abstract was read.
- No empirical study was found that measures maintenance cost of relational layout assertions (for example, Galen Framework specs) against exact-value assertions. That comparison would be new evidence.

## 7. What concrete lessons follow for onionskin's design?

### Takeaway
The evidence supports onionskin's core bet: relational assertions on rendered geometry and computed style, plus scoped version-to-version style diffs. But it also says where the risk moves to: element selection, render timing, fonts and viewport, and over-broad diffs that people approve without reading.

### Cited Findings
- Locators dominate breakage: over 73% of record/replay breakages (secondary summary of Hammoudi et al.) and about 70% of Android GUI test modifications (Coppola et al. TR 2019). [Source](https://blog.acolyer.org/2016/05/30/why-do-recordreplay-tests-of-web-applications-break/); [Source](https://doi.org/10.1109/TR.2018.2869227)
- Robust locator generation reduced fragility by 90% vs absolute XPath (Robula+). Contextual locators were proposed because small layout changes break many tests (Yandrapally et al. 2014). [Source](https://doi.org/10.1002/smr.1771); [Source](https://doi.org/10.1145/2610384.2610390)
- Visual scripts broke on graphic and arrangement changes and needed more changes than layout-based scripts, but caught a defect the layout suite missed (Coppola et al. A-TEST 2019). [Source](https://ar5iv.labs.arxiv.org/html/1907.08164)
- Async rendering and animation timing cause most UI flakiness, and window-size differences cause layout flakiness (Romano et al. 2021). [Source](https://ar5iv.labs.arxiv.org/html/2103.02669)
- Screenshot baselines depend on OS, browser, settings, hardware, power source and headless mode (Playwright docs). [Source](https://playwright.dev/docs/test-snapshots)
- No threshold cleanly separates meaningful from insignificant page changes (Yandrapally et al. 2020). [Source](https://doi.org/10.1145/3377811.3380416)
- Snapshot diffs that are large or lack context are hard to review and invite blind updates. Small snapshots, review as code, and no automatic updates in CI are the advice (Cruz et al.). [Source](https://doi.org/10.1016/j.jss.2023.111797); [Source](https://homepages.dcc.ufmg.br/~mtov/diss/2024-victor.pdf)
- Over-checking produces brittle assertions, and under-checking misses faults (Huo and Clause). Detailed oracles find faults earlier at higher cost (Memon et al.). [Source](https://doi.org/10.1145/2635868.2635917); [Source](https://doi.org/10.1109/ASE.2003.1240304)

### Inferences
1. Make selection a first-class, separate layer. Encourage stable test hooks (IDs, data attributes, roles) defined once and reused, instead of structural paths or visible text written inline in each assertion. This follows the locator findings and the programmable-over-recorded result from WCRE 2013.
2. Keep the default assertion vocabulary relational and qualitative. Examples: left-of, above, inside, overlaps or not, aligned edges, same size, visible, within viewport. Treat exact pixel or colour checks as an explicit opt-in. Huo and Clause's brittle-assertion definition is the citable rationale.
3. Build in a settle step before reading layout: fonts loaded, images decoded, animations and transitions finished or disabled, and boxes stable over consecutive frames. Romano's Resource Rendering and Animation Timing categories are the evidence.
4. Make the viewport (and device pixel ratio) part of every test's declared environment, and pin fonts. Relational checks can then be re-run across several widths as a cheap consistency oracle, in the style of ReDeCheck.
5. For version-to-version style diffs, compare per element and per property, report each difference with its context, let tests declare which properties matter and which to ignore, and never auto-accept a new baseline in CI. This follows the snapshot-testing drawbacks and best practices.
6. Allow tolerance only where it means something (for example, geometry derived from text). Avoid one global threshold, because the near-duplicate study shows global thresholds misclassify.
7. Keep an escape hatch for "what the user sees". The Coppola hybrid result and the Spotify case show that purely structural checks can miss visual defects. A small number of targeted exact or visual checks complement the symbolic layer.

### Gaps
- None of the cited studies evaluates a relational layout assertion library directly. The benefit of "X is left of Y" over "X is 12px left of Y" is inferred from the locator, oracle-brittleness and snapshot literature, not measured.
- No study was found on how stable computed-style values are across browsers, OS versions or font setups. This would decide which properties onionskin can compare exactly between two versions of a page.
