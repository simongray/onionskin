# Diff filters, layout-dependent style values and cross-engine comparison (notes for onionskin)

Scope: these notes go deeper than `doc/prior-art.md` and `doc/research-notes/` and do not repeat them. Where an older note already covers a source (GWALI's three heuristics, MFix's intra-segment rule, WebSee's special regions, ReDeCheck's constants, Mazinanian, CILLA, Hague), it is only pointed to. Element matching and pixel-comparison algorithms are out of scope.

Source labels: [PR] peer-reviewed paper, [PRE] preprint, [SPEC] specification, [SRC] browser or tool source code, [DATA] machine-readable data set or live test results, [DOC] tool or vendor documentation. "Read on 2026-11-12" means the live file or API was read that day. Engine source was read from the `main` branches, so it describes current development code, not a specific release.

## 1. Expected-change filters and excluded regions

### Takeaway
Every tool ends up with the same four controls: exclude an element or subtree, lower the strictness for a region, ignore a kind of change, and approve what is left by hand. Element-level exclusion tied to a selector is the unit that survives layout change; fixed rectangles do not. No study was found that measures how often developers approve visual or snapshot changes without looking.

### Cited Findings

Research tools

- [SRC] X-PERT's open reimplementation (Georgia Tech, MIT licence, archived, last push 2015-10-05) filters nodes before it builds the alignment graph. It lists 45 tag names to drop (among them A, B, BR, EM, FORM, LABEL, OPTION, SPAN, STRONG, TBODY, TR, UL; the lookup is passed the node object, not its tag name, so the list may have no effect in this reimplementation), and it drops any box with a negative origin, any box 5 px or less in width or height ("Negligible dimensions"), and container tags (DD, DIV, DT, P, TD, TR) with no visible child. — [AlignmentGraph.java](https://github.com/orso-research-lab/xpert/blob/master/src/edu/gatech/xpert/dom/layout/AlignmentGraph.java)
- [SRC] X-PERT also filters by kind and size of change. A sibling direction change (above, below, left, right) is reported only when the gap between the two boxes differs by more than 5 px between browsers (`diffThreshold = 5`). A lost top, bottom or middle alignment of a child in its parent is reported only when the alignment held with an error below 0.8 of its tolerance in the browser where it held; horizontal justification and sibling edge alignment are reported on any flip. — [AGDiff.java](https://github.com/orso-research-lab/xpert/blob/master/src/edu/gatech/xpert/dom/layout/AGDiff.java)
- [PR] CrossT (Mesbah and Prasad, "Automated cross-browser compatibility testing", ICSE 2011, pp. 561-570) compares DOM states and ignores "case sensitivity, node-level white space, attribute order, node text values, attribute value order, and white-space between the values". It also "takes as input a list of patterns that can be excluded", such as browser-specific attributes and elements (its Table 1 lists `COLGROUP` insertion, `valign="middle"` against `"center"`, and an iframe that one browser adds). Screen-level false positives still ranged "from 12% for Cnn (lowest) to 37% for Ind-v2 (highest)". — [CrossT, author PDF](https://people.ece.ubc.ca/amesbah/resources/papers/icse11.pdf); [DOI](https://doi.org/10.1145/1985793.1985870)
- [PR] WebDiff (Roy Choudhary, Versee, Orso, ICSM 2010, pp. 1-10) reported 121 issues in nine real applications with 21 false positives, and the authors attribute many of the false positives to limits of the implementation. Its handling of variable elements (a second screenshot) is described in the older notes. — [abstract via OpenAlex](https://api.openalex.org/works/doi:10.1109/ICSM.2010.5609723); [DOI](https://doi.org/10.1109/ICSM.2010.5609723)
- [PR, industry track] XBIDetective (Grewal, Castelluccio, Mujahid, Muizelaar, Graham, Odvarko, Bezemer, "XBIDetective: Leveraging Vision Language Models for Identifying Cross-Browser Visual Inconsistencies", accepted at ICSE-SEIP 2026, arXiv 2512.15804) takes five full-page screenshots one second apart in headless Firefox and Chrome and overlays them to separate dynamic from static content. A model then detects advertisements, then dynamic elements (carousels, changing backgrounds, placeholder text, real-time content), and only then compares browsers while ignoring both. Remaining false positives came from undetected dynamic content, cookie banners and other pop-ups that appear in one browser only, scrollbar handling, and headless-mode quirks. — [arXiv 2512.15804](https://arxiv.org/html/2512.15804v1)
- GWALI, IFix, MFix, WebSee and FieryEye filters: see `doc/research-notes/layout_failure_detection_research.md`. FieryEye's abstract adds only that it takes regions to exclude and predicts "the elements and styling properties most likely to cause the observed failure". — [abstract via OpenAlex](https://api.openalex.org/works/doi:10.1109/ICST.2016.35); [DOI](https://doi.org/10.1109/ICST.2016.35)

Visual regression tools

- [DOC] BackstopJS (open source, maintained; last release 2024-09-07 per the older report) has two exclusion modes with different layout effects. `hideSelectors` sets `visibility: hidden`, which keeps "the original layout flow". `removeSelectors` deletes the elements, so they no longer affect layout. The docs advise `hideSelectors` for dynamic blocks of fixed size, such as ad banners, and `removeSelectors` when the size cannot be predicted. `misMatchThreshold` defaults to 0.1 (percent of pixels), `requireSameDimensions` defaults to true, and `backstop approve --filter=<image_filename_regex>` promotes only matching images. For dynamic applications the docs recommend static content stubs of several lengths. — [BackstopJS README](https://github.com/garris/BackstopJS/blob/master/README.md)
- [DOC] Playwright (open source, active). `toHaveScreenshot` takes `mask` ("locators that should be masked when the screenshot is taken", drawn in pink `#FF00FF`; `maskColor` since v1.35) and `stylePath` (since v1.41), a style sheet applied while the screenshot is made, which "allows filtering out dynamic or volatile elements". Animations are disabled and the caret hidden by default; `threshold` defaults to 0.2. — [Playwright PageAssertions](https://playwright.dev/docs/api/class-pageassertions); [Playwright snapshots guide](https://playwright.dev/docs/test-snapshots)
- [DOC] Chromatic (commercial, active). Elements are ignored with `data-chromatic="ignore"`, the class `chromatic-ignore`, or an `ignoreSelectors` list set per story, component or project. The limit is stated: "dimension changes of this element still trigger a change". Selectors cannot cross a shadow root, and inside nested iframes only the whole iframe box can be ignored. The example ignores a video and a date paragraph built from `new Date()`. — [Chromatic: ignoring elements](https://www.chromatic.com/docs/ignoring-elements/)
- [DOC] Percy (BrowserStack, commercial, active). A region gets one of four rules: Ignore ("excludes all visual changes within the defined region"), Layout (flags structure changes instead of pixel changes, with a threshold for small shifts), Intelli Ignore ("automatically detects and ignores dynamic UI elements", with settings for carousels, banners, cookie notices, ads and custom classes) and Standard (pixels, five sensitivity levels). A region is linked to a DOM element by default. A hand-drawn region is "unlinked", stays at fixed coordinates, and the docs warn that it may be wrong at other widths or browsers. — [Percy: define regions](https://www.browserstack.com/docs/percy/set-regions/define-regions)
- [DOC] Applitools Eyes (commercial, active). Match levels: Exact (pixel to pixel, "not recommended for ordinary verification purposes"), Strict (what a person would see), Ignore Colors, Layout (checks that "the relative positions of these elements are consistent" and ignores text, graphics, colour and style) and Dynamic (text must match a pattern such as a date, email address or URL; a changed date is not a difference, an invalid date format is). Any level can be applied to a region. Floating regions let a small region move inside a larger one. The docs call ignore regions a last resort because "most cases can be handled by Layout regions or Ignore Colors regions". Element-based regions need the captured DOM. — [Applitools match levels](https://applitools.com/docs/eyes/concepts/best-practices/match-levels)
- [DOC, from search-result text, pages not opened] Applitools groups steps "by similar differences", and a maintenance action (accept, reject, add a region) on one step is repeated on every step in scope with the same differences. A training transcript says grouping requires the differences to be exactly the same. — [Applitools: grouping steps by similar differences](https://applitools.com/docs/topics/test-manager/pages/page-test-results/tm-tr-auto-maintenance-group-by-sim-diffs.html)

Structural diff tools

- [DOC] sosie (OCaml, new, see older report) runs normalisation as a list of rules before comparison: `Drop_attributes` (class, style, `data-*`, "expected to change"), `Mask_text` by selector (a `<time>` element becomes `[DATE]`), `Mask_text_matching` by regular expression, `Drop_subtree` by selector, `Round_bounds` (for example 0.5 px), `Canonicalize_colors` and `Canonicalize_fonts`. The design rule is that "anything the tool ignores ... is stated in the config file, not buried in the implementation". — [sosie design document](https://github.com/cuihtlauac/sosie/blob/main/sosie-design.md)
- [DOC] StyleProof (npm, active, v9 line) separates review from certification. In review-gate mode a reviewer other than the author ticks "Approve all changes", and a new push that changes styles reopens the check. In certify mode any difference fails and nothing can be approved. Excluded surfaces get the status `excluded-with-reason`. — [StyleProof README](https://github.com/BenSheridanEdwards/StyleProof)

Approval behaviour

- [PRE] Watanabe, Horikawa, Reid, Kashiwa, Iida, "What Are Developers Actually Discussing When Visual Regression Tests Fail?" (arXiv 2608.07020, August 2026, 6 pages) studied 307 pull requests with Chromatic results from 103 repositories against 299 pull requests with image attachments only. Pull requests with visual tests had a 3.8 times longer median resolution time and 10 times more discussion comments, with no significant difference in acceptance rate. Of 189 flagged issues, 39.7% were layout, 27.5% appearance, 14.8% colour, 9.5% text, 6.9% state, 6.3% test and 4.2% image; 35 (18.5%) had non-stylistic causes and 5 were regressions that could not be seen. The summary read did not report how often changes are approved without review. — [arXiv 2608.07020](https://arxiv.org/abs/2608.07020)
- [DOC] Jest's `--ci` flag changes what happens when a snapshot is new: "Instead of the regular behavior of storing a new snapshot automatically, it will fail the test and require Jest to be run with `--updateSnapshot`". — [Jest CLI](https://jestjs.io/docs/cli)
- Snapshot studies already in the older report (Cruz et al. 2023, Cruz 2024, Fujita et al. 2023 and 2026) remain the only academic evidence found; they report fragility and the advice against automatic updates, not a measured rate of blind approval.

### Inferences
- Granularity that works, in order of how well it survives change: (1) element or subtree by selector (all tools); (2) kind of change inside a region (Applitools region levels, Percy rules, GWALI and MFix rules, X-PERT's direction filter); (3) property (sosie's whitelist, CrossT's attribute patterns); (4) text pattern (sosie `Mask_text_matching`, Applitools Dynamic). Fixed coordinates are the weakest unit, and Percy says so itself.
- Hiding and removing are different filters. BackstopJS's split maps onto onionskin as "exclude from the diff but keep in layout" against "report as a region whose size may change and ignore moves that follow from it". Chromatic's limit (an ignored element that changes size still fails) is the honest default for a structural diff: an excluded element's own box and styles are skipped, but if its box changes the report should say that the excluded region resized and group the moved neighbours under it.
- Dynamic regions can be found without configuration by capturing the same version twice (WebDiff, XBIDetective, StyleProof's self-check). In a structural diff this is cheap: elements whose box, text or style differ between two captures of one version are volatile and can be proposed as exclusions.
- Borrow: named, data-driven rules listed in the report (sosie); region-scoped strictness with a "relations only" level (Applitools Layout, Percy Layout), which onionskin already has as its relation diff; text masks by pattern; a filter that ignores direction changes below a gap difference and reports the measured error (X-PERT); repeat of one approval over identical changes (Applitools); approval by someone other than the author and re-opening on new changes (StyleProof); no silent creation of baselines in CI (Jest).
- Avoid: fixed-coordinate regions; a hard-coded tag ignore list like X-PERT's (it names SPAN, A and UL, which often carry layout today); filters applied inside the comparison where the user cannot see them; ignore lists that suppress the fact that the ignored element changed size.

### Gaps
- No peer-reviewed measurement of how often visual or snapshot baselines are approved without inspection was found. Practitioner posts describe it; none count it.
- The FieryEye and WebSee papers could not be opened (the USC host returned a certificate error), so FieryEye is cited from its abstract only.
- reg-suit's options and Percy's grouping of matching diffs were not read. Applitools' grouping is cited from search-result text.
- GWALI, IFix and MFix were not re-read; the older notes are the source.

## 2. Grouping changes by cause

### Takeaway
No research tool or product was found that reports one line per root cause for a computed-style diff. The parts exist: Chromium's DevTools Protocol returns the full cascade input for a node, the CSS data in w3c/webref says which properties inherit and what percentages refer to, and a few tools (StyleProof, Applitools RCA, SeeSS, X-Diag, FieryEye) attribute changes to a narrower cause by other means.

### Cited Findings
- [SRC] Chrome DevTools Protocol, CSS domain (read 2026-11-12). `CSS.getMatchedStylesForNode` returns the inline style, the attribute style, `matchedCSSRules`, pseudo-element matches, `inherited` ("a chain of inherited styles, from the immediate node parent up to the DOM tree root"), inherited pseudo-element styles, keyframes rules, `@position-try` rules with the index of the active fallback, `@property` rules and registrations, `@function` rules, and `parentLayoutNodeId` ("the first parent element that does not have display: contents"; experimental). — [CSS.pdl](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/CSS.pdl)
- [SRC] Other CSS domain commands that bear on cause. `getComputedStyleForNode` returns the computed style plus experimental "extra fields" (currently `isAppearanceBase`). `resolveValues` (experimental) resolves a value in the context of an element, for example `1em` against its font size. `getLonghandProperties` (experimental) expands a shorthand value. `getAnimatedStylesForNode` (experimental) returns styles that come from animations and transitions, including inherited ones. `getPlatformFontsForNode` reports "platform fonts which we used to render child TextNodes". `trackComputedStyleUpdates` and `takeComputedStyleUpdates` (experimental) report nodes whose tracked computed properties changed. `startRuleUsageTracking`, `stopRuleUsageTracking` and `takeCoverageDelta` report which rules were used. — [CSS.pdl](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/CSS.pdl)
- [SPEC] WebDriver BiDi defines the modules browser, browsingContext, emulation, input, log, network, script, session, storage and webExtension. There is no CSS module, so the matched-rule data above has no cross-browser protocol equivalent. — [WebDriver BiDi](https://w3c.github.io/webdriver-bidi/)
- [DATA] @webref/css (W3C, v8.7.8, npm metadata modified 2026-10-22) lists 822 properties. Per property it can carry `inherited`, `percentages` (what a percentage refers to, for example "refer to logical width of containing block" for `margin-top`), `computedValue` (prose), `logicalPropertyGroup` (128 properties), `longhands` and `resetLonghands` (170 shorthands), and `legacyAliasOf` (64 properties). A `usedValue` key also exists; how many properties carry it was not counted. — [webref CSS package README](https://github.com/w3c/webref/blob/main/packages/css/README.md); [css.json on jsDelivr](https://cdn.jsdelivr.net/npm/@webref/css/css.json)
- [SRC] Chromium's property table has a `priority` field for "properties that influence other properties, like line-height influencing lh units", which are computed first. This is the engine's own record that some properties are inputs to others. — [css_properties.json5](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/css/css_properties.json5)
- [DOC] StyleProof's report counts causes separately from differences: "1 distinct change (2 computed-style difference(s) · 3 state-delta difference(s))", then one heading per selector ("`button.btn` · 1 element restyled"). Properties that only follow `color` are printed as indented child rows marked `(currentColor)`, for example `-webkit-text-fill-color` and `-webkit-text-stroke-color` under a colour change. With its change-reach option it also joins changed class tokens in the source with classes gained or lost on paired elements. — [StyleProof README](https://github.com/BenSheridanEdwards/StyleProof)
- [DOC] Applitools Root Cause Analysis stores DOM and CSS with each image and, for a clicked difference, lists tag changes, attribute changes, bounding-box changes (left, top, width, height), CSS property changes ("all properties of a related CSS rule are shown, with changed ones highlighted") and text changes. It shows "significant differences for any DOM elements that could impact the diff"; the page does not define significant and does not describe tracing to an ancestor or to inheritance. — [Applitools RCA](https://applitools.com/docs/eyes/concepts/reviewing-tests/root-cause-analysis)
- [PR] SeeSS (Liang, Kuo, Lee, Chan, Lin, Chen, "SeeSS: seeing what I broke, visualizing change impact of cascading style sheets (CSS)", UIST 2013, pp. 353-356) "automatically tracks CSS change impact across a site"; "the impacted page fragments are sorted by severity and the differences before and after the change are highlighted using animation". It goes from a rule change to affected fragments, the reverse of a diff. — [abstract via OpenAlex](https://api.openalex.org/works/doi:10.1145/2501988.2502006); [DOI](https://doi.org/10.1145/2501988.2502006)
- [PR] X-Diag (Xu, Zhou, Gu, Wu, Chen, Wei, "X-Diag: Automated Debugging Cross-Browser Issues in Web Applications", ICWS 2018, pp. 66-73) "narrows down the root causes of cross-browser issues step-by-step by checking whether such issues are caused by incompatible DOM APIs, CSS properties or Html elements". XBIDetective's related-work section gives it 89% precision and a median run time of 7.95 s; that figure was not checked against the paper. — [abstract via OpenAlex](https://api.openalex.org/works/doi:10.1109/icws.2018.00016); [DOI](https://doi.org/10.1109/icws.2018.00016); [arXiv 2512.15804](https://arxiv.org/html/2512.15804v1)
- [PR] FieryEye (Mahajan, Li, Behnamghader, Halfond, "Using Visual Symptoms for Debugging Presentation Failures in Web Applications", ICST 2016, pp. 191-201) "builds a model that links observable changes in the web site's appearance to faulty elements and styling properties" and predicts the most likely pair. Its predecessor is Mahajan, Li, Halfond, "Root cause analysis for HTML presentation failures using search-based techniques", SBST 2014, pp. 15-18. — [abstract via OpenAlex](https://api.openalex.org/works/doi:10.1109/ICST.2016.35); [SBST 2014 DOI](https://doi.org/10.1145/2593833.2593836)
- [PR] Burg, Ko, Ernst, "Explaining Visual Changes in Web Interfaces", UIST 2015, pp. 259-268, addresses finding the JavaScript, CSS and content that together produce a visual behaviour. Only the first lines of the abstract were read. — [DOI](https://doi.org/10.1145/2807442.2807473)
- [PR] Long, Wu, Zhang, Chen, Wei, "Poster: Repair Cross Browser Layout Issues by Combining Learning and Search-based technique", ICST 2021, pp. 470-473, learns a decision tree from repaired layout issues so that "the recommended solution" can be applied "to fix similar XBIs", an example of treating many reports as one cause. — [DOI](https://doi.org/10.1109/icst49551.2021.00062)
- CSS dependency analyses (CILLA, Mazinanian and Tsantalis, Hague et al., Genevès et al.) work on rules and selectors; see `doc/research-notes/css_refactoring_and_equivalence.md`. The older notes record no feature in them that traces a changed computed value back to a cause.

### Inferences
- A diff can group by cause from capture data alone, with no rule information, in four folds. (1) Inheritance: for an inherited property (webref `inherited`), report the change once at the highest changed element whose parent did not change, and count descendants that carry the same old and new value. (2) Derived values: fold `currentcolor` followers under `color` (StyleProof does this), fold a `line-height` change in px under a `font-size` change when the ratio is unchanged, and treat a logical and a physical property of one group (`logicalPropertyGroup`) as one value. (3) Layout-dependent values (section 3): fold changes in `width`, `height`, insets, margins, the `transform` matrix and grid track sizes under the box change of the same element, not as style changes. (4) Layout propagation: fold moved or resized boxes under the highest ancestor or earliest sibling whose own size changed.
- Where Chromium is the capture engine, `CSS.getMatchedStylesForNode` on both versions adds a fifth fold: group elements whose winning declaration for the changed property comes from the same rule. On Firefox this needs an in-page walk of `document.styleSheets` with `element.matches`, since BiDi has no CSS module; that walk is not confirmed here to give the same answer as the engine for layers, scope and nesting.
- `getPlatformFontsForNode` names the font that was really used. A box change with no style change and a different platform font is a font-fallback cause, which is the common benign case across engines and machines.
- Borrow: StyleProof's "N distinct changes (M differences)" headline and its child rows for derived properties; Applitools RCA's five difference kinds as report categories; webref's `inherited`, `percentages` and `logicalPropertyGroup` as the dependency table; X-Diag's ordered narrowing (content, then style, then layout).
- Avoid: guessing a cause from pixels with a statistical model (FieryEye's route) when the captured facts can decide it; presenting an inferred cause as certain when it rests on a heuristic fold.

### Gaps
- No study was found that measures how much such grouping shortens a diff or whether developers find the grouped line correct.
- The "computed style trace" in Chrome DevTools' Computed pane could not be confirmed from the DevTools CSS reference page that was read; the protocol commands above are what was verified.
- Burg et al. 2015, FieryEye and the SBST 2014 paper were not read in full.

## 3. Resolved versus computed values

### Takeaway
`getComputedStyle` returns used values for a short, fixed list of properties, and several of them depend on layout: sizes, margins, paddings, insets, the `transform` matrix, `transform-origin`, `perspective-origin` and grid track lists. Both engines keep an explicit list of these in source, and the lists agree closely. Chrome and Firefox agree on the main cases in the shared tests and differ in a known set of edge cases. `computedStyleMap()` returns true computed values but is not in Firefox releases as of November 2026.

### Cited Findings

What the specifications say

- [SPEC] CSSOM section 9, Editor's Draft read 2026-11-12. The resolved value is the used value for `background-color`, the eight `border-*-color` longhands (physical and logical), `box-shadow`, `caret-color`, `color`, `outline-color`, and any "resolved value special case property like color defined in another specification". For `line-height` it is `normal` if the computed value is `normal`, otherwise the used value. For `block-size`, `height`, `inline-size`, `width`, all `margin-*` and all `padding-*` longhands (physical and logical) it is the used value "if the property applies to the element or pseudo-element and the resolved value of the display property is not none or contents", otherwise the computed value. For `top`, `right`, `bottom`, `left` and the four `inset-*` longhands it is the used value "if the property applies to a positioned element and the resolved value of the display property is not none or contents, and the property is not over-constrained", otherwise the computed value. Other specifications may define more special cases. For "any other property" it is the computed value. — [CSSOM, resolved values](https://drafts.csswg.org/cssom/#resolved-values)
- [SPEC] `getComputedStyle` returns "all longhand properties that are supported CSS properties, in lexicographical order", plus custom properties whose value is not the guaranteed-invalid value, when the element is connected, in the flat tree and in a rendered browsing context; otherwise the list is empty. A note says "there are UAs that handle shorthands, and all UAs handle shorthands that used to be longhands like overflow" (issue 2529), and the order of custom properties is undefined (issue 4947). A pseudo-element argument that fails to parse, or is `::slotted()` or `::part()`, gives an empty object in the algorithm text, while the change log says a TypeError is thrown. — [CSSOM, getComputedStyle](https://drafts.csswg.org/cssom/#dom-window-getcomputedstyle)
- [SPEC] Special cases defined in other specifications:
  - `grid-template-rows` and `grid-template-columns`: when the element generates a grid container box the resolved value is the used track list, including implicit tracks, in px. The specification's example returns `[a] 50px [b] 320px [b c d e] 40px [e] 40px 0px 0px 0px 0px 50px`. It warns that these values "might not round-trip correctly" and says: "In general, resolved values are the computed values, except for a small list of legacy 2.1 properties". — [CSS Grid 2, section 7.2.6](https://drafts.csswg.org/css-grid-2/#resolved-track-list)
  - `transform`: when the computed value is a transform list, the resolved value is one `matrix()` function (Transforms 1, section 3.2) or one `matrix()` or `matrix3d()` function (Transforms 2, section 2.1). The matrix includes resolved percentages, so it depends on the box size. — [CSS Transforms 1](https://drafts.csswg.org/css-transforms-1/); [CSS Transforms 2](https://drafts.csswg.org/css-transforms-2/)
  - `transform-origin` and `perspective-origin` are each "a resolved value special case property like height", so they return used px values. — [CSS Transforms 1, section 4](https://drafts.csswg.org/css-transforms-1/); [CSS Transforms 2](https://drafts.csswg.org/css-transforms-2/)
  - `translate`: "The resolved value of the translate property is the computed value, and thus getComputedStyle() includes percentage values in its results." — [CSS Transforms 2](https://drafts.csswg.org/css-transforms-2/)
  - `border-*-width`: "The resolved value for the border-width properties is the used value. If the border-style ... is none or hidden, then the used width is 0." Hairline widths are a UA-defined length equal to a whole number of device pixels. — [CSS Backgrounds 3](https://drafts.csswg.org/css-backgrounds-3/#border-width); [CSS Borders 4](https://drafts.csswg.org/css-borders-4/)
  - `min-width` and `min-height: auto`: "For backwards-compatibility, the resolved value of this keyword is zero for boxes of all CSS2 display types ... when aspect-ratio is auto. It also resolves to zero when no box is generated." — [CSS Sizing 3](https://drafts.csswg.org/css-sizing-3/#valdef-width-auto)
  - Insets of absolutely positioned boxes whose self-alignment is `normal`: the resolved value of the weaker inset is the value that matches the margin box after layout. — [CSS Positioned Layout 3](https://drafts.csswg.org/css-position-3/)
  - Colours: "The resolved value of a `<color>` is its used value." Serialised sRGB components may be non-integer numbers, and the precision "is not defined in this specification, but must at least be sufficient to round-trip eight bit values". — [CSS Color 4, section 15](https://drafts.csswg.org/css-color-4/#resolving-color-values)
  - Used values are serialised with every value type that stands for a length converted to a length, which is why percentages come back as px. — [CSS Values 4](https://drafts.csswg.org/css-values-4/)
  - A logical property and its physical partner "must return the same value" from APIs that return computed values. — [CSS Logical 1](https://drafts.csswg.org/css-logical-1/)
  - `font-family: system-ui` must serialise as `system-ui` "on every platform"; `font-width` (old name `font-stretch`) always serialises as a percentage. — [CSS Fonts 4](https://drafts.csswg.org/css-fonts-4/)
  - With CSS `zoom`, `getComputedStyle` lengths "must be unscaled" while `getBoundingClientRect` returns scaled rectangles. — [CSS Viewport](https://drafts.csswg.org/css-viewport/)
- [SPEC] The used value is "the result of taking the computed value and completing any remaining calculations to make it the absolute theoretical value used in the formatting of the document"; `width: auto` "can't be resolved into a length without knowing the layout of the element's ancestors". The actual value is the used value after adjustments such as integer border widths. — [CSS Cascade 5, sections 4.5 and 4.6](https://drafts.csswg.org/css-cascade-5/#used)
- [SPEC] `computedStyleMap()` "represents the actual computed values, not the resolved value concept used by Window.getComputedStyle(). It can thus return different values ... for some properties (such as width)." — [CSS Typed OM 1](https://drafts.css-houdini.org/css-typed-om-1/#dom-element-computedstylemap)

What the engines do

- [SRC] Chromium marks properties whose "resolved value used for getComputedStyle() depends on layout" with `layout_dependent: true`. ### Inferences
- A label set with three values fits the evidence better than two. "Layout-dependent used value": sizes, margins, paddings, insets, grid track lists, `transform`, `transform-origin`, `perspective-origin` (and `translate` in Chromium's table only). "Used value without layout": colours, `line-height` when not `normal`, `border-*-width`, `min-width` and `min-height: auto`. "Computed": everything else. Only the first group changes because an ancestor or sibling changed.
- The label is conditional on the element, not only on the property. Per CSSOM and both engines, the value is a used value only if the element has a box, the property applies, and (for insets) the element is positioned. Gecko narrows further: a margin given as a length and a transform with no percentage do not depend on layout. onionskin can compute the condition from data it already has (`display`, `position`, whether a box was captured) and label each value, not each property.
- Cross-engine style comparison should skip or normalise: colour strings (number precision and modern colour spaces), `font-family` and `font` serialisation, `border-*-width` on native form controls, resolved `width` and `height` of scroll containers, `min-width: auto`, insets of relatively positioned inlines, and anything on elements outside the flat tree or with `display: none`.
- `computedStyleMap()` would separate declared change from layout change cleanly (it keeps `50%` and `auto`), but it cannot be the common path while Firefox lacks it. It can be an optional Chrome and Edge enrichment: where the computed-map value is unchanged and the resolved value changed, the cause is layout.
- Shorthands: enumeration is longhands only, but engines differ on which names are longhands (section 4), so a whitelist has to be written per longhand with an engine-specific mapping.
- Borrow: Chromium's `layout_dependent` list as the seed of the whitelist label, checked against Gecko's switch; the WPT `css/cssom` tests as a regression list for onionskin's own capture across engines. Avoid: treating the CSSOM list as complete (grid, transforms, borders, sizing and position add to it); comparing resolved strings across engines without normalisation.

### Gaps
- Release behaviour was not measured directly; engine source on `main` and WPT stable runs stand in for it. Chromium's flag on `translate` conflicts with the Transforms 2 note that its resolved value is the computed value; which one Chrome follows was not tested.
- No published table lists, per property, where Chrome and Firefox return different resolved strings on real pages. The WPT counts show where tests fail, not how often pages hit those cases.
- The percentage of WPT differences caused by missing features rather than by serialisation was not separated.

## 4. Property sets across engines

### Takeaway
The lists differ because each engine enumerates its own supported longhands. Chromium's table has about 480 enumerable longhands and Gecko's about 410 to 430 entries before preferences, which matches what onionskin sees. A few names are longhands in one engine and shorthands or aliases in the other. w3c/webref is the maintained machine-readable source for standard properties, inheritance and aliases; mdn/data is being retired. Neither says whether a value depends on layout; Chromium's source does.

### Inferences
- A cross-engine style diff should compare the intersection of a whitelist built from webref's standard longhands, after mapping each engine's names to the standard name with an explicit table: aliases from webref's `legacyAliasOf`, plus the handful of engine-specific pairs above. Where one engine has a shorthand and the other a longhand (`vertical-align`, `border-spacing`), compare the longhands of the engine that splits them or skip the property and say so.
- Properties outside the intersection are not differences. They should be reported once per run as "only in Chrome" or "only in Firefox", not per element.
- The whitelist needs a version: both lists change with every browser release (42 Chromium longhands are behind flags today).
- For "depends on layout", the only machine-readable sources are engine code. A small hand-kept table derived from Chromium's `layout_dependent` flag and checked against Gecko's switch (section 3) is enough; it is about 34 longhands.
- Borrow: webref as the data dependency (with its `inherited`, `logicalPropertyGroup`, `legacyAliasOf` keys). Avoid: mdn/data for new work; using either engine's enumeration as the definition of "all properties".

- The exact enumerated counts for release Chrome 157 and Firefox 160 were not measured; source counts explain the gap but do not reproduce 480 and 390 exactly.
- How many webref properties carry the `usedValue` key, and what it contains, was not checked.
- Safari's list was not examined.

## 5. Cross-browser inconsistency detection

### Takeaway
X-PERT is still the reference for comparing engines by relations: parent-child containment and alignment plus sibling order and edge alignment, with a 5 px tolerance and several filters that only its source code states. Later work moved to classifiers over DOM and image features (F-scores of 0.35 to 0.70 for layout) and, in 2026, to vision-language models (79% accuracy). None of the later tools reports a better result for layout than the relation approach, and none publishes a tolerance study.

### Cited Findings
- [SRC] X-PERT alignment graph, from the authors' reimplementation. ### Inferences
- onionskin's relation diff is a superset of X-PERT's graph: Allen relations per axis give X-PERT's four directions and four edge alignments, and inside plus alignment gives its parent-child labels. What X-PERT adds is filtering that onionskin lacks: alignment facts only when the child is clearly smaller than the parent (ratio 0.1 to 0.7), a tolerance that scales with the child's size, a minimum box size, and a direction change that must also be a measurable gap change. These rules exist to keep cross-engine reports short, and they are a ready list of opt-in filters.
- The 5 px edge tolerance was chosen for integer coordinates from 2013 browsers. With fractional boxes, a tolerance near 1 px (section 6) is the engine-noise floor; 5 px is a readability choice, not a noise bound.
- The classifier line of work shows that per-element absolute features do not transfer well: F-scores stay at or below 0.70 for layout, and 0.35 for failures inside components. That supports relations between selected elements over learned features of single elements.
- Borrow: X-PERT's labels as names for cross-engine relation changes; its normalised error (how close the alignment was to its tolerance) as a confidence value on each reported change; Browserbite's point that a different DOM may render the same, so cross-engine comparison should start from boxes and relations, not attributes. Avoid: the fixed tag list; integer rounding before comparison; treating a classifier score as an explanation.

### Gaps
- The X-PERT paper could not be opened (author copy 404, repository 403), so its study of real issues, its evaluation tables and its precision and recall are not confirmed first-hand. The thresholds above come from the reimplementation, which the README says differs from the original tool in output format; it does not say the constants are the paper's.
- WebMate, the 2018 survey, and the full texts of Browserbite and both Watanabe papers were not read; their numbers are from abstracts.
- No detector published between 2019 and 2026 that compares engines at the level of relations was found. This is absence in the searches made, not proof.

## 6. Benign layout differences between Blink and Gecko

### Takeaway
The documented, systematic sources are: different fixed-point layout units, fonts (fallback, metrics, `line-height: normal`), device-pixel snapping of borders, scrollbars, native form controls and user-agent defaults. The browser vendors' shared test suite itself accepts layout differences below 1 px. No study quantifies these differences on real pages.

### Cited Findings
- [SRC] Blink lays out in fixed point with "1/64 of a pixel in an int32_t storage" (`LayoutUnit`); values are truncated, rounded or ceiled to a multiple of that unit. — [layout_unit.h](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/platform/geometry/layout_unit.h)
- [SRC] Gecko uses app units: `AppUnitsPerCSSPixel()` returns 60. — [AppUnits.h](https://github.com/mozilla-firefox/firefox/blob/main/gfx/src/AppUnits.h)
- [SRC] The shared web-platform-tests layout helper passes a measured value when it is within 1 px of the expected one: `assert_tolerance` fails only if `Math.abs(actual - expected) >= 1`. This helper backs the `data-expected-width`, `data-offset-x` and similar attributes used across layout tests. — [check-layout-th.js](https://github.com/web-platform-tests/wpt/blob/master/resources/check-layout-th.js)
- [DOC] WPT reference tests allow declared fuzz because "a test may have subtle differences in rendering compared to the reference due to, e.g., anti-aliasing"; and "the position and thickness of the underline depends on the UA, the font, and/or the platform". — [WPT reftests](https://web-platform-tests.org/writing-tests/reftests.html)
- [SPEC] `line-height: normal`: CSS 2 "tells user agents to set the used value to a 'reasonable' value based on the font of the element" and recommends "between 1.0 to 1.2". CSS Inline 3 says: "Determine the preferred line height automatically based on the metrics of the used font." Neither fixes a formula. — [CSS 2.2, line-height](https://www.w3.org/TR/CSS22/visudet.html#propdef-line-height); [CSS Inline 3](https://drafts.csswg.org/css-inline-3/#line-height-property)
- [SPEC] Fonts: when no listed family has a glyph, the UA runs an installed font fallback procedure and "the result of this procedure can vary across user agents"; `font-size` "must be matched within a UA-dependent margin of tolerance"; `system-ui` "is highly dependent on the platform". — [CSS Fonts 4](https://drafts.csswg.org/css-fonts-4/)
- [SPEC] Borders: a UA "may only be able to render borders with integer pixel widths and may therefore have to approximate the used width"; hairlines are a UA-defined length of a whole number of device pixels. — [CSS Cascade 5, actual values](https://drafts.csswg.org/css-cascade-5/#actual); [CSS Borders 4](https://drafts.csswg.org/css-borders-4/)
- [SPEC] Scrollbars: "Whether classic scrollbars or overlay scrollbars are used, the appearance and size of the scrollbar, and whether scrollbars appear on the start or end edge of the box, is UA defined." Classic scrollbars take space in a gutter as wide as the scrollbar; overlay scrollbars take none. — [CSS Overflow 3, scrollbar-gutter](https://drafts.csswg.org/css-overflow-3/#scrollbar-gutter-property)
- [DATA] Engines disagree on the resolved `width` of a scroll container (WPT `getComputedStyle-width-scroll.tentative.html`: Chrome 0/1, Firefox 1/1, Safari 0/1 on 2026-11-11). — [wpt.fyi, css/cssom](https://wpt.fyi/results/css/cssom?label=master&label=stable)
- [SRC] Form controls: Gecko's computed-style code notes that "Theming can override used padding", so native themed controls have used paddings that no style sheet declares. Chromium's protocol exposes `isAppearanceBase`, whether a node is "rendered with base appearance". Border widths of checkbox and radio inputs resolve differently in Chrome and Safari than in Firefox (WPT `resolved-border-width.html`, 0/2, 2/2, 0/2). — [nsComputedDOMStyle.cpp](https://github.com/mozilla-firefox/firefox/blob/main/layout/style/nsComputedDOMStyle.cpp); [CSS.pdl](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/CSS.pdl); [test source](https://github.com/web-platform-tests/wpt/blob/master/css/cssom/resolved-border-width.html)
- [SPEC] Default styles: the HTML Standard's rendering section gives the rules UAs are "expected to" use "as part of the user-agent level style sheet defaults", and encourages implementers "to adapt the suggestions in this section to their target media". — [HTML Standard, Rendering](https://html.spec.whatwg.org/multipage/rendering.html)
- [DOC] Tools say the same from experience. Playwright: "Screenshots differ between browsers and platforms due to different rendering, fonts and more", and rendering "can vary based on the host OS, version, settings, hardware, power source". BackstopJS: "different environments can render the same webpage in slightly different ways", most of all text, with Docker as the remedy. sosie's design: "Cross-engine differences (Chrome renders `line-height: normal` differently from Safari) are expected and not sosie's concern." StyleProof warns when "stylesheet-free UA defaults differ between base and head". — [Playwright snapshots](https://playwright.dev/docs/test-snapshots); [BackstopJS README](https://github.com/garris/BackstopJS/blob/master/README.md); [sosie design document](https://github.com/cuihtlauac/sosie/blob/main/sosie-design.md); [StyleProof README](https://github.com/BenSheridanEdwards/StyleProof)
- [PR, industry track] XBIDetective lists scrollbar handling, headless-mode rendering and pop-ups that appear in one browser as causes of false reports between Firefox and Chrome. — [arXiv 2512.15804](https://arxiv.org/html/2512.15804v1)

### Inferences
- Unit noise is small and bounded: one Blink unit is 0.0156 px and one Gecko unit 0.0167 px, so a single rounded value differs by at most about 0.017 px between engines. It adds up along a row of siblings or lines of text, which is why the shared tests use a 1 px bound, not a unit-sized one. For onionskin, two tolerances follow: near zero (for example 0.02 px) within one engine and machine, and just under 1 px for cross-engine relation edges, in line with `check-layout-th.js`.
- Text is the main carrier. Any box whose size comes from text (inline content, auto-height blocks, intrinsically sized flex and grid items) inherits font differences; `line-height: normal` multiplies them by line count. A cross-engine comparison is far more stable when the page uses a web font loaded in both engines and an explicit numeric `line-height`. onionskin can check both from captured style and warn when they are missing, since it already captures `font-family` and `line-height`.
- A relation-level comparison should by default tolerate or exclude: text boxes and text-sized boxes beyond a size tolerance that scales with line count; form controls without `appearance: none`; scroll containers (compare the border box, not `width`); hairline borders; elements whose size comes from UA defaults (unstyled headings, lists, fieldsets).
- Borrow: the WPT 1 px rule as the documented cross-engine default; StyleProof's separate warning for UA default drift; Playwright's practice of naming the environment in the baseline. Avoid: one tolerance for both same-engine and cross-engine runs; reading a cross-engine box difference on a text container as a layout bug without checking the used font.

### Gaps
- No engine document or study was found that measures typical text-width or line-height differences between Blink and Gecko for the same font. Bugzilla threads discuss causes (subpixel positioning, metric snapping, hinting) but were seen only as search-result text.
- The HTML Standard's wording on native widget sizes was not extracted; only the general "expected" language was.
- Whether headless Chrome, Edge and Firefox use overlay or classic scrollbars by default on each platform was not checked.

## 7. Interop and web-platform-tests data up to 2026

### Takeaway
Interop and WPT data measure conformance on tests, not how often real pages differ. They show that mainstream layout (flexbox, grid, positioning) is no longer a focus area and that 2026 work is on newer features. No current study says how often real pages render with layout differences between engines.

### Cited Findings
- [DOC] Interop 2026 has 20 focus areas: anchor positioning, advanced `attr()`, container style queries, `contrast-color()`, custom highlights, dialog and popover additions, fetch uploads and ranges, `getAllRecords()` for IndexedDB, JSPI for Wasm, media pseudo-classes, Navigation API, scoped custom element registries, scroll-driven animations, scroll snap, `shape()`, view transitions, web compat, WebRTC, WebTransport and CSS `zoom`. Investigation areas are accessibility testing, JPEG XL, mobile testing and WebVTT. Anchor positioning and `zoom` carry over from 2025. — [web.dev: Interop 2026](https://web.dev/blog/interop-2026); [WebKit: Announcing Interop 2026](https://webkit.org/blog/17818/announcing-interop-2026/)
- [DOC] The web compat focus area is "a small set of tests chosen because failures in some browsers break real websites"; for 2026 it covers ESM module loading, the timing of scroll events relative to animation events, and unprefixed `user-select`. None is a layout item. — [WebKit: Announcing Interop 2026](https://webkit.org/blog/17818/announcing-interop-2026/)
- [DATA] Interop 2026 dashboard data for stable browsers on 2026-11-11 (Chrome 157, Edge 157, Firefox 160, Safari 27.2), the dashboard's "interop" column for the layout-related areas (by the project's usual definition, the share of tests that pass in every browser; the definition was not re-read for these notes): anchor positioning 99.4%, `zoom` 96.9%, container style queries 89.4%, scroll snap 71.6%, scroll-driven animations 67.4%, `shape()` 91.6%, view transitions 78.4%. On 2026-01-01 the same figures were 15.2%, 54.5%, 4.7%, 48.8%, 9.0%, 4.5% and 71.7%. — [results-analysis, interop-2026-stable-v2.csv](https://github.com/web-platform-tests/results-analysis/blob/gh-pages/data/interop-2026/interop-2026-stable-v2.csv); [Interop 2026 dashboard](https://wpt.fyi/interop-2026)
- [DATA] Browser-specific failures (by the metric's name, a score built from tests that fail in one engine only; the formula was not re-read), stable browsers on 2026-11-11: Chrome 921, Firefox 2,358, Safari 4,893. On 2018-06-03, the first row, the scores were 398, 1,361 and 3,770. The test suite grew over that time, so the rows are not a trend. — [results-analysis, stable-browser-specific-failures.csv](https://github.com/web-platform-tests/results-analysis/blob/gh-pages/data/stable-browser-specific-failures.csv)
- [PR, industry track] XBIDetective's authors (several at Mozilla) write that "the normal assumption is that most websites do not contain XBIs". Of 1,052 sites taken from Bugzilla and WebCompat reports, 243 still showed an inconsistency between Firefox and Chrome on manual review and 538 rendered the same. On 1,695 other sites the tool flagged 78 (4.6%), unverified. — [arXiv 2512.15804](https://arxiv.org/html/2512.15804v1)
- [PRE] In pull requests with visual tests, layout was the largest class of flagged issue (39.7% of 189); this is about regressions between versions, not engines. — [arXiv 2608.07020](https://arxiv.org/abs/2608.07020)
- [DOC, from search-result text] A Mozilla retrospective on Interop 2025 is reported to say that for anchor positioning and the Navigation API "a good score was possible while behavior differed from other browsers". The post itself was not opened. — [Mozilla Hacks: Launching Interop 2026](https://hacks.mozilla.org/?p=48246)

### Inferences
- For pages that use established layout features with pinned fonts, differences between Blink and Gecko should mostly be the benign kinds in section 6. Real divergence is more likely where a page uses this year's focus areas (anchor positioning, `zoom`, scroll snap, container style queries, view transitions).
- onionskin can use the Interop focus list as a hint: when a captured page's styles use a property from an area with a low all-browser score, a cross-engine difference there is more likely a real engine difference than a page bug. This is a heuristic, not a measured rule.
- The 4.6% flag rate from XBIDetective and X-PERT's older "over half of sites with issues have layout issues" are not comparable and neither is a prevalence estimate.

### Gaps
- Interop 2025's final overall and per-browser scores were not found in the pages read, and the 2025 CSV was not at the expected path.
- No study after X-PERT (2013) was found that samples real pages and counts layout differences between current engines.
- The Mozilla retrospective was not read directly.

## 8. Scoping a verdict

### Takeaway
The tools that are careful about this make two separate claims: what was compared came out equal, and this is the list of what was compared. They name the dimensions (surfaces or states, widths, engine, property list), give each missing item a status, and fail or warn when a changed rule was never exercised.

### Cited Findings
- [DOC] StyleProof states the boundary in one sentence: "StyleProof certifies only what it captured: a surface that was never captured has no base and no head map, so its change can never appear in a diff and the gate stays green having never looked at it." It keeps the two claims apart: "a visual PASS and a complete capture are two claims, never one green." — [StyleProof README](https://github.com/BenSheridanEdwards/StyleProof)
- [DOC] StyleProof's confidence ledger gives every surface one status: `captured`, `excluded-with-reason`, `inaccessible`, `unknown` (declared but never captured) or `unproven-determinism`, and renders a completeness badge (`complete`, `limited`, `unasserted`, `unknown`). "No coverage percentage is ever invented for surfaces that cannot be enumerated." — [StyleProof README](https://github.com/BenSheridanEdwards/StyleProof)
- [DOC] StyleProof on unexercised rules: "maps prove only the states the spec exercises. A restyle confined to a conditional render branch the fixture never drove ... produces byte-identical honest captures on both sides." With its reach options, "a changed CSS rule no captured state matched fails certify mode and needs approval in review-gate mode". Changed class tokens are labelled `never-rendered`, `unknown` or `unmeasured`; `never-rendered` is used only when the token appears on no captured element and no capture omissions are recorded, and volatile elements or an ignore list leave the answer `unknown`. — [StyleProof README](https://github.com/BenSheridanEdwards/StyleProof)
- [DOC] sosie scopes by property and by engine. "The whitelist is the trust boundary: sosie's 'equivalent' verdict means 'equivalent with respect to these properties.'" "Each engine is compared against itself." "Single-engine testing is a necessary condition; multi-engine testing approaches a sufficient one." A planned `audit-whitelist` command shows "what sosie is blind to" by resetting every property outside the whitelist and comparing screenshots. Unpaired routes are reported as "route only in baseline" or "route only in modified". — [sosie design document](https://github.com/cuihtlauac/sosie/blob/main/sosie-design.md)
- [PR] CrossT words its claim as holding "within the automatically explored state space". — [CrossT, author PDF](https://people.ece.ubc.ca/amesbah/resources/papers/icse11.pdf)
- [DOC] Playwright puts the environment in the baseline's name (`example-test-1-chromium-darwin.png`) because results differ "between browsers and platforms", and tells users to compare "in the same environment where the baseline screenshots were generated". — [Playwright snapshots](https://playwright.dev/docs/test-snapshots)
- [DOC] Applitools recommends the Layout level, not a stricter one, for "cross-environment testing where a single baseline is used for multiple execution environments", which scopes a cross-browser verdict to relative positions. — [Applitools match levels](https://applitools.com/docs/eyes/concepts/best-practices/match-levels)
- [SRC] Chromium can report which rules were used: `CSS.startRuleUsageTracking`, `stopRuleUsageTracking` and `takeCoverageDelta`. — [CSS.pdl](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/CSS.pdl)
- Earlier sources on the same point (Mazinanian et al. on unvisited DOM states, Hague et al. on testing and redundancy, CILLA's unmatched selectors, VizAssert's stated parameter ranges) are in `doc/research-notes/css_refactoring_and_equivalence.md`.

### Inferences
- A verdict line for onionskin can follow the two-claim pattern: "No differences in N elements across these states, widths and engines, for these P properties and these relations", followed by a second line listing what was not covered: states declared but not captured, excluded regions with their reasons, properties outside the whitelist or outside the engine intersection, and rules in the changed style sheets that matched no captured element.
- For cross-engine runs the scope has one more dimension: the kind of fact compared. "Same relations among the selected elements within 1 px" is a different and weaker claim than "same boxes" or "same styles", and the report should print which one was made, as Applitools does by naming the match level.
- Unexercised rules can be found on Chromium with rule-usage tracking and on any engine by testing each selector against captured elements. A rule that changed between versions and matched nothing should make the result "unverified", not "equal". Exclusions weaken this: if a region was excluded, a rule that matches only inside it is unknown, not unused (StyleProof's distinction).
- Borrow: per-item statuses in place of a coverage percentage; `excluded-with-reason`; failing a strict mode when a changed rule was never exercised; naming engine, platform and width in every stored capture. Avoid: a single green result that merges "equal" and "complete"; the word "equivalent" without the property list and matrix next to it.

### Gaps
- No research paper was found that tests how developers read scoped verdicts or whether the extra statuses change behaviour.
- StyleProof's rules are from its README; the referenced `docs/REFERENCE.md` was not read. Both StyleProof and sosie are young projects with no published user reports.
- Percy's and Chromatic's wording on scope was not examined.
