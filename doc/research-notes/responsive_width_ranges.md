## The responsive layout graph: nodes, edges, constraints, and how samples become ranges

### Takeaway
The responsive layout graph (RLG) is a tree-shaped graph with one node per element and one edge per parent-child or sibling pair; each node carries visibility ranges and each edge carries a list of non-overlapping `(min-width, max-width, type, attribute-set)` tuples with inclusive integer bounds. Ranges are built by walking the sampled widths in ascending order, comparing each sample's alignment graph with the previous one, and running a binary search between the two widths whenever a node or an edge's attribute set differs. The method assumes at most one change per fact between two neighbouring samples, and this is its main weakness.

Data model:
- [PR-text] STVR 2020, Definition 1: a visibility constraint for node n is a pair (x1, x2), "an inclusive range of viewport widths for which n is present in the DOM of the web page and has properties making it visible". Definition 2: an alignment constraint for a node pair is a 4-tuple (x1, x2, t, P) with t in {pc, s} (parent-child, sibling) and P a set of alignment attributes that hold between x1 and x2 inclusive. — [STVR 2020, sec. 3.1](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf)
- [PR-text] The RLG is the 4-tuple (E, R, F_VC, F_AC): E is every element shown at one width or more between w_min and w_max; R is the set of node pairs with at least one alignment constraint; F_VC maps a node to its visibility constraints; F_AC maps an edge to its alignment constraints. Both maps must satisfy a non-overlap rule: for two different constraints a and b of the same node or edge, x1a > x2b or x2a < x1b, so "for a particular viewport width, there is at most one alignment constraint for a pair of web page elements". — [STVR 2020, sec. 3.1](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf)
- [PR-text] Edges (ISSTA 2017 wording): element e2 is contained in e1 if its bounding rectangle is inside that of e1; e2 is a child of e1 if no other element lies between them in containment; two elements are siblings if they share a parent. "A directed edge, (e1, e2), is formed in the rRLG from e1 to e2 if there is at least one viewport width where e1 is the parent of e2, or, they are siblings." — [ISSTA 2017, sec. 3.1](https://eprints.whiterose.ac.uk/id/eprint/116989/10/c50-3.pdf)
- [PR-text] Example of one edge with two constraints: (320, 767, pc, {CJ}) and (768, 1400, pc, {LJ}) for a `div` that is centred in `body` below 768 px and left-justified from 768 px. — [ISSTA 2017, Figure 2](https://eprints.whiterose.ac.uk/id/eprint/116989/10/c50-3.pdf)
- [PR-text] The ASE 2015 version had a third constraint type that later papers dropped. A width constraint is a 4-tuple (x1, x2, m, c) "that describes how the width w_e of the element e (measured in pixels) varies in relation to the width w_p of its direct container", using a line fitted to the element's widths between x1 and x2: w_e = (m/100 × w_p) + c. — [ASE 2015, sec. III-A](https://gregorykapfhammer.netlify.app/download/research/papers/key/Walsh2015-paper.pdf)
- [PR-text] ISSTA 2017 calls its model the "refined RLG" (rRLG): it "does not model the width of web page elements through 'width constraints'", because width constraints "do not contribute to detecting the five common types of RLF". — [ISSTA 2017, sec. 3.1](https://eprints.whiterose.ac.uk/id/eprint/116989/10/c50-3.pdf)

Published algorithms (STVR 2020, Algorithms 1 to 4; restated from the paper's prose, since the pseudo-code listings did not survive text extraction):
- [PR-text] Algorithm 1, EXTRACTRESPONSIVELAYOUTGRAPH(page, w_min, w_max, w_step, use_breakpoints): (1) S = GETSAMPLEWIDTHS(...); (2) G = EXTRACTALIGNMENTGRAPHS(page, S), a list of (width, alignment graph) pairs in ascending width; (3) F_VC = EXTRACTVISIBILITYCONSTRAINTS(G); (4) F_AC = EXTRACTALIGNMENTCONSTRAINTS(G); (5) E = domain of F_VC, R = domain of F_AC; return (E, R, F_VC, F_AC). — [STVR 2020, sec. 3.2](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf)
- [PR-text] Algorithm 2, visibility. Take the first graph; for each element open a constraint with x1 = first width and x2 unknown. For each later graph g_c with previous graph g_p: for each element in g_c but not g_p, binary-search between the two widths for the exact width where it appears and open a new constraint there; for each element in g_p but not g_c, binary-search for the width where it disappears and close its open constraint. After the last graph, close every open constraint at the last width. — [STVR 2020, sec. 3.2.3](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf)
- [PR-text] Algorithm 3, alignment. Same walk over edges. For an edge in both graphs: if relationship type and attribute set are equal, do nothing; otherwise binary-search "to establish the point between the two viewport widths of the last two graphs that the change first occurred", close the old constraint there and open a new one with the new attributes. Edges that appear or disappear (because a node does) are searched and opened or closed in the same way. At the end, close all open constraints at the last width. — [STVR 2020, sec. 3.2.4](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf)
- [code] The binary search as implemented: `searchForLayoutChange(key, min, max, searchForNode, flippedKey, appear)`: if `max - min == 1` return `max`; else `mid = (max + min) / 2`, capture the page at `mid` unless it is already cached, test whether the key (or, for siblings, the key with the two nodes swapped) exists in that layout; if `(found && appear) || (!found && !appear)` recurse on `[min, mid]`, else on `[mid, max]`. The result is the first width of the new state; the old constraint's upper bound is set to that width minus 1. Captured widths are kept in a set (`alreadyGathered`) and a map of layouts, so every search reuses earlier captures. — [ResponsiveLayoutGraph.java, lines 861-896 and 1084-1104](https://github.com/redecheck/redecheck/blob/d3f2364960aa7398f7085a502576da70759f5ed0/src/main/java/shef/rlg/ResponsiveLayoutGraph.java)
- [code] Because the attribute set is part of the edge key, a changed attribute set shows up as one key missing and another new. `pairUnmatchedEdges` pairs the two when both nodes match (in either order for siblings), or when the child is the same and only the parent differs. The search then looks for the width where the old key stops existing. — [ResponsiveLayoutGraph.java, lines 338-420](https://github.com/redecheck/redecheck/blob/d3f2364960aa7398f7085a502576da70759f5ed0/src/main/java/shef/rlg/ResponsiveLayoutGraph.java)
- [code] Capture at one width: `wdriver.manage().window().setSize(new Dimension(w, browserHeight))` on the same live page, then the DOM is extracted repeatedly until two consecutive extractions are equal. The page is not reloaded per width. — [Tool.java, capturePageModel](https://github.com/redecheck/redecheck/blob/d3f2364960aa7398f7085a502576da70759f5ed0/src/main/java/shef/main/Tool.java)
- [PR-text] Implementation notes: parent-child and sibling discovery uses an R-tree (JSI RTree library) filled with element bounding boxes; the regression mode ran on Selenium 2.53.1 with PhantomJS 2.1.1. — [STVR 2020, sec. 3.4](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf)
- [PR-text] Algorithm 4, DIFFRLGS(RLG_curr, RLG_mod): report nodes not in both (matched by identical absolute XPath); for matched nodes report visibility constraints not in both; report edges not in both; for alignment constraints not in both, call COMPAREALIGNMENTCONSTRAINT, which classes a partial match as a bounds difference (same attributes, different range; reported widths are the symmetric difference of the two ranges), an attributes difference (same range, different type or attributes) or a compound difference (the whole range of the unmatched constraint is reported). Worked example: before, (768, w_max, s, {L}); after, (768, 811, s, {A}) and (812, w_max, s, {L}); the diff reports a bounds difference on {L} (768 against 812) and an unmatched constraint {A} over 768 to 811. — [STVR 2020, sec. 3.3](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf)

### Inferences
- The published algorithm assumes each fact changes at most once between two neighbouring samples. Two cases break it. (a) A-B-A: the relation differs only strictly between two samples; both samples agree, so no search starts and the B range is never seen. (b) A-B-C: the search looks for the width where the old key stops existing, then labels everything from there to the upper sample with the upper sample's attributes, so B's range is merged into C's. The STVR paper admits the first case in general terms ("could potentially fail to sample certain layout behaviours that occur between two consecutive sample widths"). onionskin can close most of this gap cheaply: after a search finishes, compare the fact at the found boundary with the fact at the upper sample; if they differ, search again on the remaining interval.
- The binary search is per fact, but every capture is a whole page, so captures are shared. The number of extra captures is bounded by (number of distinct change widths) × log2(step), not by the number of facts. onionskin should cache by width in the same way and derive all facts from each capture.
- The edge key that includes the attribute set is an implementation shortcut. A cleaner model for onionskin is a map from element pair to a sorted vector of `[from to fact-set]` runs (a run-length encoding over width). It gives the same non-overlap rule for free and makes diffing two captures a merge of two sorted run lists.
- The RLG stores the whole attribute set per range. With onionskin's finer per-axis Allen relations, storing the set as one unit would split ranges whenever any single fact flips. Storing one run list per fact family (x-axis relation, y-axis relation, containment, each alignment) keeps ranges long and reports readable.
- The ASE 2015 width constraint is the only published attempt to give a quantity a range: a linear function of the parent's width that holds from x1 to x2. It fits fluid layouts (percent widths, `vw`, `clamp()`) well and is worth reviving for onionskin's quantitative tier, as "width of A = m × width of B + c from 320 to 767".
- Borrow from ReDeCheck: inclusive integer ranges with a non-overlap rule; ascending walk with a search at each difference; a width-keyed capture cache; diff classes (bounds, attributes, compound) with the symmetric difference of ranges as "the widths to look at". Avoid: the single-change assumption; attribute sets inside keys; resizing a live window without recording whether the page was reloaded (see the question on breakpoints for why this matters).

## How sample widths are chosen, and what each strategy costs

### Takeaway
ReDeCheck's default is a 60 px grid from 320 to 1400 px, plus the widths on both sides of every `min-width` and `max-width` breakpoint parsed from the linked style sheets, plus binary search wherever two neighbouring samples differ. The journal study found that this samples under a tenth of the widths and under a third of the time of exhaustive sampling with almost no loss in detection, that step size barely matters once binary search is on, and that 60 or 80 px is a good default. Later tools from the same line gave up sampling and capture every width.

### Inferences
- With binary search, the grid step decides only two things: how many captures are spent, and how likely it is that a short A-B-A range is missed. The measured optimum of 60 to 80 px reflects 2015-era cost (one browser, PhantomJS or Firefox 46, resize in place). onionskin captures in parallel, so the balance moves. Exhaustive capture took ReDeCheck about 0.1 s per width; if onionskin's per-width cost is similar and it has 8 workers, all 1081 widths from 320 to 1400 take seconds of browser time, not minutes.
- Binary search is sequential: each step waits for the last. A parallel version is a k-ary search: split the interval into k + 1 parts with k captures at once. With 7 parallel captures a 60 px gap is resolved in two rounds (60 to about 8, then 8 to 1) instead of six.
- A sensible staged plan: (1) capture a coarse grid plus both sides of every extracted breakpoint in parallel; (2) for each neighbouring pair of samples whose facts differ, refine by k-ary search, sharing captures across facts; (3) re-check each found boundary against the upper sample to catch A-B-C; (4) offer an exhaustive mode for release checks, as the authors suggest.
- The two fixed-list studies are the best published numbers on what onionskin's users lose today by capturing a short list of widths: 19 to 34% of real failures (ISSTA 2017) and 9 of 48 seeded regressions, mostly those visible at 10 widths or fewer (STVR 2020).
- Borrow: grid plus both sides of breakpoints plus search; a width-keyed cache; an exhaustive mode. Avoid: treating 60 px as a law (it is a cost trade-off from one study on 15 pages); assuming breakpoints carry most change points (the paper found many did not).

### Gaps
- The papers report no per-capture time, so the 0.1 s figure is my division of 108 s by 1001 widths and includes fixed start-up cost.
- No study measures sampling strategies on pages built with container queries, grid auto-placement or fluid type; all subjects date from 2015 to 2017.
- I could not confirm from the Layout Dr paper itself that it samples every width.

## Finding media query breakpoints reliably from a live page

### Takeaway
ReDeCheck's own breakpoint extraction is fragile: it downloads only `<link rel="stylesheet">` files, parses them outside the browser, and accepts only `min-width` and `max-width` in px or em (em × 16). A CDP-based tool can do much better with `CSS.getMediaQueries`, which returns every media query the engine holds, where it came from, whether it is active, and each length already computed to pixels. Two things remain outside any style-sheet scan: range-syntax queries need their comparison operator read from the query text, and breakpoints applied by JavaScript are not in the style sheets at all.

### Cited Findings

What ReDeCheck does:
- [code] Style sheets are found by an injected script that returns the `href` of every `<link>` with `rel="stylesheet"`. Inline `<style>` blocks, `@import`ed sheets and sheets added by script are not looked at. — [getCssFiles.js](https://github.com/redecheck/redecheck/blob/d3f2364960aa7398f7085a502576da70759f5ed0/resources/getCssFiles.js)
- [code] Each file is fetched by URL from Java and parsed with jStyleParser; `@media` rules with a numeric query are kept. Breakpoints are read with the regular expression `\(([A-Za-z]*-width:[ ]+)([0-9]*[.]+[0-9]*)(em|px)\)` applied to each media expression as the parser prints it. Only `px` and `em` match; em values are multiplied by 16; a `min` expression adds the value and the value − 1, a `max` expression adds the value and the value + 1. An expression that does not match throws inside a `try` and is skipped without a message. Fetch and parse errors are also swallowed. — [RLGExtractor.java, getBreakpoints and getMediaQueries](https://github.com/redecheck/redecheck/blob/d3f2364960aa7398f7085a502576da70759f5ed0/src/main/java/shef/main/RLGExtractor.java)

### Inferences
- `CSS.getMediaQueries` solves most of ReDeCheck's extraction problems at once: it covers inline, linked and imported sheets, it does not depend on the page's origin rules because it is not page script (unconfirmed from a primary source, but DevTools shows cross-origin rules the same way), and `computedLength` removes the em × 16 guess. onionskin should take width breakpoints as every expression whose `feature` ends in `width`, using `computedLength`.
- `MediaQueryExpression` has one value and a feature name but no comparison operator. For `min-width` and `max-width` the prefix gives the direction. For range syntax such as `(width >= 600px)` or `(400px <= width < 700px)` the direction and strictness must be read from `CSSMedia.text`. A simple and safe rule avoids parsing: for each distinct computed value v, sample the nearest integers below, at and above v. That covers inclusive, exclusive and fractional thresholds (767.98 leads to 767 and 768).
- Media query em and rem follow the browser default font size. If onionskin ever varies the default font size as a capture parameter (as the earlier report suggests), every em breakpoint moves, so breakpoints must be extracted per capture configuration, not once per page.
- The `width` feature includes a classic scrollbar, while layout uses the width without it. Under `Emulation.setDeviceMetricsOverride` in headless Chrome scrollbars are normally overlaid, so the two agree; Firefox and headed runs may differ. Record the measured `innerWidth` and `documentElement.clientWidth` in each capture so that a range is stated in a defined unit.
- Integer widths never land in a fractional gap, so onionskin will not see the "neither rule applies" state that real devices with fractional widths can hit. A cheap extra check: for each pair of thresholds v and v′ with 0 < v′ − v ≤ 1, warn about the gap without rendering.
- JavaScript breakpoints (`matchMedia`, `innerWidth` comparisons, `ResizeObserver`) and markup breakpoints (`<source media>`, `sizes`) are not in the CSS domain's output. Two consequences: (1) the grid and the search are still needed; (2) loading the page fresh at each width (what onionskin does) and resizing a live page (what ReDeCheck does) can give different layouts, since some scripts read the width only at load. The capture should record which was done, and a range fact should be labelled "at load".
- Firefox has no CDP. The practical options are an in-page CSSOM walk (which hits the cross-origin limit) or reusing the breakpoints found in Chrome for the same URL, which is sound unless the site serves different CSS per browser.
- Borrow: Polypane's "edges" and ReDeCheck's both-sides rule; DevTools' source link (keep `sourceURL` and `range` so a report can say which rule a change point belongs to). Avoid: text-level parsing of CSS files outside the browser; silent skipping of anything not understood (report unparsed queries).

### Gaps
- I could not confirm how Chrome fills `MediaQueryExpression` for range-syntax queries (one expression per bound, or none). This needs a five-minute experiment against a test page.
- I did not confirm from a primary source that `CSS.getMediaQueries` includes cross-origin sheets, constructed sheets and sheets inside shadow roots.
- WebDriver BiDi, which onionskin uses for Firefox, has no CSS inspection module as far as I know; unconfirmed.
- `CSSMediaRule.matches` is not on the MDN page I read; I could not confirm its status. `window.matchMedia` (not re-read this session) remains the way to test a query string from script.

## Container queries, fluid typography, viewport units and intrinsic layout against the breakpoint assumption

### Takeaway
The assumption that layout changes only at media query breakpoints was already false in the original studies, and CSS has since moved further from it: container queries switch on a container's size, `clamp()` and viewport units make sizes change at every width, and wrapping flex rows and auto-fit grids change column counts at widths that appear in no style sheet. I found no peer-reviewed work and no dedicated tool for testing container queries or for locating layout change points other than ReDeCheck's sample-and-search; the 2025 and 2026 follow-up papers do not mention container queries, grid, `clamp()` or viewport units at all.

### Cited Findings

What the original work already observed:
- [PR-text] "responsive faults are often found at hard-to-predict viewport widths between the breakpoints standardly employed in RWD". — [ASE 2015, sec. IV-D](https://gregorykapfhammer.netlify.app/download/research/papers/key/Walsh2015-paper.pdf)
- [PR-text] Adding breakpoint widths saved few binary searches because "many layout changes observed during the extraction of the RLG could be at viewport widths not programmed as breakpoints in the site's CSS files". — [STVR 2020, RQ3](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf)
- [PR-text] The wrapping failure type is by definition an intrinsic change: a row wraps when its container "is not wide enough to contain its children", at a width set by content, not by a query. — [ISSTA 2017, sec. 3.2](https://eprints.whiterose.ac.uk/id/eprint/116989/10/c50-3.pdf)

Container queries:
- [docs] "The `@container` CSS at-rule is a conditional group rule that applies styles to a containment context." MDN marks it "Baseline Widely available ... across browsers since February 2023". The page also lists `style()`, `scroll-state()` and `anchored()` queries. — [MDN @container](https://developer.mozilla.org/en-US/docs/Web/CSS/@container)
- [docs] Container queries "are an alternative to media queries, which apply styles to elements based on viewport size or other device characteristics". Units: `cqw`, `cqh`, `cqi`, `cqb`, `cqmin`, `cqmax`, each 1% of a query container's dimension. — [MDN container queries guide](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_containment/Container_queries)
- [spec] Container queries are defined in CSS Containment Module Level 3 (W3C Working Draft, 18 August 2022, as fetched). For container units, "If no eligible query container is available, then use the small viewport size for that axis." — [CSS Containment 3](https://www.w3.org/TR/css-contain-3/)
- [spec] CSS Conditional Rules Module Level 5 (W3C Working Draft, 30 October 2025, as fetched) also specifies `@container`, including scroll-state queries. A relative length in a container query is resolved against the container: "The 40em value used in the query condition is relative to the computed value of font-size on the relevant query container." — [CSS Conditional 5](https://www.w3.org/TR/css-conditional-5/)
- [spec] CDP support, all experimental: type `CSSContainerQuery` with `conditionText`, `name`, `physicalAxes`, `logicalAxes`, `queriesScrollState`, `queriesAnchored` (`text` is deprecated); `CSSRule.containerQueries`; `DOM.getContainerForNode` ("Returns the query container of the given node based on container query conditions") and `DOM.getQueryingDescendantsForContainer`. The CSS domain has `getMediaQueries` but no matching command that lists all container queries (checked against the command list in the file). — [CSS.pdl](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/CSS.pdl); [DOM.pdl](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/DOM.pdl)

Fluid sizes and viewport units:
- [docs] "`clamp(MIN, VAL, MAX)` is resolved as `max(MIN, min(VAL, MAX))`." Example: `font-size: clamp(1rem, 2.5vw, 2rem)`, which gives "a font-size that grows with the size of the viewport, but doesn't go below a minimum font-size or above a maximum font-size". Baseline: widely available. — [MDN clamp()](https://developer.mozilla.org/en-US/docs/Web/CSS/clamp)
- [spec] Viewport units come in large (`lv*`, and the plain `v*`), small (`sv*`) and dynamic (`dv*`) forms. The small viewport assumes retractable browser interface is shown, the large assumes it is hidden. Dynamic units "are not stable even while the viewport itself is unchanged", and "The UA is not required to animate the dynamic viewport-percentage units." — [CSS Values 4 (Working Draft, 12 March 2024, as fetched)](https://www.w3.org/TR/css-values-4/#viewport-relative-lengths)

Intrinsic layout:
- [docs] Grid `auto-fill` "Resolves to the largest number of repetitions that does not cause overflow" of a size-constrained box; `auto-fit` "Behaves as `auto-fill`, except that after placing grid items, any empty repeated tracks are collapsed." — [MDN repeat()](https://developer.mozilla.org/en-US/docs/Web/CSS/repeat)

Research and tooling since:
- [preprint] LocaliCSS (ENASE 2025) and ReDeFix (ICSME 2025) work only with media-query ranges. A model summary of both full texts found no mention of container queries, grid, `clamp()` or viewport units; LocaliCSS's property list does include flexbox conditions such as a missing `flex-wrap: wrap`. ReDeFix wraps every repair "within a media rule spanning the failure range". — [Zerin et al. 2025a, arXiv 2605.25476](https://arxiv.org/abs/2605.25476); [Zerin et al. 2025b, arXiv 2511.00678](https://arxiv.org/abs/2511.00678)
- [search] A 2026 preprint on pages generated by multimodal models reports that the leading causes of cross-environment failures are a missing viewport meta tag (46%) and missing flexible wrapping (29.5%). — [Guo et al. 2026, arXiv 2608.12518](https://arxiv.org/abs/2608.12518)
- [blog] Practitioner advice on container queries: test the container, not the window ("does it respond correctly to the width of its actual container"); resize the parent container directly in the test; take one visual snapshot per distinct layout mode to limit noise. I found only blog posts, no tool with container-aware width selection. — [frontendtester.com](https://frontendtester.com/how-to-test-css-container-queries-without-breaking-visual-regressions/)
- [PR] VizAssert (PLDI 2018) is the one approach that covers all widths in a range without sampling, by solving for a counterexample, but its CSS model predates container queries and does not cover modern layout modes (see the earlier report). — [Panchekha et al. 2018](https://doi.org/10.1145/3192366.3192407)

### Inferences
- Three kinds of change point now exist, and only the first is listed anywhere. (1) Declared: media query thresholds. (2) Derived: container query thresholds, each of which maps to zero, one or several viewport widths through the container's own width. (3) Emergent: wraps, auto-fit column counts, `clamp()` knees, text reflow. The sample-and-search method finds all three, which is the main argument for keeping it as the base and treating extracted breakpoints only as extra sample points and as labels.
- Worked examples (my arithmetic). `font-size: clamp(1rem, 2.5vw, 2rem)` with a 16 px root is 16 px up to 640 px wide, grows linearly to 32 px at 1280 px, then stays; the knees at 640 and 1280 are in no media query. `grid-template-columns: repeat(auto-fit, minmax(240px, 1fr))` with a 16 px gap in a container that is the viewport minus 48 px goes from one to two columns at 544 px, to three at 800 px and to four at 1056 px.
- A container's width is not always a rising function of viewport width. When a sidebar appears at a media breakpoint, the main column gets narrower as the viewport gets wider. A query such as `@container (min-width: 700px)` on that column can then be true, false and true again as the viewport grows. So even a correct page can have a short range around a breakpoint in which a component drops back to its narrow layout; a range model must allow several ranges per fact and must not assume one switch per query.
- Symbolic relations are what make ranges useful under fluid layout. With `clamp()` and `vw`, exact sizes and positions change at every width, so an exact-value fact has a range of one pixel, while "left of", "above" and "inside" hold over long ranges. onionskin's graded facts fit this: report ranges for coarse relations, and describe quantities over a range as a bound (`width between 280 and 420`) or as a line in the viewport or container width (the ASE 2015 width constraint).
- Container-aware sampling is possible with CDP. For each captured element, `CSS.getMatchedStylesForNode` gives the `containerQueries` on its rules and `DOM.getContainerForNode` gives the container; the capture already has the container's box at each sampled width. Where the container's inline size crosses a query threshold between two samples, add samples on both sides of the crossing (interpolate, then search). This is ReDeCheck's both-sides rule applied to derived thresholds. Note that only queries on rules that match some element at some sampled width are seen this way.
- A second range variable follows from the blog advice: for component work, vary the container's width directly (onionskin's capture already accepts extra CSS, so a named container can be forced to a width) and state facts over container width. "The card's image is left of its text when the card is at least 400 px wide" is then a stable expectation wherever the card is used.
- Dynamic viewport units and scroll-state queries depend on state that a headless capture does not vary (browser interface shown or hidden, scroll position). A width-range fact should carry the caveat that it holds for the captured scroll position and a static viewport.
- Borrow: nothing new from the 2025 and 2026 papers on this point; they repeat the media-query-only model. Avoid: equating "breakpoint" with "media query"; reporting a change point as unexplained when a container query or an intrinsic wrap explains it (label change points as declared, derived or emergent).

### Gaps
- No peer-reviewed study of responsive testing on pages that use container queries, grid auto-placement or fluid type was found. All published subject sets date from 2015 to 2021.
- I did not verify how reliably `DOM.getContainerForNode` and `CSSRule.containerQueries` behave in current Chrome; both are experimental.
- The CSS Containment 3 and CSS Conditional 5 status lines are as reported by the fetch tool's summary; the two drafts overlap and I did not establish which one is normative for container queries today.
- The clamp() definition in CSS Values 4 itself was not read (the page was truncated); MDN is the cited source.

## Viewport height, device pixel ratio and orientation as ranges

### Takeaway
Every tool in the ReDeCheck line varies width only and fixes the height (1000 px in VERVE, Layout Dr and LocaliCSS). The only work found that treats height as a range is VizAssert, which proves assertions for all widths from 1024 to 1920 px, heights from 800 to 1080 px and default font sizes from 16 to 32 px. Nothing treats device pixel ratio as a range. Android's guidance is the clearest practical model: width and height are classified separately into size classes, and width is said to matter more.

### Cited Findings
- [code] ReDeCheck opens the page in a pop-up of `width=320,height=1024`, then sets the window to `(w, browserHeight)` for each width, with `browserHeight = 600`. Only the width varies. — [RLGExtractor.java](https://github.com/redecheck/redecheck/blob/d3f2364960aa7398f7085a502576da70759f5ed0/src/main/java/shef/main/RLGExtractor.java); [Tool.java](https://github.com/redecheck/redecheck/blob/d3f2364960aa7398f7085a502576da70759f5ed0/src/main/java/shef/main/Tool.java)
- [PR-text] VERVE renders pages "without scrollbars and at a fixed viewport height of 1000 pixels". — [Althomali et al. 2021, sec. 4.3](https://eprints.whiterose.ac.uk/165542/8/stvr.1756.pdf)
- [PR-text] Layout Dr runs headless Chromium "with a fixed viewport height of 1000 pixels". — [Althomali et al. 2022, sec. V](https://eprints.whiterose.ac.uk/id/eprint/230094/1/althomali2022.pdf)
- [PR-text] The STVR 2020 paper mentions orientation only in related work on mobile apps; it has no treatment of height, pixel ratio or orientation for web pages (checked by text search). — [STVR 2020, sec. 5.2](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf)
- [PR-text] VizAssert "verified each assertion for all possible screen widths 1024–1920 pixels, screen heights 800–1080 pixels, and default font sizes 16–32 pixels". A failure comes with concrete parameters, for example a "1856 × 800" window, or a "1872 × 800 browser with 16px text". — [Panchekha et al., PLDI 2018, sec. 5.2](https://doi.org/10.1145/3192366.3192407)
- [spec] Media features beyond width: `height`; `aspect-ratio`, "the ratio of the value of the width media feature to the value of the height media feature"; `orientation`, which is portrait when height is greater than or equal to width and landscape otherwise; `resolution`, "the density of the pixels". — [Media Queries 4](https://www.w3.org/TR/mediaqueries-4/)
- [docs] Android window size classes: width compact under 600 dp, medium 600 to 840, expanded 840 to 1200, large 1200 to 1600, extra-large from 1600; height compact under 480 dp, medium 480 to 900, expanded from 900. "Available width and height are classified separately", and "Available width is usually more important than available height due to the ubiquity of vertical scrolling". The classes "are determined by the window size available to your application regardless of the type of device". Testing advice: "test the layout behavior across all window sizes, especially at the compact, medium, and expanded breakpoint widths." — [Android: use window size classes](https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes)
- [PR] dVermin (Su, Chen, Wang, Liu, Wang, Li, Wang; "The Metamorphosis: Automatic Detection of Scaling Issues for Mobile Apps", ASE 2022, DOI 10.1145/3551349.3556935) varies the display scale: it compares each view at the default scale with a larger one. It reports 97% precision and recall for pages and found 21 new issues in F-Droid apps, 20 confirmed or fixed. It compares two settings, not a range. — [arXiv 2212.04388](https://arxiv.org/abs/2212.04388)
- [PR-text] ReFLAIR (He, He, Huq, Malek; Proc. ACM Softw. Eng. 3, FSE, article FSE129, July 2026) compares two fixed viewports, 1280 × 1024 and 320 × 1024 CSS pixels. — [He et al. 2026](https://doi.org/10.1145/3808136)
- [docs] Bootstrap notes that fractional viewport widths "can occur under certain conditions on high-dpi devices". — [Bootstrap breakpoints](https://getbootstrap.com/docs/5.3/layout/breakpoints/)
- [docs] Tools that take a height or pixel ratio take single values: BackstopJS viewports are `label`, `width`, `height`; Percy has `min-height` (default 1024) and a `device-pixel-ratio` for asset discovery (default 1); Playwright has `viewport: { width, height }` and `deviceScaleFactor`; Chrome DevTools has width, height and DPR fields. — [BackstopJS](https://github.com/garris/BackstopJS); [Percy config](https://www.browserstack.com/docs/percy/references/config-options); [Playwright emulation](https://playwright.dev/docs/emulation); [Chrome DevTools device mode](https://developer.chrome.com/docs/devtools/device-mode)

### Inferences
- A width range is only meaningful at a stated height. `orientation` flips where width equals height, so a capture height of 800 px creates a hidden breakpoint at 800 and 801 px wide for any rule guarded by `(orientation: landscape)`. An `aspect-ratio` query flips at ratio × height. onionskin should store the height (and scale, default font size and engine) with every range fact, and when the style sheets contain `orientation`, `aspect-ratio` or `height` queries it should add the implied widths to the sample set.
- Height needs sampling only when something depends on it: height or aspect media queries, `vh`/`dvh`/`svh` units, sticky or fixed positioning, or container queries on block size. `CSS.getMediaQueries` reports the `feature` of each expression, so the presence of height-dependent queries can be detected and height breakpoints extracted the same way as width breakpoints. Otherwise one height is enough, as Android's guidance implies.
- If both dimensions are varied, treat them as two independent partitions and capture their product only at the partition boundaries (both sides of each height breakpoint × the width samples). No published tool does this; VizAssert gets the same effect by solving.
- Device pixel ratio changes rounding, hairline borders and image choice, not block layout. A range over it has little value; a short list (1, 2, 3) as a declared capture parameter is enough. Fractional widths are the part worth a note, and they can be emulated by setting a fractional width only if the browser accepts one (untested).
- Borrow: VizAssert's idea that a failure report names one concrete parameter set; Android's separate width and height classes as a naming scheme. Avoid: leaving height implicit, as every ReDeCheck-line tool does.

### Gaps
- No work was found that treats device pixel ratio or zoom level as a range for web pages.
- Whether `Emulation.setDeviceMetricsOverride` and BiDi `browsingContext.setViewport` accept fractional widths was not tested.
- SwiftUI and Xcode preview variants (orientation and Dynamic Type) were not checked against Apple's documentation in this session.

## How tools report range results, and what was found readable

### Takeaway
ReDeCheck reports one line per failure with the element XPaths and the width range, plus one annotated screenshot taken at the middle of the range. The authors' own measure of reading cost is the number of distinct ranges (137 ranges for 33 real failures, 4.2 checks per failure), and their own data show the format's main fault: one real problem produced 147 report lines. No user study of report formats exists. Commercial visual tools avoid the question by reporting per listed width.

### Inferences
- The unit of a readable report is the range, then the change point, not the element pair. ReDeCheck's 147-line case shows what happens otherwise. onionskin should group facts that share a range, or that change at the same width, into one entry: "at 768 px, 14 relations change (matches `@media (min-width: 768px)` in main.css:212)", with the pairs listed under it.
- Per pair, a run-length timeline reads well and is what the README's THIS/PREV/NEXT block approximates: `logo / search: left-of 320-767 | above 768-1400`. For the author's example sentence, the timeline is the data and the sentence is one run of it.
- Each range entry should name the widths worth opening: the narrowest width of the range (VERVE's default, with its stated reason), and the two bordering widths (Layout Dr, VERVE small-range). The midpoint, ReDeCheck's choice, has no stated reason and VERVE moved away from it.
- State what was sampled. A range found by search is exact to the pixel only at its ends; in between it rests on the samples. A line such as "holds at all 23 sampled widths in 320-767; boundary located between 767 and 768" keeps the claim honest and fits the earlier report's design choice 17 (verdicts scoped to the captured matrix).
- Label each change point with its cause when known: a media query (from `CSS.getMediaQueries`, with source file and line), a container query, or "no declared breakpoint" for intrinsic changes. DevTools' "reveal in source" is the precedent.
- For diffs between two versions, the STVR classes map directly: same fact, different range ("left-of now ends at 811, was 767"); same range, different fact; and new or lost ranges. Report the symmetric difference of widths as "look here".
- Borrow: ranges with both bordering widths; grouping by distinct range; Chromatic's rule that a baseline is keyed by a stable name, not by the width value. Avoid: one line per element pair; absolute XPaths as the only element names; a screenshot at the midpoint only.

## Small-range layouts and other range-based heuristics

### Takeaway
A small-range layout is a relation between two elements that holds for at most five or six consecutive widths with a different relation directly below and directly above. As a detector it is noisy: across 45 pages ReDeCheck raised 248 small-range reports, of which 152 were true and 96 false, and 147 of the true ones were one grid problem on one page. Only four of 45 pages had any real small-range failure. The follow-up tools either add a screenshot check (VERVE) or leave the type out (LocaliCSS, ReDeFix).

### Cited Findings
- [PR-text] Cause, as the authors see it: clashing media queries. A rule with `max-width: 768px` and another with `min-width: 768px` are both active at exactly 768 px, since both bounds are inclusive; such failures "occur only in small sub-ranges of the entire range of viewport widths". Example: at one width, Cloudconvert's menu covers the logo. — [ISSTA 2017, sec. 3.2, RLF 4](https://eprints.whiterose.ac.uk/id/eprint/116989/10/c50-3.pdf)
- [PR-text] Algorithm 3: for every edge and every alignment constraint (a_min, a_max, t, P) on it, if a_max − a_min ≤ thres, and a constraint for the same pair and type exists at a_min − 1 and at a_max + 1 "but with different alignment attributes", report a small-range layout for (a_min, a_max). "thres = 5 for experiments in this paper". — [ISSTA 2017, Algorithm 3](https://eprints.whiterose.ac.uk/id/eprint/116989/10/c50-3.pdf)
- [code] The code tests `(ac.getMax() - ac.getMin()) < 5`, then looks for a constraint of the same pair and type whose `max == min − 1` and one whose `min == max + 1`. So the code allows up to five widths and the paper's inequality up to six. It does not require the constraints before and after to be equal to each other. — [RLGAnalyser.java, checkForSmallRanges](https://github.com/redecheck/redecheck/blob/d3f2364960aa7398f7085a502576da70759f5ed0/src/main/java/shef/analysis/RLGAnalyser.java)
- [PR-text] VERVE describes them as "restricted to a range of 1–5 viewports" and as caused by "off-by-one mistakes resulting in a media query being activated for a viewport width erroneously" or other "emergent, intermittent effects". — [Althomali et al. 2021, sec. 3.3 and 4.3](https://eprints.whiterose.ac.uk/165542/8/stvr.1756.pdf)
- [PR-text] ISSTA 2017 results by type (TP / FP / non-observable): collision 8 / 0 / 24; element protrusion 3 / 0 / 36; viewport protrusion 24 / 0 / 23; small-range 152 / 43 / 0; wrapping 10 / 5 / 0. Small-range reports are 195 of 328. — [ISSTA 2017, Table 1b](https://eprints.whiterose.ac.uk/id/eprint/116989/10/c50-3.pdf)
- [PR-text] Per page, the 152 true small-range reports are: AccountKiller 147, CloudConvert 1, Pepfeed 2, WillMyPhoneWork 2. The 43 false ones are spread over 13 pages, 14 of them on Pepfeed. The AccountKiller reports are all "in the range of 476–480 pixels". (This table sums to 326 reports, not 328; the two papers differ by two.) — [Althomali et al. 2021, Table III(a) and sec. 4.5](https://eprints.whiterose.ac.uk/165542/8/stvr.1756.pdf)
- [PR-text] Cause of the false positives: "coincidental alignment attributes being assigned to edges in the rRLG. For example, an element might not have any particular horizontal alignment within its parent, yet for a small-range appear to be center justified, due to chance co-ordinate values". — [ISSTA 2017, RQ1](https://eprints.whiterose.ac.uk/id/eprint/116989/10/c50-3.pdf)
- [PR-text] On 20 further pages, "ReDeCheck reported a total of 53 small-range failures from the additional set that were all FP failures, suggesting the need for improvements to ReDeCheck's small-range detector". — [Althomali et al. 2021, RQ4(c)](https://eprints.whiterose.ac.uk/165542/8/stvr.1756.pdf)
- [PR-text] To have true cases, the authors injected a media query for 992 to 995 px that offset one element by a margin; ReDeCheck then reported 96 small-range failures, 95 true. They chose 992 because most of the pages had a breakpoint there, "a realistic position where a small-range defect may occur in practice". — [Althomali et al. 2021, sec. 4.3 and RQ4(c)](https://eprints.whiterose.ac.uk/165542/8/stvr.1756.pdf)
- [PR-text] VERVE's check: take screenshots at the first width of the small range and at the widths just below and just above it, crop the areas around the two elements, and compare colour histograms (six OpenCV measures); above a tuned threshold the report is a true positive, otherwise a false positive. Agreement with manual labels reached 98.5% on the first page set with the Intersection measure. — [Althomali et al. 2021, sec. 3.3 and RQ3](https://eprints.whiterose.ac.uk/165542/8/stvr.1756.pdf)
- [preprint] LocaliCSS leaves small-range failures out ("we have not considered this RLF type in this research") because they concern media-query rules, not element properties; ReDeFix's data set also excludes them. — [Zerin et al. 2025a, arXiv 2605.25476](https://arxiv.org/abs/2605.25476); [Zerin et al. 2025b, arXiv 2511.00678](https://arxiv.org/abs/2511.00678)
- [spec] The same fault class at sub-pixel scale: with `max-width: 320px` and `min-width: 321px`, "Any viewport widths that fall between 320px and 321px will result in none of the styles being applied." — [Media Queries 4, min- and max- prefixes](https://www.w3.org/TR/mediaqueries-4/#mq-min-max)

### Inferences
- Counted by page, real small-range failures are rare (4 of 45 pages) and the detector's precision outside one page is poor (5 true against 96 false reports). It should be an opt-in hint in onionskin, not a default check.
- Detection depends on a sample landing inside the range. With a 60 px grid and a range of at most 5 px that happens by chance about one time in ten, unless the range touches a declared breakpoint, where the both-sides samples catch it. So in practice ReDeCheck finds small ranges next to breakpoints and misses others. An exhaustive or dense pass is needed to find the rest.
- Four filters follow from the data. (1) Require the before and after facts to be equal (A-B-A); ReDeCheck does not, and an A-B-C sequence is often a legitimate two-step change. (2) Count only changes in position relations (left-of, above, overlaps, inside), not in alignment facts, since chance alignment within a tolerance caused the false positives. (3) Rank ranges that touch a declared breakpoint highest, as a likely off-by-one clash, and name the two media queries. (4) Group by range, so 147 pairs become one entry.
- onionskin's 0.5 px tolerance and fine Allen relations make chance flicker more likely than in ReDeCheck: as width grows, a gap of a fraction of a pixel between two boxes can come and go, turning `meets` into `before` and back. Deriving small-range hints from coarse facts only, or requiring a minimum change in pixels, avoids a flood.
- The clash can be found without rendering: from the extracted media queries, list widths where a `max-width: v` and a `min-width: v` query are both active (overlap at v) and pairs of thresholds less than 1 px apart (gap). This is cheaper and more precise than the geometric heuristic for the main cause the authors name.
- "Small" has no evidence behind it; 5 is a constant chosen for the experiments. A relative rule (shorter than both neighbours by a large factor) would be easier to defend, and is what the thesis wording "only a few widths compared with neighbouring widths" suggests.
- Borrow: the A-B-A idea, bordering-width comparison and VERVE's screenshot confirmation. Avoid: reporting alignment-only flicker; one report per pair; a fixed threshold presented as a fact.

### Gaps
- No study measures how often small-range layouts occur on current sites, or tries thresholds other than 5.
- The split of the 43 false positives by which attribute changed is not published.

## Later and adjacent work up to November 2026

### Takeaway
Nobody outside the Sheffield and Allegheny group has extended the range model. The group's own work stopped in 2022 with automated repair; since then one group in Dhaka has built CSS fault localisation and LLM repair on top of the same failure ranges (2025), and one FSE 2026 paper uses ReDeCheck as a baseline for a two-width accessibility check. I found no independent replication, no industrial report and no critique beyond the authors' own. Mobile platforms have settled on named size classes tested at their boundaries, which is a range model by convention and without inferred ranges.

### Inferences
- The field moved from "where does the layout change" to "repair it with an LLM" without revisiting the model. The 2025 papers treat detection as solved and pay for it with exhaustive one-pixel sampling. That leaves the inferred-range model without a maintained implementation, which is the gap onionskin would fill.
- The two ideas worth taking from the later work are small. From Layout Dr: 17 of 55 failure ranges (31%) started at the bottom of the tested interval and so had no narrower neighbour, and 18 more were bordered by a different failure. Reports and expectations must therefore treat the ends of the tested interval as "unknown beyond here", not as boundaries, and should show neighbouring failure ranges together. From ReFLAIR: a 1280 against 320 comparison of what is present and usable is a cheap, separate check that a range model does not replace.
- Property-based testing fits range checks well and nobody ships it: generate widths, check an invariant (an expectation that should hold over a range), and shrink a failing width toward the nearest boundary. With onionskin's capture cache and the binary search above, shrinking is the same search.
- Mobile practice supports named ranges: a few classes with fixed boundaries, tests at the boundaries, and width treated as more important than height. For the web, the page's own breakpoints are the natural class boundaries, and they can be extracted rather than fixed by convention.
- Borrow: Android's naming of classes and its advice not to run every test at every size; LayoutTest-iOS's product of sizes and generated data with built-in overlap checks. Avoid: assuming exhaustive sampling is free (LocaliCSS and Layout Dr report no timing for it); reading ReDeCheck's numbers from secondary sources, which already disagree on its default range.

## Specification syntax for expectations that hold only in a range of widths

### Takeaway
No tool has a syntax for "this relation holds from width a to width b". Galen tags sections with device names and binds one browser size to a set of tags when the test runs; ReDeCheck has no developer-written spec at all, only inferred tuples; visual tools take lists of widths. The only range syntaxes in use are CSS's own (`min-width`, `max-width`, the level 4 comparison form, and framework mixins over named breakpoints) and Android's size-class annotations.

### Cited Findings
- [docs] Galen tags: "you can wrap all your checks inside @on statement": `@on mobile` / `menu: height 300 px`, `@on desktop` / `menu: height 40 px`; `@on *` applies to all tags; `@on mobile, desktop` to several. — [Galen spec language guide](http://galenframework.com/docs/reference-galen-spec-language-guide/)
- [docs] Galen binds a size to tags outside the spec, in the test suite: `Home page on a small mobile device` / `http://example.com/home 320x600` / `check homepage.gspec --include "mobile,all" --exclude "nomobile"`, or with a table: `@@ parameterized` / `| deviceName | tags | size |` / `| Mobile | mobile | 320x600 |` / `| Tablet | tablet | 640x480 |` / `| Desktop | desktop | 1024x800 |`. The page documents no way to run a spec over a range of sizes. — [Galen test suite syntax](http://galenframework.com/docs/reference-galen-test-suite-syntax/)
- [docs] Galen specs can branch on JavaScript: `@if ${isVisible("banner-1")}` ... `@elseif` ... `@else`, and JavaScript blocks can read the `viewport` and `screen` objects (`header: width ${viewport.width() - 100} px`). The guide does not show a condition on viewport width, though the pieces for one exist. — [Galen spec language guide](http://galenframework.com/docs/reference-galen-spec-language-guide/)
- [PR-text] ReDeCheck's notation for an inferred fact is the tuple (x1, x2, t, P), for example (768, w_max, s, {L}), with w_min and w_max standing for the ends of the tested interval. In reports the same thing prints as `node1 , node2 , SIBLING , 320 , 989 , {attributes}`. — [STVR 2020, sec. 3.1](https://eprints.whiterose.ac.uk/163400/8/stvr.1748.pdf); [ReDeCheck README](https://github.com/redecheck/redecheck)
- [PR-text] Layout Dr and ReDeFix state a range in CSS: `@media (min-width: 800px) and (max-width:900px)`. — [Althomali et al. 2022, Figure 3](https://eprints.whiterose.ac.uk/id/eprint/230094/1/althomali2022.pdf)
- [spec] CSS itself: `(min-width: 600px)` is the same as `(width >= 600px)`, both inclusive; the level 4 form allows strict and two-sided bounds, `(400px <= width <= 700px)`. — [Media Queries 4](https://www.w3.org/TR/mediaqueries-4/#range-context)
- [docs] Bootstrap names breakpoints once and refers to them by name: `media-breakpoint-up(md)`, `media-breakpoint-only(md)`, which compiles to `@media (min-width: 768px) and (max-width: 991.98px)`, and `media-breakpoint-between(md, xl)`, which compiles to `@media (min-width: 768px) and (max-width: 1199.98px)`. — [Bootstrap breakpoints](https://getbootstrap.com/docs/5.3/layout/breakpoints/)
- [PR-text] VizAssert takes the ranges as parameters of the proof, not of each assertion: it "soundly certifies that the assertion is satisfied for all rendering parameters in a user-chosen bounded set". — [Panchekha et al. 2018, abstract](https://doi.org/10.1145/3192366.3192407)
- [docs] Android scopes tests by size class: `@RequiresDisplay(EXPANDED, COMPACT)` on a test, or project-defined annotations such as `annotation class TestExpandedWidth` selected by a runner argument. — [Android: tools to test different screen sizes](https://developer.android.com/training/testing/different-screens/tools)
- [docs] Lists of widths: Percy `widths: [375, 1280]`; BackstopJS `viewports` with `label`, `width`, `height`; Chromatic modes by name or bare width; Applitools `layoutBreakpoints: [320, 768, 1024]`; Playwright `viewport` per project. — [Percy](https://www.browserstack.com/docs/percy/references/config-options); [BackstopJS](https://github.com/garris/BackstopJS); [Chromatic](https://www.chromatic.com/docs/modes/); [Applitools](https://applitools.com/tutorials/playwright/api/runner-configuration); [Playwright](https://playwright.dev/docs/emulation)
- [search] Cornipickle, as used in the ICWE 2020 paper, expresses conditions over successive resized snapshots with temporal operators. Unconfirmed; full text not read. — [slides](https://www.slideshare.net/slideshow/detecting-responsive-web-design-bugs-with-declarative-specifications/234296758)

### Inferences
- Galen's design separates two things that a range syntax must also keep apart: the label on an expectation (`mobile`) and the mapping from labels to sizes (in the suite). Its weakness is that the mapping is to single sizes, so "mobile" is checked at 320 px only. onionskin can keep the separation and make the mapping a range: a map of names to width ranges, declared once, with expectations that refer to a name or give a literal range.
- onionskin's specs are Clojure data and already use `[low high]` for distances and sizes. The same form reads naturally for widths, for example an expectation option `:width [320 767]`, an open end as `[768 nil]`, or a named range `:width :narrow` resolved through a map such as `{:narrow [320 767] :wide [768 nil]}`. This mirrors Bootstrap's named breakpoints and ReDeCheck's (x1, x2) pairs, and needs no parser.
- The bounds need a stated meaning. Three choices come from the sources. (1) Inclusive integer bounds, as in ReDeCheck and `min-width`/`max-width`: simple, and matches what is captured. (2) Half-open real intervals, as the level 4 comparison form allows: `[768 992)` composes without gaps or overlaps and survives fractional widths. (3) Names tied to the page's own breakpoints: "from the `md` breakpoint up". Inclusive integers are the right default because captures are at integer widths, but adjacent ranges should be checked for gaps and overlaps, since that is exactly the fault the small-range detector looks for in CSS.
- The quantifier needs a stated meaning too. "Holds from 320 to 767" can mean at every captured width in the range (what a check can show), at every width (what the developer means), or only that the fact's inferred range contains 320 to 767. A third kind of expectation is about the change itself: "left-of below the switch, above from it, and the switch is at 768 give or take 2". None of the surveyed tools can state the last form, and it is the one a range model makes cheap, because the inferred run list answers it directly.
- An expectation with a range also tells the sampler where to look: both ends of each stated range, and one pixel outside each end, should be added to the sample set, in the same way as both sides of a breakpoint.
- An expectation can also be generated: capture, infer the run lists, and print them as a spec for the developer to prune. The earlier report warned against using generated facts as expectations at single widths; run lists are far shorter than per-width facts, so the warning is weaker here, but it still applies to fine relations.
- Borrow: Galen's split between labels and sizes; Bootstrap's named breakpoints with `up`, `only` and `between`; Android's class annotations for selecting which checks run at which sizes; CSS's own range forms as a familiar vocabulary. Avoid: tags bound to one size; ranges written in each expectation with no shared names (they drift apart, which is the media-query clash again, moved into the spec).

### Gaps
- Galen's guide does not show `@if` with a viewport condition; whether it works was not tested. Galen is unmaintained, so this matters only as precedent.
- Quixote's `frame.resize` (from the earlier notes) and Cypress's `cy.viewport` were not re-read in this session; both set one size imperatively and have no range form.
- I found no tool, maintained or not, with a declarative width-range syntax for layout expectations, so there is no user experience to learn from on how such a syntax ages.
