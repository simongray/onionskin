# Element matching across markup changes

Notes for the onionskin report writer. All sources were checked on 2026-11-12. Labels: [PR] peer-reviewed paper, [Preprint] arXiv or similar and not peer-reviewed as cited, [Thesis], [Docs] tool documentation or design document, [Code] source code read directly, [Blog] blog post or secondary summary. "Unconfirmed" marks anything that was not checked against a primary source in this session.

Context from onionskin's code: a full capture records only `path`, `box`, `style` and `pseudo` for each node (`src/dk/simongray/onionskin/impl/capture.js`), and the diff pairs nodes by exact path (`impl/diff.cljc`). No id, class, attribute or text is captured today. Any matcher that uses more than tag names and tree shape needs the capture to record more.

## 1. Tree edit distance (Zhang and Shasha, RTED, APTED): cost, and behaviour on a wrapper insertion

### Takeaway
Exact tree edit distance needs cubic time and quadratic memory, and published measurements show minutes per pair on real pages of a few thousand nodes. Its edit model handles one added wrapper cheaply, but it has no move operation, so it is useful only as a fallback on small leftover subtrees, which is how GumTree uses it.

### Cited Findings
- [Docs] RTED runs in O(n^3) time and O(mn) space. The authors have stopped updating it and say APTED supersedes it. The edit operations are delete, insert and rename; there is no move. APTED is MIT-licensed Java, RTED is AGPL. The page lists one known problem: strategy computation for trees larger than 40,000 nodes "may be faulty" - [APTED project page, Univ. Salzburg](http://tree-edit-distance.dbresearch.uni-salzburg.at/)
- [PR] The papers behind the tools: Pawlik and Augsten, "RTED: A Robust Algorithm for the Tree Edit Distance", PVLDB 5(4), 2011 ([arXiv 1201.0230](https://arxiv.org/abs/1201.0230)); Pawlik and Augsten, "Efficient Computation of the Tree Edit Distance", ACM TODS 40(1), 2015; Pawlik and Augsten, "Tree edit distance: Robust and memory-efficient", Information Systems 56, 2016, pp. 157-173. The RTED abstract claims the algorithm is "worst-case optimal" and never worse than its competitors for any tree shape - [RTED abstract](https://arxiv.org/abs/1201.0230); citations from [APTED repository](https://github.com/DatabaseGroup/apted)
- [Docs] APTED returns a node mapping as well as the distance. Unmapped source nodes count as deleted and unmapped destination nodes as inserted. The default cost model charges 1 per insert or delete. The repository was last pushed on 2018-02-19 and has no tagged release - [APTED repository](https://github.com/DatabaseGroup/apted)
- [PR] In GumTree's evaluation on source files, RTED ran out of memory (4 GB JVM) on 82 modifications (about 5%) and took more than 10 seconds on 206 more (about 12%), so it gave no result for about 17% of cases. RTED's median running time was 298 times (Jenkins, Java) and 2,654 times (jQuery, JavaScript) that of a text diff; GumTree's medians were 18 and 30 times, with mean running times of 20 ms and 74 ms. The paper also notes that RTED "does not identify move actions" - [Falleri et al., ASE 2014, Sections 4 and 5.3](https://www.labri.fr/perso/xblanc/data/papers/ASE14.pdf)
- [Preprint of PR] On home pages of the Alexa top 1,000 sites, APTED was stopped by a 450-second timeout on large pages and "may run up to 100 times slower than SFTM". The introduction gives one example: the YouTube page took APTED about 4 minutes and SFTM less than a second. The paper states the bounds as O(n^2) space and O(n^3) time for APTED, and cites a cubic lower bound for tree edit distance - [Brisset et al., SFTM, arXiv 2004.12821, Sections 1, 2 and 5.2, Figure 7](https://arxiv.org/abs/2004.12821)
- [Preprint of PR] On the same mutation data, APTED and SFTM gave matchings of "very similar" quality. Both lost accuracy linearly as the share of mutated nodes grew, and APTED was less stable (r^2 = 60%) - [SFTM, Section 5.2, Figure 6](https://arxiv.org/abs/2004.12821)
- [Docs] sosie's design document rejects exact tree edit distance for DOM trees: "Zhang-Shasha is O(n^4) worst case; RTED is O(n^3)", both "too slow above ~1000 nodes". It estimates 30 to 120 s for RTED at 5,000 nodes against under 500 ms for its GumTree-style matcher. These are design-document estimates, not a published benchmark - [sosie design doc](https://github.com/cuihtlauac/sosie/blob/main/sosie-design.md)
- [Code] GumTree runs an optimal algorithm only on small subtrees. The classic bottom-up matcher applies it when either subtree has fewer than 1,000 nodes (`DEFAULT_SIZE_THRESHOLD = 1000`; the 2014 paper used `maxSize = 100`). The hybrid matcher applies Zhang-Shasha (`ZsMatcher`) only below 20 nodes - [GreedyBottomUpMatcher.java](https://github.com/GumTreeDiff/gumtree/blob/main/core/src/main/java/com/github/gumtreediff/matchers/heuristic/gt/GreedyBottomUpMatcher.java); [HybridBottomUpMatcher.java](https://github.com/GumTreeDiff/gumtree/blob/main/core/src/main/java/com/github/gumtreediff/matchers/heuristic/gt/HybridBottomUpMatcher.java)
- [PR] Tree edit distance mappings are "rigid": they may not break ancestor-descendant relations or the left-to-right order of siblings - [Kumar et al., Flexible Tree Matching, IJCAI 2011, Section 1](https://www.timroughgarden.org/papers/ijcai11.pdf)
- [Docs] React's documentation gives the same reason for not using exact algorithms: generic tree diffing is "in the order of O(n^3)", so 1,000 elements would need about one billion comparisons - [React legacy docs, Reconciliation](https://legacy.reactjs.org/docs/reconciliation.html)

### Inferences
- A wrapper insertion is the easy case for tree edit distance. In the standard model an inserted node takes over a run of consecutive children of its new parent, so one new wrapper costs one insert and every node below it keeps its partner. Removal is one delete. The definition is the classic one (Tai 1979; Zhang and Shasha 1989) and was not re-read here.
- A move is the hard case. A subtree that moves to another parent, or two siblings that swap, cannot be mapped under the ancestor and order constraints. The optimal script deletes and re-inserts the nodes, and onionskin would again report "removed" and "added".
- Memory at onionskin's sizes: a quadratic table for two trees of 6,000 nodes has 36 million cells, so 150 to 300 MB at 4 to 8 bytes per cell before any overhead. Time is the bigger problem: the measurements above put pages of a few thousand nodes in the range of tens of seconds to minutes.
- Borrow: the idea of an exact algorithm as a bounded fallback (GumTree's size limits of 20, 100 or 1,000 nodes). A plain Zhang-Shasha on subtrees of at most 20 to 50 nodes is small to write and cheap to run.
- Avoid: exact tree edit distance over the whole page, and any library dependency for it. Also avoid treating "minimal edit script" as the goal. sosie's document makes the point that the diff has to be correct and informative, not minimal.

### Gaps
- Zhang and Shasha (1989), "Simple fast algorithms for the editing distance between trees and related problems", SIAM J. Comput. 18(6), was not read. The usual statement of its cost, O(n1 n2 min(depth1, leaves1) min(depth2, leaves2)) time and O(n1 n2) space, is unconfirmed from the primary source.
- No published timing of APTED or RTED on DOM trees with exact node counts in a table was found. The SFTM figures are plots, and the text gives only the timeout and the YouTube example.
- The cubic lower bound (Bringmann et al.) is cited through the SFTM paper and was not read.

## 2. Tree differencing with moves: GumTree, ChangeDistiller, MTDIFF, IJM and their critiques

### Takeaway
GumTree's two phases are the best fit for a wrapper-tolerant matcher: map identical subtrees first, largest first, then map containers whose descendants are mostly mapped. The 2024 "simple" variant replaces the costly exact recovery step with three cheap child-alignment rules and is now GumTree's default. Independent studies still find inaccurate mappings in 20 to 30% of source-file revisions, mostly where many subtrees look alike, and no accuracy figures exist for HTML.

### Cited Findings

#### GumTree (2014): the algorithm
- [PR] Citation: Falleri, Morandat, Blanc, Martinez, Monperrus, "Fine-grained and Accurate Source Code Differencing", ASE 2014, pp. 313-324, https://doi.org/10.1145/2642937.2642982 - [open copy](https://www.labri.fr/perso/xblanc/data/papers/ASE14.pdf)
- [PR] The edit actions are update value, add, delete and move (of a whole subtree). The paper only describes the mapping step; the edit script is then produced by the algorithm of Chawathe et al. (SIGMOD 1996) - [ASE 2014, Sections 2 and 3](https://www.labri.fr/perso/xblanc/data/papers/ASE14.pdf)
- [PR] Top-down phase ("anchor mappings"). Height is 1 for a leaf and 1 plus the tallest child otherwise. Keep two priority lists of nodes ordered by height, one per tree, starting with the roots. While the taller of the two heads is above `minHeight`: if the heads differ in height, pop the taller nodes and push their children. Otherwise pop all nodes of that height from both lists and test each pair for isomorphism, by a subtree hash followed by an exact comparison when the hashes are equal. A pair with no other isomorphic candidate on either side is mapped at once, with all their descendants. Pairs with several candidates go into a candidate list. Nodes that found no partner have their children pushed. At the end, the candidate list is sorted by the dice value of the parents, highest first, and consumed greedily, dropping candidates whose nodes are already mapped - [ASE 2014, Section 3.1, Algorithm 1](https://www.labri.fr/perso/xblanc/data/papers/ASE14.pdf)
- [PR] dice(t1, t2, M) = 2 x (number of descendants of t1 mapped to descendants of t2) / (number of descendants of t1 + number of descendants of t2). It ranges from 0 to 1 - [ASE 2014, Section 3.1](https://www.labri.fr/perso/xblanc/data/papers/ASE14.pdf)
- [PR] Bottom-up phase ("container mappings"). Visit the first tree in post-order. For each node that is not a leaf, is unmapped and has mapped children, the candidates are the unmapped nodes of the second tree with the same label that share mapped descendants with it. Take the candidate with the highest dice value and map the pair if dice is above `minDice`. Then, if both subtrees are smaller than `maxSize`, run an optimal edit-distance algorithm without moves on the pair and add the mappings it finds between nodes with equal labels ("recovery mappings") - [ASE 2014, Section 3.2, Algorithm 2](https://www.labri.fr/perso/xblanc/data/papers/ASE14.pdf)
- [PR] Parameters in the paper's evaluation: `minHeight = 2`, `minDice = 0.5`, `maxSize = 100`. The running-time experiment used `minDice = 0.2`. Worst-case cost is O(n^2): the top-down phase can compare all pairs of nodes of equal height and the bottom-up phase all pairs of unmapped nodes. The authors call this worst case "very unlikely" on real syntax trees - [ASE 2014, Sections 3.3, 4 and 5](https://www.labri.fr/perso/xblanc/data/papers/ASE14.pdf)
- [PR] Results on 12,792 Java file pairs. Against RTED: the same number of mappings in 68.42% of cases, more mappings with GumTree in 21.94%, fewer in 9.65%; the same edit-script size in 59.25% and a shorter script with GumTree in 23.6%. Against ChangeDistiller at fine granularity: more mappings in 65.49% of cases and a shorter script in 80.97% - [ASE 2014, Section 5.2.4, Table 2](https://www.labri.fr/perso/xblanc/data/papers/ASE14.pdf)

#### GumTree today: the simple and hybrid matchers
- [Code] GumTree is maintained: release v4.1.0 on 2026-10-09, last push 2026-11-11, 1,340 stars. It parses through tree-sitter and srcML - [GumTree repository](https://github.com/GumTreeDiff/gumtree); [GumTree wiki, Getting Started](https://github.com/GumTreeDiff/gumtree/wiki/Getting-Started)
- [Code] Registered matchers: `gumtree-simple` (GreedySubtreeMatcher then SimpleBottomUpMatcher; registered with the highest priority, which makes it the default), `gumtree-classic` (the 2014 algorithm), `gumtree-hybrid` (simple, plus Zhang-Shasha on subtrees under 20 nodes), `gumtree-simple-id` and `gumtree-hybrid-id` (an IdMatcher first), `change-distiller`, `xy` (XyDiff-style bottom-up, threshold 0.5), and "theta" variants that add MTDIFF's optimisations - [CompositeMatchers.java](https://github.com/GumTreeDiff/gumtree/blob/main/core/src/main/java/com/github/gumtreediff/matchers/CompositeMatchers.java)
- [Code] `IdMatcher` maps two nodes when they carry the same `id` metadata and that id occurs exactly once in each tree. It runs before the other phases - [IdMatcher.java](https://github.com/GumTreeDiff/gumtree/blob/main/core/src/main/java/com/github/gumtreediff/matchers/heuristic/IdMatcher.java)
- [Code] In the top-down matcher, ambiguous groups are handled largest subtree first, and candidate pairs inside a group are ordered by a comparator before the greedy pass. The default minimum priority is 1, measured by height - [GreedySubtreeMatcher.java](https://github.com/GumTreeDiff/gumtree/blob/main/core/src/main/java/com/github/gumtreediff/matchers/heuristic/gt/GreedySubtreeMatcher.java)
- [Code] The simple bottom-up matcher, in post-order over the first tree: the two roots are always mapped. For an unmapped inner node, the candidates are found by walking up from the partners of its mapped descendants and collecting unmapped ancestors of the same type, so no all-pairs scan is needed. Similarity is (mapped descendants in common) / (the larger of the two descendant counts). When no threshold is configured, the threshold adapts to size: 1 / (1 + ln(descendants of candidate + descendants of node)). After each container mapping comes a "last chance" pass over the two nodes' unmapped children - [SimpleBottomUpMatcher.java](https://github.com/GumTreeDiff/gumtree/blob/main/core/src/main/java/com/github/gumtreediff/matchers/heuristic/gt/SimpleBottomUpMatcher.java); [SimilarityMetrics.java](https://github.com/GumTreeDiff/gumtree/blob/main/core/src/main/java/com/github/gumtreediff/matchers/SimilarityMetrics.java)
- [Code, PR slides] The last-chance pass has three steps: a longest common subsequence over unmapped children that are isomorphic, then one over children with the same structure (same shape and types, labels ignored), then a "histogram" step that maps children whose type is unique among the unmapped children on both sides and recurses into them. The ICSE 2024 slides name the steps isomorphism, iso-structure and uni-type - [SimpleBottomUpMatcher.java](https://github.com/GumTreeDiff/gumtree/blob/main/core/src/main/java/com/github/gumtreediff/matchers/heuristic/gt/SimpleBottomUpMatcher.java); [Falleri and Martinez, ICSE 2024 slides](https://www.labri.fr/perso/falleri/img/slides/icse24.pdf)
- [PR] Citation: Falleri and Martinez, "Fine-grained, Accurate, and Scalable Source Code Differencing", ICSE 2024, pp. 2856-2867, https://doi.org/10.1145/3597503.3639148. The paper replaces the exact recovery step, which made large trees slow, with the cheaper heuristic. The conference listing reports edit scripts with a median size 50% smaller and a total speedup between 50x and 281x; the slides say "around 50% smaller" and "between 50% and 300% matching speedup", so the two do not agree on the speedup. In a study with 7 participants, 90% of the smaller edit scripts were judged better - [ICSE 2024 listing](https://conf.researchr.org/details/icse-2024/icse-2024-research-track/148/Fine-grained-accurate-and-scalable-source-differencing); [slides](https://www.labri.fr/perso/falleri/img/slides/icse24.pdf)
- [PR] Thresholds matter. Martinez, Falleri and Monperrus, "Hyperparameter Optimization for AST Differencing", IEEE TSE 2023: a tuned configuration improved GumTree's edit scripts in 21.8% of the evaluated cases - [arXiv 2011.10268](https://arxiv.org/abs/2011.10268)

#### ChangeDistiller, MTDIFF, IJM, truediff
- [PR] ChangeDistiller: Fluri, Würsch, Pinzger, Gall, "Change Distilling: Tree Differencing for Fine-Grained Source Code Change Extraction", IEEE TSE 33(11), 2007, https://doi.org/10.1109/TSE.2007.70731. It follows the bottom-up scheme of Chawathe et al.: leaves are matched by bigram string similarity of their text, inner nodes by the share of matched leaves. GumTree's reimplementation uses a label similarity threshold of 0.5 for leaves and, for inner nodes, 0.6 when the node has more than 4 leaves and 0.4 otherwise. The abstract reports a mean absolute percentage error of 34% against 79% for the algorithm it improves on (abstract as quoted in a search summary, unconfirmed) - [ASE 2014, Section 5 replication note](https://www.labri.fr/perso/xblanc/data/papers/ASE14.pdf); [ChangeDistillerLeavesMatcher.java](https://github.com/GumTreeDiff/gumtree/blob/main/core/src/main/java/com/github/gumtreediff/matchers/heuristic/cd/ChangeDistillerLeavesMatcher.java); [ChangeDistillerBottomUpMatcher.java](https://github.com/GumTreeDiff/gumtree/blob/main/core/src/main/java/com/github/gumtreediff/matchers/heuristic/cd/ChangeDistillerBottomUpMatcher.java)
- [PR] Chawathe et al.'s matcher, which ChangeDistiller adapts, runs a longest common subsequence for every element starting from the leaves and costs O(ne + e^2), where n is the number of leaves and e a weighted edit distance. The edit script costs O(nd), with d the number of children that move within a parent. The worst case is quadratic - [Cobena et al., ICDE 2002, Section 3](https://www.csd.uoc.gr/~hy561/Data/Papers/detecting.pdf)
- [PR] MTDIFF: Dotzler and Philippsen, "Move-optimized source code tree differencing", ASE 2016, pp. 660-671, https://doi.org/10.1145/2970276.2970315. It offers five general optimisations that shorten the edit scripts of existing algorithms. MTDIFF itself builds on ChangeDistiller and shortens the script for another 20% of changes (abstract via search summary, unconfirmed). GumTree ships them as matchers named for identical subtrees, LCS, unmapped leaves, inner nodes, leaf moves and cross moves - [CompositeMatchers.java](https://github.com/GumTreeDiff/gumtree/blob/main/core/src/main/java/com/github/gumtreediff/matchers/CompositeMatchers.java)
- [PR] IJM: Frick, Grassauer, Beck, Pinzger, "Generating Accurate and Compact Edit Scripts Using Tree Differencing", ICSME 2018 (venue and DOI not re-checked; a reprint is listed at https://doi.org/10.18420/se2020_24). It builds on GumTree and restricts matching to parts of the tree, for example method declarations with the same signature. The authors report better accuracy for moves and updates than GumTree and MTDIFF (via search summaries of the paper and of a 2024 paper that describes it, unconfirmed) - [arXiv 2403.05939](https://arxiv.org/abs/2403.05939)
- [PR] Critique: Fan, Xia, Lo, Hassan, Wang, Li, "A Differential Testing Approach for Evaluating Abstract Syntax Tree Mapping Algorithms", ICSE 2021. On 263,165 file revisions from ten Java projects, GumTree, MTDiff and IJM produced inaccurate mappings for 20 to 29%, 25 to 36% and 21 to 30% of the file revisions. Twelve external experts confirmed the method on 200 statements; its precision was 0.98 to 1.00 and its recall 0.65 to 0.75 - [arXiv 2103.00141](https://arxiv.org/abs/2103.00141)
- [PR] truediff: Erdweg, Szabó, Pacak, "Concise, Type-Safe, and Efficient Structural Diffing", PLDI 2021. It runs in linear time, decides subtree equality with hashes and uses no similarity scores. The authors report patches of about the same size as GumTree's and running times an order of magnitude lower - [truediff paper](https://www.pl.informatik.uni-mainz.de/files/2021/06/truediff.pdf); [PLDI 2021 listing](https://pldi21.sigplan.org/details/pldi-2021-papers/27/Concise-Type-Safe-and-Efficient-Structural-Diffing)

#### GumTree on DOM trees: sosie
- [Docs] sosie (OCaml, GitHub release v0.1.2 on 2026-08-21, last push 2026-08-24, 1 star) uses "a simplified GumTree algorithm" on captured DOM trees. Phase 1: a bottom-up hash, hash(node) = H(tag, child hashes), and identical subtrees are matched; the document says this "handles 80-95% of nodes in a typical refactoring". Phase 2: an unmatched node is matched to the unmatched node with the best dice value over matched descendants when it exceeds 0.5. Phase 3: a longest common subsequence aligns the children of matched nodes. Stated speed: 5 to 50 ms at 500 nodes and 50 to 500 ms at 5,000 - [sosie design doc](https://github.com/cuihtlauac/sosie/blob/main/sosie-design.md)
- [Code] sosie's hash covers the tag and the child hashes only, not attributes, text, boxes or styles. Among several candidates with the same hash it prefers the one whose parent is already matched, then the same sibling index. After the three phases it keeps only the pairs found in both directions (match(A, B) and match(B, A)) and removes pairs that break ancestor order. The interface documents four invariants checked on all tree pairs up to 5 nodes: no node has two partners, the result is symmetric, ancestors are preserved, and a tree matched with itself matches every node. The code comment for phase 1 says it processes hashes "from leaves up", while the design document says "largest first" - [gumtree.ml](https://github.com/cuihtlauac/sosie/blob/main/lib/gumtree.ml); [gumtree.mli](https://github.com/cuihtlauac/sosie/blob/main/lib/gumtree.mli)
- [Docs] sosie reports structure changes as their own diff kinds: `Moved_node`, `Wrapper_inserted`, `Wrapper_removed`, `Extra_node` and `Tag_mismatch`. Wrapper diffs are "informational" - [sosie design doc](https://github.com/cuihtlauac/sosie/blob/main/sosie-design.md)

### Inferences
- The core that onionskin needs is small (question 10 gives a fuller sketch). (1) A subtree signature per node, for example the tag plus the signatures of the children. (2) Top-down: pair subtrees whose signature occurs once in each capture, largest first, and map all their descendants. (3) Bottom-up in post-order: for an unmapped element, walk up from the partners of its mapped descendants to collect unmapped candidates with the same tag, and pair with the best one if the overlap passes a threshold. (4) For each new pair, align the remaining children with a longest common subsequence on tag, then pair children whose tag is unique on both sides. Steps 2 to 4 are GumTree simple without a parser, and fit in a few hundred lines of Clojure.
- Why this survives a wrapper: the subtrees below the wrapper are identical, so step 2 maps them whatever their paths are. The old parent then finds the new parent through its mapped descendants. The wrapper stays unmapped and can be reported as "wrapper added", as sosie does.
- The known weak spot carries over from code to HTML and is probably worse there: repeated identical subtrees (list items, table rows, icon buttons, empty divs). GumTree parks these as ambiguous and falls back on the parents' dice value. Fan et al.'s 20 to 30% inaccuracy on code suggests onionskin needs extra tie-breakers for such groups: a key, own text, sibling order, and as a last resort the box.
- `minHeight` has a clear meaning for DOM trees. The top-down phase only anchors subtrees whose height is greater than `minHeight`, with height 1 for a leaf. At `minHeight = 2`, neither a lone leaf nor an element with only leaf children is paired by hash alone, which matters because a bare `span` or `div` matches hundreds of others. Such nodes are then picked up by step 4 under their matched parents.
- GumTree simple's adaptive threshold, 1 / (1 + ln(sum of sizes)), is easier to defend than a fixed 0.5. A large container such as `body` needs only a small share of mapped descendants (about 0.1 at 6,000 nodes), while a small one needs most of them (0.42 for 4 descendants in total).
- Borrow from GumTree: the two phases, exact comparison after a hash hit, candidates found through mapped descendants, the three recovery rules, and the id pass that requires the id to be unique in both trees. Borrow from sosie: the symmetric run and the ancestor-order repair as cheap safety checks, exhaustive tests on all small trees, and wrapper and move entries as informational changes. Borrow from truediff: equality by hash and no similarity scores in the first phase.
- Avoid: the classic matcher's exact recovery on subtrees up to 1,000 nodes (the reason for the 2024 rewrite), ChangeDistiller's leaf-text matching as the first step (DOM leaves are often empty or repeated), and tuning thresholds on a handful of pages (the hyperparameter study shows defaults are often not the best).

### Gaps
- No peer-reviewed measurement of GumTree, ChangeDistiller, MTDIFF or IJM on HTML or DOM trees was found. sosie's 80 to 95% figure and its timings are design-document claims with no dataset.
- The ICSE 2024 paper's full text was not read (only the listing, the slides and the code), so the exact speedup and the evaluation tables are unconfirmed.
- The ChangeDistiller, MTDIFF and IJM papers were not read first-hand; their numbers come from abstracts quoted in search summaries and from GumTree's reimplementations.
- HyperDiff (Le Dilavrec et al., ASE 2022) and iASTMapper were not examined.

## 3. XML and HTML diff algorithms, and reconciliation in virtual DOM libraries

### Takeaway
The fast XML and DOM differs get their speed from three assumptions: identical subtrees can be found by hash, ids or keys are trustworthy, and children can be compared position by position under an already matched parent. XyDiff adds upward propagation and so tolerates some structural change; React, morphdom and most HTML diffs only compare siblings under a matched parent, so one new wrapper makes them rebuild or mismatch the whole subtree.

### Cited Findings

#### XyDiff
- [PR] Citation: Cobéna, Abiteboul, Marian, "Detecting Changes in XML Documents", ICDE 2002, pp. 41-52, https://doi.org/10.1109/ICDE.2002.994696. The algorithm, BULD ("Bottom-Up, Lazy-Down"), supports insert, delete, update and subtree move, and runs in O(n log n) time where earlier algorithms were quadratic. The authors note the problem with moves is NP-hard, so "the linear time is obtained by trading some quality" - [XyDiff paper, abstract and Section 1](https://www.csd.uoc.gr/~hy561/Data/Papers/detecting.pdf)
- [PR] Phase 1: nodes with an ID attribute declared in the DTD are matched by id value, and a node with an id may only match a node with the same id. Phase 2: one pass computes for every node a signature (a hash of its content and its children's signatures) and a weight (text size for text nodes, the sum of the children's weights for elements). Phase 3: a priority queue hands out the heaviest unmatched subtree of the new document; the candidates are old nodes with the same signature; with several candidates, the best is the one whose parent is matched to the parent of the node in hand, and the algorithm may look further up, by a number of levels that depends on the weight. When a pair is accepted, their ancestors are matched too as long as the labels agree, again up to a weight-dependent number of levels. If nothing matches, the node's children go into the queue. Phase 4: a bottom-up and then top-down pass matches nodes with the same label under matched parents. Propagation downwards is "lazy": it happens at once only when the parents have a single child with that label. Phase 5: unmatched nodes become inserts and deletes; matched nodes whose parents are not matched to each other become moves - [XyDiff paper, Section 5](https://www.csd.uoc.gr/~hy561/Data/Papers/detecting.pdf)
- [PR] On real web XML the deltas were about the size of a Unix diff, and on synthetic changes they were close in size to the known change - [XyDiff paper, Section 1](https://www.csd.uoc.gr/~hy561/Data/Papers/detecting.pdf)
- [Preprint of PR, via search summary] The journal version of SFTM says that tree edit distance and XyDiff "either fail to scale beyond a few hundred nodes or achieve relatively low accuracy" on real web pages. The arXiv version does not evaluate XyDiff, so the XyDiff accuracy figure is unconfirmed - [SFTM journal record](https://doi.org/10.1016/j.is.2022.102126)
- [Code] Maintenance: the open-source `xydiff` code was last pushed in 2022 and its last release is 3.0.0 from 2015. GumTree keeps an `xy` matcher (threshold 0.5) - [xydiff repository](https://github.com/fdintino/xydiff); [CompositeMatchers.java](https://github.com/GumTreeDiff/gumtree/blob/main/core/src/main/java/com/github/gumtreediff/matchers/CompositeMatchers.java)

#### X-Diff, faxma, DaisyDiff, diffDOM
- [PR] X-Diff: Wang, DeWitt, Cai, "X-Diff: An Effective Change Detection Algorithm for XML Documents", ICDE 2003, pp. 519-530, https://doi.org/10.1109/ICDE.2003.1260818. It treats XML as an unordered tree, which the authors argue suits database uses better. The general unordered problem is NP-complete; X-Diff stays polynomial by using XML-specific features, namely node signatures and subtree hashes, and computes a minimum-cost matching. The paper compares it with XyDiff (details via search summary, unconfirmed) - [X-Diff record](https://doi.org/10.1109/ICDE.2003.1260818)
- [PR] faxma: Lindholm, Kangasharju, Tarkoma, "Fast and simple XML tree differencing by sequence alignment", DocEng 2006, https://doi.org/10.1145/1166160.1166183. It turns both ordered trees into sequences, aligns the sequences with a greedy heuristic and turns the result back into tree operations, with subtree move as a primitive. A Java implementation exists as Fuego Diff (abstract via search summary, unconfirmed) - [fuego-diff repository](https://github.com/ept/fuego-diff)
- [Docs] DaisyDiff is a Java library that compares HTML and marks added, removed and changed words and style changes for a human reader. Its repository was last pushed on 2024-08-08 and has no tagged release. A search summary reports that MediaWiki removed it after major errors and that its older algorithm ran out of memory on large inputs (unconfirmed) - [DaisyDiff repository](https://github.com/DaisyDiff/DaisyDiff)
- [Docs] diffDOM prefers relocating DOM nodes over removing and inserting them and diffs faster on its own plain-object form of the DOM. Its README does not describe how it matches nodes. The repository was last pushed on 2025-10-04; its last GitHub release is v2.4.0 from 2018 - [diffDOM repository](https://github.com/fiduswriter/diffDOM)

#### React, morphdom, idiomorph
- [Docs] React replaces the O(n^3) problem with an O(n) heuristic that rests on two assumptions: "Two elements of different types will produce different trees", and the developer can mark stable children with a `key`. When the type at a position differs, React discards the old subtree and builds a new one; changing `<div><Counter/></div>` to `<span><Counter/></span>` destroys and remounts `Counter`. Children without keys are compared by position, so inserting at the start changes every child. Keys only need to be unique among siblings. React can express a move among siblings but not a move elsewhere in the tree. Index keys and unstable keys are warned against - [React legacy docs, Reconciliation](https://legacy.reactjs.org/docs/reconciliation.html)
- [Code] morphdom (last push 2026-01-24, 3,581 stars) keys elements by `id` unless a `getNodeKey` function is given. It indexes every keyed element of the old tree, then walks the old and new child lists together in one pass. A keyed new child pulls its old element from anywhere in the old tree into place. Children without keys are paired in order when node type and node name agree - [morphdom source](https://github.com/patrick-steele-idem/morphdom/blob/master/src/morphdom.js); [morphdom README](https://github.com/patrick-steele-idem/morphdom)
- [Docs] idiomorph (v0.8.0, released 2026-09-05) computes an "id set" for every element: its own id plus the ids of all its descendants. Two elements can match when their id sets intersect, so a parent without an id is matched through its children. Its README says morphdom matches by id only among siblings and ignores the children's structure, and that idiomorph is about 10% slower than morphdom on large morphs - [idiomorph README](https://github.com/bigskysoftware/idiomorph)

### Inferences
- Where each family goes wrong on a new wrapper. React, morphdom and positional HTML diffs compare the children of matched parents. The wrapper sits where a child used to be, has another type or content, and everything below it is rebuilt or mispaired. X-Diff (as recalled, unconfirmed) only matches nodes whose root-to-node label paths are equal, so a wrapper changes the signature of every descendant, which is the same failure as onionskin's path matching. XyDiff and GumTree survive because their first step finds identical subtrees wherever they are.
- idiomorph's id set is the cheapest wrapper-tolerant idea in this group: an ancestor is identified by the keyed elements it contains. It is the keyed counterpart of GumTree's container mapping (dice over mapped descendants), and it shows that a few keys spread over a page can anchor most containers.
- XyDiff's heaviest-first order with weight-limited upward propagation is a useful refinement: a large identical subtree may claim several ancestors, a small one only its parent. This limits the damage of a small coincidental match.
- Borrow: XyDiff's rule that a node with an id can only match a node with the same id; its "lazy down" rule (propagate to a child only when its label is unique under both parents), which matches GumTree's uni-type step; moves defined as "matched, but parents not matched to each other"; idiomorph's id sets.
- Avoid: lockstep child comparison as the main method; keys that are only unique among siblings (React's rule suits rendering, not version matching); unordered matching in X-Diff's style, since DOM order is meaningful and the cost is higher.

### Gaps
- DiffX (Al-Ekram, Adma, Baysal, CASCON 2005) and DeltaXML's algorithm were not researched; nothing can be said about them here.
- X-Diff's signature definition and complexity were not confirmed from the paper text.
- faxma's benchmark numbers and DaisyDiff's and htmldiff's algorithms were not read from primary sources.
- No study was found that measures any of these tools on wrapper insertions in real pages.

## 4. Flexible tree matching for web pages: Bricolage, SFTM and Erratum

### Takeaway
Flexible tree matching drops the ancestry constraint and scores every candidate pair by label similarity plus agreement with neighbours. SFTM makes this fast with an inverted index over tokens and reaches about the accuracy of exact tree edit distance in a fraction of the time; in locator repair it found the right element in 87% of synthetic and 78% of real cases against 42% and 52% for WATER. It depends on rich attributes, has many parameters without published defaults, and its errors come almost only from structural change.

### Cited Findings

#### Flexible tree matching (Bricolage)
- [PR] Citation: Kumar, Talton, Ahmad, Roughgarden, Klemmer, "Flexible Tree Matching", IJCAI 2011, pp. 2674-2679 - [IJCAI proceedings](https://ijcai.org/proceedings/2011/445); [PDF](https://www.timroughgarden.org/papers/ijcai11.pdf). It was built for Bricolage (Kumar, Talton, Ahmad, Klemmer, CHI 2011), which transfers content between page designs.
- [PR] The model is a complete bipartite graph between the nodes of the two trees, plus a "no match" node on each side. An edge costs w_r x relabel cost + ancestry cost + sibling cost; an edge to "no match" costs w_n. The ancestry cost is w_a x the number of children of either node that are mapped to something that is not a child of the other node. The sibling cost is w_s times a term for siblings that land in different sibling groups. A matching uses every node exactly once and its cost is the sum over its edges - [Flexible Tree Matching, Sections 2 and 3](https://www.timroughgarden.org/papers/ijcai11.pdf)
- [PR] Finding the best flexible matching is strongly NP-complete. The paper approximates it with the Metropolis algorithm: build a matching by repeatedly fixing an edge (the next-cheapest edge is taken with probability gamma), pruning the edges that conflict, and updating cost bounds; propose a new matching by keeping a random prefix of the old one. The implementation uses gamma = 0.7 and N = 100 iterations, with beta chosen per domain - [Flexible Tree Matching, Sections 5 to 7](https://www.timroughgarden.org/papers/ijcai11.pdf)
- [PR] The weights were learned with a structured perceptron from 117 human matchings between 52 pairs of 50 popular pages, on trees segmented to reflect visual structure. People agreed with each other on only 78.3% of matches on average; the learned model agreed with them on 68.7% (77.7% under a nearest-neighbour measure) on held-out data - [Flexible Tree Matching, Sections 8 and 9](https://www.timroughgarden.org/papers/ijcai11.pdf)
- [Preprint of PR] The original algorithm does not scale: it took an hour on a toy example of 58 nodes, and each Metropolis iteration costs O(N^4) in the worst case - [SFTM, Sections 3.3 and 5.1](https://arxiv.org/abs/2004.12821)

#### SFTM
- [PR] Citation: Brisset, Rouvoy, Seinturier, Pawlak, "SFTM: Fast matching of web pages using Similarity-based Flexible Tree Matching", Information Systems 112, 2023, article 102126, https://doi.org/10.1016/j.is.2022.102126. The preprint is "SFTM: Fast Comparison of Web Documents using Similarity-based Flexible Tree Matching" - [arXiv 2004.12821](https://arxiv.org/abs/2004.12821); [dblp record](https://dblp.org/rec/journals/is/BrissetRSP23.html)
- [Preprint of PR] Step 1, node similarity. Each node becomes a set of tokens: its tag, its attribute names, the words of its attribute values and its XPath. An inverted index maps each token to the nodes of the first tree that carry it. A token's weight is IDF(t) = log(N / number of nodes with t), and the similarity S0(n, m) is the sum of the weights of the tokens the two nodes share. Tokens carried by more than f(N) nodes are dropped; the evaluation uses f(N) = sqrt(N) - [SFTM, Sections 4.1.1, 4.2.1 and 4.2.2](https://arxiv.org/abs/2004.12821)
- [Preprint of PR] Step 2, propagation. The score of a pair is raised by the similarity of its ancestors: Sp(n, m) is the sum over i from 0 to p of w_i x S0(i-th parent of n, i-th parent of m). Only pairs with non-zero S0 are scored - [SFTM, Section 4.1.2](https://arxiv.org/abs/2004.12821)
- [Preprint of PR] Step 3, matching. An edge exists only where the score is non-zero. Its cost is 1 / (1 + Sp), and "no match" costs w_n. The Metropolis search then looks for a low-cost one-to-one matching, with the objective exp(-beta x cost / size). Costs are never recomputed during the search, which is the main saving over the original algorithm - [SFTM, Sections 4.1.3 and 4.2.4](https://arxiv.org/abs/2004.12821)
- [Preprint of PR] Cost: O(N x f(N) x log N), dominated by sorting the edges. Measured running time fitted n log n with r^2 = 86%. Raising the token limit from N^0.5 to N^0.8 made the computation more than 60 times longer for a 3.5% gain in accuracy - [SFTM, Sections 4.3 and 5.2, Figures 8 and 9](https://arxiv.org/abs/2004.12821)
- [Preprint of PR] Evaluation: home pages of the Alexa top 1,000 sites, each with 10 mutants in which 0 to 50% of nodes were changed, 7,502 pairs in all. The mutations were structural (remove, duplicate, wrap, unwrap, swap), on attributes (remove, remove words) and on content (replace text, change letters, remove, remove words). APTED was run on 852 pairs. The parameter study used 53 pairs with 1,065 nodes on average. The paper gives no values for p, w_i, w_n, beta, gamma or the number of iterations, and no per-mutation breakdown - [SFTM, Section 5](https://arxiv.org/abs/2004.12821)
- [Preprint of PR] Stated limits: only home pages; synthetic mutations may not reflect real changes; the method relies on labels that tell nodes apart, meaning many attributes per element - [SFTM, Sections 6 and 7](https://arxiv.org/abs/2004.12821)
- [Code] Implementations by the first author exist on GitHub (`lssol/sftm_tree_matching`, 5 stars, and others), last pushed in late 2024 - [sftm_tree_matching repository](https://github.com/lssol/sftm_tree_matching)

#### Erratum (locator repair with SFTM)
- [PR] Citation: Brisset, Rouvoy, Seinturier, Pawlak, "Erratum: Leveraging Flexible Tree Matching to Repair Broken Locators in Web Automation Scripts", Information and Software Technology, 2022 - [arXiv 2106.04916](https://arxiv.org/abs/2106.04916)
- [Preprint of PR] Erratum matches the whole old page against the whole new page with SFTM and then looks up each broken locator's element in the matching, so all locators of a page are repaired by one matching - [Erratum, Sections 4.1 and 4.3](https://arxiv.org/abs/2106.04916)
- [Preprint of PR] Mutation dataset (650 URLs, 3,291 version pairs, 49,305 located elements): Erratum 87.0% correct, 9.0% mismatched, 4.0% no match; WATER 42.1% correct, 54.4% mismatched, 3.5% no match. Wayback dataset (64 URLs, 2,314 pairs 7 to 360 days apart, 34,421 elements, a labelled sample of 366 disagreements): Erratum 78.3% and WATER 51.9%, both within 5 points. The average page had about 1,500 nodes - [Erratum, Tables 1, 3, 4 and 5](https://arxiv.org/abs/2106.04916)
- [Preprint of PR] Erratum was "almost exclusively sensitive to structural mutations", barely sensitive to attribute mutations, and not sensitive to content mutations because it ignores node content by default. Its mismatches rise when the structure changes heavily. WATER's accuracy fell as pages grew, because more elements share a tag - [Erratum, Section 6.1, Figures 9 to 12](https://arxiv.org/abs/2106.04916)
- [Preprint of PR] The authors treat "no match" as better than a mismatch, because it warns the developer. WATER is faster for a single element, but its time grows with the number of locators while Erratum's stays flat; Erratum is faster from about 3 locators per page. No absolute times are given in the text - [Erratum, Sections 6.1 and 6.2](https://arxiv.org/abs/2106.04916)

### Inferences
- SFTM is the only published method here that was measured on wrapper insertions in real DOM trees ("wrap" and "unwrap" are among its mutations), but the papers do not report accuracy per mutation, so the effect of a wrapper alone is unknown. Erratum's finding that structure is its main source of error suggests that label-driven matching does not make structural change harmless.
- SFTM fits onionskin badly as it stands. Its strength comes from attribute tokens, which onionskin does not capture; with tag and path alone, almost every token is either too common (dropped by the sqrt(N) rule) or changes with the wrapper (the path). It also has six or more parameters without published values and a random search, which makes results hard to explain and to reproduce in a test tool.
- Two ideas transfer well. First, an inverted index from token to nodes with a rarity cut-off gives candidate pairs in near-linear time without comparing all pairs. Second, IDF weighting says in one formula what the locator studies found by hand: a token that few elements carry (an id, a test id, a rare class, a distinctive text) is strong evidence, and a common one (the tag `div`) is weak.
- The 78.3% agreement between people in the Bricolage study is a ceiling for any accuracy claim when designs differ a lot. For two versions of the same page the truth is better defined, but a matcher's score on a hand-labelled set should still be read with the labelling noise in mind.
- Borrow: IDF-weighted token overlap as a second pass for elements left unmatched by the structural pass, restricted to pairs that share a rare token; the three-way result (correct, mismatch, no match) and the preference for no match. Avoid: Metropolis search, learned weights, and whole-page flexible matching as the first step.

### Gaps
- The Information Systems version of SFTM was not read; any XyDiff comparison and final parameter values in it are unconfirmed.
- Neither paper gives a table of running time by node count. The only concrete times are "less than a second" for YouTube and the fitted curve.
- Bricolage (CHI 2011) itself was not read; it is cited through the IJCAI paper.
- Erratum's volume and page numbers in Information and Software Technology were not checked.

## 5. Web element matching in testing research: which properties are weighted, and which are stable

### Takeaway
Every multi-attribute matcher in the testing literature trusts tag, id, name and visible text most and structural paths least, and the measurements agree: absolute paths lose 67 to 79% of elements between releases, while a weighted mix of 14 properties loses 12%, and an optimised mix about 1 to 4%. When weights are fitted to data, text, neighbour text, name, type and aria-label come out high and class comes out low or is dropped.

### Cited Findings

#### How fragile are paths?
- [PR] Leotta, Stocco, Ricca, Tonella, "Using Multi-Locators to Increase the Robustness of Web Test Cases", ICST 2015, https://doi.org/10.1109/ICST.2015.7102611. Over six applications and 675 target elements, each with a later release, the share of broken locators was: absolute XPath 67% (449), id-relative XPath 49% (331), Montoto 22% (151), Selenium IDE 16% (107), ROBULA+ 12% (78). A weighted vote over the five broke 8% (55); the best possible combination would break 7% (46). In three of the six applications every absolute XPath broke - [Leotta et al. 2015, Table II](https://sepl.dibris.unige.it/publications/2015-leotta-ICST.pdf)
- [PR] ROBULA+ cut locator fragility by 90% against absolute XPaths and by 63% against Selenium IDE locators - [Leotta et al., J. Softw. Evol. Process 2016](https://doi.org/10.1002/smr.1771), as recorded in the earlier onionskin notes
- [PR] Nass, Alégroth, Feldt, Leotta, Ricca, "Similarity-based Web Element Localization for Robust Test Automation", ACM TOSEM 32(3), 2023, https://doi.org/10.1145/3571855. On 598 elements from the home pages of 40 popular sites, with the old version 12 to 60 months older than the new one, the share of elements not found was: absolute XPath 79%, id-relative XPath 59%, Selenium IDE 47%, Montoto 46%, ROBULA+ 35%, the best case of the multi-locator 24%, Similo 12% (72 of 598) - [Similo, arXiv 2208.00677, Table 5](https://arxiv.org/abs/2208.00677)
- [PR, Blog] Hammoudi, Rothermel and Tonella found that locators caused over 73% of record-and-replay test breakages, and attribute-based locators (id, name) caused more of them than structural ones; the base rate of each locator kind is not known - [Colyer's summary of Hammoudi et al., ICST 2016](https://blog.acolyer.org/2016/05/30/why-do-recordreplay-tests-of-web-applications-break/)
- [PR] In Vista's benchmark, locators caused 74% of breakages. Of 733 breakages, 695 were "non-selection" (the locator found nothing) and 38 were "mis-selection" (the locator found a different element), which is the more dangerous kind because the test goes on with the wrong element - [Stocco, Yandrapally, Mesbah, FSE 2018, Section 2](https://people.ece.ubc.ca/amesbah/resources/papers/fse18-vista.pdf)

#### WebDiff, CrossCheck, X-PERT, GWALI, WATER
- [PR, via search summary] WebDiff (Roy Choudhary, Versee, Orso, ICSM 2010, https://doi.org/10.1109/ICSM.2010.5609723) records for every DOM node its tag name, id, XPath, coordinates, clickability, visibility, z-index and a hash of its text. Its match index works like this: two nodes with the same defined id match; nodes with different tag names score zero; otherwise the score is a weighted sum of rho1, one minus the normalised Levenshtein distance between the two XPaths, and rho2, from the other properties, with rho1 weighted "considerably more" because matching nodes should have the same or a very similar XPath. The exact weights and threshold were not confirmed from the paper - [WebDiff record](https://doi.org/10.1109/ICSM.2010.5609723)
- [PR] GWALI reused WebDiff's matching between a page and its translation, where frameworks add tags, and found it "close to perfect" on its subjects - [Alameer et al., ICST 2016](https://viterbi-web.usc.edu/~halfond/papers/alameer16icst.pdf), as recorded in the earlier onionskin notes
- [PR] WATER (Choudhary, Zhao, Versee, Orso, "WATER: Web Application TEst Repair", ETSE 2011, https://doi.org/10.1145/2002931.2002935) first looks for an element with exactly the same id, XPath, class, link text or name. If none exists it ranks elements with the same tag by XPath Levenshtein similarity, weighted 0.9, plus coordinates, clickability, visibility, z-index and text hash - [Xu et al., arXiv 2312.05778, Section 4.3 and Table 3](https://arxiv.org/abs/2312.05778); [Erratum, Section 5.1](https://arxiv.org/abs/2106.04916)
- [PR] WATER's measured accuracy: 57% of 733 breakages (Vista study), 58% of 139 broken statements (Xu et al.), 42.1% on synthetic and 51.9% on real page pairs (Erratum). It never detected a mis-selection - [Vista, Section 5](https://people.ece.ubc.ca/amesbah/resources/papers/fse18-vista.pdf); [Xu et al., Table 5](https://arxiv.org/abs/2312.05778); [Erratum, Tables 3 and 5](https://arxiv.org/abs/2106.04916)

#### Vista and COLOR
- [PR] Vista (Stocco, Yandrapally, Mesbah, "Visual Web Test Repair", ESEC/FSE 2018) finds the element by its appearance: a screenshot of the element from the working version is searched for in the new page with SIFT and FAST feature detection followed by Fast Normalized Cross Correlation template matching and a visual filter. It repaired 592 of 733 breakages (81%) against 420 (57%) for WATER, found 80% of mis-selections where WATER found none, and found 33% of elements that had moved to a neighbouring page. Both tools were right in 56% of cases, and WATER was about 7% faster in one of the paper's two timing comparisons. The code was last pushed in 2018 - [Vista paper, Sections 3 and 5](https://people.ece.ubc.ca/amesbah/resources/papers/fse18-vista.pdf); [Vista repository](https://github.com/saltlab/vista)
- [PR] COLOR (Kirinuki, Tanno, Natsukawa, "COLOR: Correct Locator Recommender for Broken Test Scripts using Various Clues in Web Application", SANER 2019, pp. 310-320, https://doi.org/10.1109/SANER.2019.8667976; the assignment gave ICST 2019, but the record is SANER) combines attributes, texts, images and positions. The authors measured how reliable each property was across two releases and used that reliability as its weight. It put the right locator first in 77 to 93% of cases on four open-source applications and was more robust to layout change than structure-based repair (abstract via search summary; the paper is not open access, so the per-property reliabilities are unconfirmed) - [COLOR record](https://doi.org/10.1109/SANER.2019.8667976)
- [PR] An industrial replication of COLOR (Taha, Papadakis, Muller, ICPC 2026 RENE track, https://doi.org/10.1145/3794763.3798173) covered 4,471 test executions over 133 CI days. Locator breakage and visibility problems caused most instability, and the top recommendation was correct "in most cases". The named limits were missing element data, dynamically generated locators, and sparse or volatile HTML attributes - [ICPC 2026 listing](https://conf.researchr.org/details/icpc-2026/icpc-2026-replications-and-negative-results--rene-/5/Industrial-Replication-of-COLOR-Locator-Repair-in-Continuous-Integration-and-Failure-Patterns-under-UI-DOM-Evolution)

#### Similo, VON Similo and their replication
- [PR] Similo compares 14 properties of the wanted element with every candidate in the new page, multiplies each result (0 to 1) by a weight and adds them up. Weight 1.5: tag, id and name (exact match, case ignored), visible text (normalised Levenshtein; built from text, value or placeholder) and neighbour texts (share of common words). Weight 0.5: class, href, alt, absolute XPath and id-relative XPath (all normalised Levenshtein), is-button (exact), location (1 at the same spot, falling to 0 at 100 px), area and shape (width x height and width / height). The weights were set by hand: all started at 1, and the properties judged more stable and more unique, partly on COLOR's findings, were raised - [Similo, arXiv 2208.00677, Sections 3.1 and 3.2, Figure 4](https://arxiv.org/abs/2208.00677)
- [PR] Similo takes 2.96 ms per wanted element on one thread, and 0.01 to 0.02 ms per comparison of two elements. It always returns its best candidate, even when the element is gone; the authors call choosing a rejection threshold "non-trivial" - [Similo, Sections 5.2 and 6, Table 8](https://arxiv.org/abs/2208.00677)
- [PR] VON Similo (Nass, Alégroth, Feldt, Coppola, "Robust web element identification for evolving applications by considering visual overlaps", ICST 2023) treats DOM nodes that cover the same screen area as one visual element: two nodes are equivalent when the ratio of the intersection to the union of their boxes is above 0.85 and the centre of one lies inside the other. Each property's score is the best over all pairs of nodes from the two groups. On 1,163 matching and 1,163 non-matching pairs from 33 sites, accuracy was 94.1% (threshold 0.40) against 82.3% for Similo (threshold 0.28); the abstract gives 94.7% and 83.8% - [VON Similo, arXiv 2301.03863, Sections III and V](https://arxiv.org/abs/2301.03863)
- [PR] Kluge and Stocco, "Web Element Relocalization in Evolving Web Applications: A Comparative Analysis and Extension Study", Empirical Software Engineering (venue per the authors; arXiv May 2025). They rebuilt both algorithms and made a larger benchmark: the home pages of 30 applications in 16 versions from September 2018 to September 2023, four months apart, with 10,376 element pairs, of which about 2,011 had a broken locator. On the pairs with broken locators Similo found 95.8%, VON Similo 83.9%, and their tuned Similo++ and HybridSimilo 98.8% - [Kluge and Stocco, arXiv 2505.16424, Section 4.2.4 and Table 2](https://arxiv.org/abs/2505.16424)
- [PR] They added three properties (type, aria-label, and the full attribute map) and searched weights in steps of 0.05 between 0 and 3. Across four fitted configurations: visible text got 2.5 to 2.95, name 1.7 to 2.9, type 1.1 to 2.85, attributes 1.0 to 2.5, location 1.2 to 2.15, neighbour text 1.0 to 2.3, aria-label 0.9 to 2.95. Id varied widely (0.5 to 2.85), as did tag (0.8 to 2.35). Absolute XPath stayed low (0.05 to 1.05). Class was dropped once and is-button twice. The search is random and reaches different optima - [Kluge and Stocco, Table 3 and Section 5.3](https://arxiv.org/abs/2505.16424)
- [PR] Measured stability for the two added properties: `type` appears on 12% of elements and is unchanged in 96% of pairs; `aria-label` appears on 16% and is unchanged in 82%. The authors "observed a correlation between property stability and optimal weights". No stability figures are given for the original 14 - [Kluge and Stocco, Sections 4.3.1 and 8](https://arxiv.org/abs/2505.16424)
- [PR] Reported failure modes of similarity matching: the element changes tag (button to span) or text; a new element takes the old element's position and wins on location; similar icons swap places; with visual overlap, any node of the overlapping group may be returned; and a wrong match is always returned and only shows up later in the test - [Kluge and Stocco, Sections 2.3, 3.4 and 6](https://arxiv.org/abs/2505.16424)
- [PR] A later study by Nass and colleagues on ranking approaches reports up to 88.4% probability of ranking the right element first with learning-to-rank, and examines sensitivity to the weights (Journal of Systems and Software, 2025; via search summary, unconfirmed) - [Chalmers record](https://research.chalmers.se/en/publication/544187)

#### Properties and weights side by side

|---|---|---|---|
| WebDiff, WATER | same id (decides alone); same tag (required) | coordinates, visible, clickable, z-index, text hash | XPath edit distance, the dominant term (0.9 in WATER) |
| COLOR | attributes, text, image and position, each weighted by its measured reliability across two releases (values not seen) | not known | not used as the main clue |
| Similo | tag, id, name, visible text, neighbour text (1.5) | class, href, alt, is-button, location, area, shape (0.5) | absolute and id-relative XPath (0.5) |
| Similo++ (fitted) | visible text, name, type, attributes, aria-label, location | class and is-button (often dropped) | absolute XPath 0.05 to 1.05 |

| Vista | appearance of the element (image) | | none |
| StyleProof | id, data-testid, first token of data-style; tag plus own text when unique | tag, box and own-text length for re-nested elements | path with child positions |

### Inferences
- The ranking of signals that the evidence supports, strongest first: a developer key or an id that is unique in both versions; name, type and aria-label where present; the element's own visible text; tag (close to a hard requirement, though tags do change); text of neighbours; position and size; class; structural path. Absolute paths are the weakest signal measured in every study, and onionskin's current key is an absolute path.
- Ids are strong when present and unchanged, but they vary: the fitted weights for id range from 0.5 to 2.85, and id-relative XPaths broke for 49 to 59% of elements. An id should decide a match only when it is unique on both sides; a missing or generated id should not count against a pair.
- Class is a poor matching signal. This suits onionskin: CSS refactors rename classes (to utility classes, CSS modules, hashed names), and those are exactly the changes onionskin is meant to check.
- VON Similo's overlap rule is directly useful for wrappers. A wrapper that adds no padding has the same box as its only child, so the pair passes the 0.85 overlap test. The rule also explains a trap: after a wrapper is added, the old element has two nodes in the new page with almost the same box, and a geometry-based matcher may pick the wrapper.
- Per-element similarity search does not scale to matching every element. At Similo's 0.01 to 0.02 ms per comparison, 6,000 x 6,000 comparisons take 6 to 12 minutes on one thread. A whole-page matcher must first cut the candidates down by tree structure or by shared rare tokens.
- Borrow: Similo's property list as the checklist of what the capture could record (tag, id, name, type, aria-label, own text, a few attributes); a hard tag requirement with a reported exception ("retagged"); WATER's and StyleProof's order of exact evidence first and similarity second. Avoid: XPath edit distance as the main term (WebDiff, WATER), hand-set weights presented as facts, and a matcher that always returns its best guess.

### Gaps
- X-PERT's and CrossCheck's node matching was not read first-hand; the open copies returned 404 or 403. WebDiff's exact weights and threshold are unconfirmed.
- COLOR's per-property reliability numbers, the most direct published measurement of property stability, sit behind a paywall and were not seen.
- No study reports, for a large sample of element pairs, how often each of id, class, name, text and tag changes between versions. Kluge and Stocco give figures for type and aria-label only.
- All Similo-family benchmarks use home pages from the Internet Archive 4 to 60 months apart. That is far more change than the before-and-after of one pull request, so the absolute accuracy figures are pessimistic for onionskin's use, by an unknown amount.

## 6. Embeddings and language models for re-identifying elements (2023 to 2026)

### Takeaway
Published work uses a language model as a second judge over the top candidates of a cheap matcher, not as the matcher. GPT-4 raised VON Similo from 91.3% to 95.0% at about 2 seconds and 4.5 cents per element; a later tuned non-LLM variant reached about the same accuracy, so a simple method gives up a few points at most. No peer-reviewed study of embedding-based matching across page versions was found.

### Cited Findings
- [PR] Nass, Alégroth, Feldt, "Improving Web Element Localization by Using a Large Language Model", Software Testing, Verification and Reliability, 2024 (venue per the Chalmers record). VON Similo ranks the candidates, the top ten go to GPT-4 as JSON with 13 properties each, and the model returns the id of the best one. On 804 element pairs from 48 applications with versions 12 to 60 months apart: VON Similo found 734 (91.3%) at 29 ms each; with GPT-4, 764 (95.0%) at 1,934 ms each and 35.86 US dollars in total, about 0.045 dollars per element. The model fixed 40 cases and broke 10. In 13 cases the right element was not in the top ten - [arXiv 2310.02046, Sections IV to VIII, Table IV](https://arxiv.org/abs/2310.02046); [Chalmers record](https://research.chalmers.se/en/publication/542478)
- [PR] Kluge and Stocco's HybridSimilo, with no language model, reached 95.51% on the same benchmark under the comparable measure, slightly above the 95.0% of the GPT-4 variant. They did not re-run the GPT-4 variant, because it depends on a proprietary API with unknown settings - [arXiv 2505.16424, Sections 3.3 and 5.4](https://arxiv.org/abs/2505.16424)
- [Preprint] Xu, Li, Tan, "Guiding ChatGPT to Fix Web UI Tests via Explanation-Consistency Checking" (arXiv, January 2024; a later version is listed at ICST 2025 as "Understanding and Enhancing Attribute Prioritization in Fixing Broken Web UI Tests", link between the two unconfirmed). On 139 broken statements from 5 open-source applications, matching accuracy was: Vista 68, with ChatGPT 97; WATER 81, with ChatGPT 86; XPath edit distance alone 43, with ChatGPT 122 (88%). The model was gpt-3.5-turbo, given at most 10 candidates; the whole study cost 10.96 US dollars over 8,429 requests, and results are the best of four runs. With 10 candidates, XPath edit distance contained the right element 90.1% of the time - [arXiv 2312.05778, Sections 5 and 6, Tables 4 and 5](https://arxiv.org/abs/2312.05778)
- [Preprint] The same study checked the model's explanations. The model mentioned XPath 1,653 times and text 1,492 times; 51% of the XPath mentions were consistent with the data against 80% of the text mentions. The authors conclude that putting text before XPath may give more accurate matching - [arXiv 2312.05778, Section 8, Table 6](https://arxiv.org/abs/2312.05778)
- [Thesis] A University of Helsinki master's thesis on self-healing Robot Framework tests found that larger models repaired most: GPT-4 Turbo and Mistral Large repaired 87.5% of the repairable locators (via search summary, unconfirmed) - [Helsinki thesis](https://helda.helsinki.fi/server/api/core/bitstreams/631b961a-8642-42ed-9826-3e196eac9cf7/content)
- [Preprint] A March 2026 preprint argues against per-run model calls on cost grounds and re-derives broken selectors from the accessibility tree with a fixed ten-level order (role, test id, ARIA label, class fragments, text). Its evidence is thin: one demo site, 31 test combinations, one author - [arXiv 2603.20358](https://arxiv.org/abs/2603.20358)
- [Preprint] A May 2026 industrial case study of a multi-agent test system reports that 38% of 300 runs produced no runnable test, that repairs converged for 70% of scenario families after 3.4 rounds on average, and that agents weakened assertions or deleted tests to make runs pass - [arXiv 2605.01471](https://arxiv.org/abs/2605.01471)
- [Preprint] ReproBreak (May 2026) is a dataset of 449 reproducible locator breaks from Cypress and Playwright projects, mined from 359 repositories. It could serve as test data for a matcher - [arXiv 2605.12158](https://arxiv.org/abs/2605.12158)

### Inferences
- What a simple method gives up: on the hardest public benchmark (versions years apart), about 4 points between a hand-weighted similarity (91%) and the same with GPT-4 (95%), and nothing once the weights are fitted (95.5%). For a before-and-after pair from one change the gap should be smaller still.
- The model's gain came from "context awareness" and meaning (for example, a renamed label that means the same), which are exactly the cases where a text or tag changed. A dependency-free matcher cannot do this; it should report such elements as unmatched and let the developer supply a key.
- The pattern "cheap matcher proposes ten candidates, a stronger judge picks" is sound and worth keeping as a shape: onionskin can return the runners-up for an uncertain pair so that a person, or an outside tool, can decide.
- Avoid for onionskin: any model call inside the diff. It adds cost, seconds per element, a network dependency and results that change between runs, in a tool whose value is a deterministic verdict. The case study above shows the failure mode of letting an agent "repair" until green.

### Gaps
- No peer-reviewed paper was found that matches elements across versions with learned embeddings (MarkupLM-style encoders or siamese networks) and reports accuracy. The search turned up vendor pages and blog posts only.
- No study uses a 2025 or 2026 model on the Similo benchmarks, so the current size of the gap is unknown.
- The Helsinki thesis was not read; its figure comes from a search summary.

## 7. Matching on rendered properties: box geometry, computed style and text

### Takeaway
Boxes and text can rescue a pairing when the tree shape changed, and StyleProof does this in production, but only as a last step among elements left unpaired, only when the signature is unique, and with text and geometry kept out of the reported findings. Computed style is not used as a matching signal by any tool surveyed. The risk for onionskin is circular: a signal that is also the thing being diffed pulls the matcher towards pairs that did not change.

### Cited Findings
- [Docs] StyleProof (last push 2026-11-11, 3 stars) keys elements by a structural path with `nth-child` positions. In version 6.2.2 a wrapper "re-keyed the button's structural path", the element showed up as an advisory remove plus add, and a real colour change on it "vanished" from the certified diff. A later release pairs such elements back - [StyleProof re-nesting proof](https://github.com/BenSheridanEdwards/StyleProof/blob/main/docs/proof/re-nesting/README.md)
- [Docs] The pairing order in StyleProof: first correct for shifted `nth-child` positions, then "geometry among one-sided elements". A re-nested element is paired "by tag, rect, and own-text length, whether or not the paths share an ancestor". Ambiguous signatures and elements whose hashed identity (`id`, `data-testid`, `data-style`) was replaced "stay one-sided and fail closed". A change that only adds a wrapper still certifies as no reviewable change - [StyleProof CHANGELOG, entry for #472](https://github.com/BenSheridanEdwards/StyleProof/blob/main/CHANGELOG.md)
- [Docs] StyleProof also pairs by text. When both captures recorded own text, "an element whose tag and own text are unique on both sides is paired by that identity first", so a sibling inserted into a group, or a group moved into a new wrapper, pairs each element with itself and not with its neighbour by position. Ancestors pair only when every identified descendant agrees on one destination, and ambiguous text stays unpaired. The text "is compared in memory for this pairing only; it never becomes a finding in the certification diff". Captures without text "stay positional for pairing" - [StyleProof REFERENCE](https://github.com/BenSheridanEdwards/StyleProof/blob/main/docs/REFERENCE.md)
- [Docs, Code] sosie uses no rendered property for matching. Its subtree hash covers tags and shape only, and ties are broken by parent and sibling position. Bounds, styles and text are compared after matching, exactly: "No approximations in comparison", "no fuzzy matching". The matcher is "designed to err on the side of reporting diffs", and unmatched nodes are reported, "not silently dropped" - [sosie design doc](https://github.com/cuihtlauac/sosie/blob/main/sosie-design.md); [gumtree.ml](https://github.com/cuihtlauac/sosie/blob/main/lib/gumtree.ml)
- [PR] Similo scores location (full score at the same spot, none beyond 100 px), area and shape, each at the low weight of 0.5, on COLOR's finding that elements tend to keep their place and size. When weights were fitted to data, location rose to between 1.2 and 2.15 - [Similo, Section 3.2](https://arxiv.org/abs/2208.00677); [Kluge and Stocco, Table 3](https://arxiv.org/abs/2505.16424)
- [PR] The reported downside of position: a new element placed where the old one was can win on visual similarity over the true element that moved, and similar icons that swap places are often confused - [Kluge and Stocco, Section 6](https://arxiv.org/abs/2505.16424)
- [PR] WebDiff and WATER carry coordinates, visibility, z-index and a text hash as minor terms beside the XPath distance - [Xu et al., Table 3](https://arxiv.org/abs/2312.05778)
- [PR] Vista matches on appearance alone and beat the DOM-based WATER by 81% to 57%, including 80% of the mis-selections that WATER never noticed. A purely visual match needs screenshots and computer-vision code - [Vista, Section 5](https://people.ece.ubc.ca/amesbah/resources/papers/fse18-vista.pdf)
- [PR] VON Similo defines when two nodes are the same thing on screen: box intersection over union above 0.85 and one centre inside the other box - [VON Similo, Section III](https://arxiv.org/abs/2301.03863)
- [Docs] Playwright deprecated its layout-based selectors and warns that matching by layout can give unexpected results - [Playwright, other locators](https://playwright.dev/docs/other-locators), as recorded in the earlier onionskin report

### Inferences
- The circularity risk has two forms. If boxes or styles add to a match score, a real change lowers the score of the true pair, and the element is either left unpaired (reported as removed and added, which hides the property change in noise, the failure StyleProof documented) or paired with a look-alike neighbour (a wrong pair, which can report a change that did not happen or hide one that did).
- Exact geometry as a fallback is safer than it sounds for onionskin's main use, checking that a refactor changed nothing visible. A pair made because tag and box are equal cannot hide a box change, and its style differences are still reported. If the box did change, the element stays unpaired and is reported, which errs towards a false alarm. This matches sosie's rule that a spurious diff is tolerable and a missed one is not.
- The remaining risk of a geometry fallback is a swap: two elements with the same tag and size that traded places pair with each other's old position. If they also look the same, nothing visible changed and nothing is reported, which is acceptable. If they differ, the diff reports style changes where the truth is a move. A unique own text or key prevents this, which is why StyleProof tries text identity before geometry.
- A wrapper with no padding or border has the same box as its child. A geometry fallback must therefore also require the same tag, or prefer the deeper node, or the old element may pair with the new wrapper.
- Text is the safest rendered signal for onionskin, because onionskin does not diff text today. It fails on dynamic or translated content, so it should count only when the tag and text are unique on both sides.
- Computed style should stay out of matching. No surveyed tool uses it, most values repeat across many elements (onionskin's capture already stores each value once and refers to it by index), and style is the main thing the diff reports.
- Borrow from StyleProof: the order (keys, then text identity, then position correction, then geometry among leftovers), the uniqueness requirement at each step, and the rule that a replaced key forbids a pairing. Borrow from VON Similo: the overlap test as the definition of "same box" if a tolerance is wanted. Avoid: weighted sums that mix geometry with identity (Similo's design suits finding one element, not certifying a page), and geometry as a locator in general.

### Gaps
- X-PERT's and WebDiff's use of geometry in matching was not confirmed from the papers.
- No study measures how often geometry-based pairing is right or wrong after a markup change. StyleProof documents the rule and one worked example, not an accuracy figure.
- How sosie's and StyleProof's matchers behave on large real refactors is unreported; both tools have a handful of users.

## 8. Developer-supplied keys

### Takeaway
Tools agree on the mechanism: a dedicated attribute or id that is unique in the document decides the match before any heuristic runs, and a key present on one side forbids pairing with an element that has a different key. Playwright, StyleProof, GumTree, XyDiff, morphdom, idiomorph and React all work this way. No study was found that measures how long test ids survive; the evidence for their stability is documentation and indirect.

### Cited Findings
- [Docs] Playwright recommends locators in this order: role (with accessible name), text, label, placeholder, alt text, title, test id. It says CSS and XPath locators are "not recommended" because they "can be tied to the DOM structure or implementation" and break when it changes. `getByTestId` reads `data-testid` by default, and the attribute name can be changed with `testIdAttribute`. The page calls test ids "the most resilient way of testing" and notes they are not user-facing - [Playwright locators](https://playwright.dev/docs/locators)
- [Docs] A Playwright ARIA snapshot is a YAML form of the accessibility tree: each node has a role, an optional accessible name and attributes such as `[level=1]`. Matching is order-sensitive and can be partial, with regular expressions for names. The default child mode, `contain`, passes when the listed children are present in order; `equal` and `deep-equal` are stricter. The page does not say how generic wrapper elements are treated - [Playwright ARIA snapshots](https://playwright.dev/docs/aria-snapshots)
- [Docs] StyleProof treats `id`, `data-testid` and the first token of a developer-written `data-style` attribute as identities that are hashed into the element's semantic path. The first `data-style` token counts only "when it uniquely identifies a sibling"; later tokens stay free for state (`status ok` to `status warn`) without changing identity. When StyleProof corrects for shifted positions it keeps every such identity segment, so that it "cannot undo the identity boundary and compare two different semantic roles as a restyle" - [StyleProof REFERENCE](https://github.com/BenSheridanEdwards/StyleProof/blob/main/docs/REFERENCE.md); [StyleProof CHANGELOG, #472](https://github.com/BenSheridanEdwards/StyleProof/blob/main/CHANGELOG.md)
- [Code] sosie has no key step in its matcher. Its configuration can drop attributes such as `class`, `style` and `data-x-*` before comparison and can mask or drop subtrees chosen by tag, `#id` or `.class` - [sosie design doc](https://github.com/cuihtlauac/sosie/blob/main/sosie-design.md); [gumtree.ml](https://github.com/cuihtlauac/sosie/blob/main/lib/gumtree.ml)
- [Code] GumTree's `IdMatcher` pairs nodes whose id occurs exactly once in each tree and runs first in the `-id` matchers - [IdMatcher.java](https://github.com/GumTreeDiff/gumtree/blob/main/core/src/main/java/com/github/gumtreediff/matchers/heuristic/IdMatcher.java)
- [PR] XyDiff's first phase matches nodes by ID attribute, and a node with an id "must" match a node with the same id value or nothing. The authors note the running time drops when ids are used - [XyDiff paper, Sections 1 and 5](https://www.csd.uoc.gr/~hy561/Data/Papers/detecting.pdf)
- [Docs, Code] React keys must be stable and unique among siblings. morphdom uses `id` or a custom `getNodeKey`. idiomorph extends ids to ancestors through id sets - [React legacy docs](https://legacy.reactjs.org/docs/reconciliation.html); [morphdom source](https://github.com/patrick-steele-idem/morphdom/blob/master/src/morphdom.js); [idiomorph README](https://github.com/bigskysoftware/idiomorph)
- [PR] Indirect evidence on survival. XPaths anchored on the nearest id broke for 49% of elements across one release step and failed for 59% across 12 to 60 months. Where present, `type` was unchanged in 96% of pairs and `aria-label` in 82%. An industrial replication names "dynamically generated locators" and "sparse or volatile HTML attributes" as limits on repair - [Leotta et al. 2015, Table II](https://sepl.dibris.unige.it/publications/2015-leotta-ICST.pdf); [Similo, Table 5](https://arxiv.org/abs/2208.00677); [Kluge and Stocco, Section 4.3.1](https://arxiv.org/abs/2505.16424); [ICPC 2026 listing](https://conf.researchr.org/details/icpc-2026/icpc-2026-replications-and-negative-results--rene-/5/Industrial-Replication-of-COLOR-Locator-Repair-in-Continuous-Integration-and-Failure-Patterns-under-UI-DOM-Evolution)
- [Thesis] Althomali's thesis proposes developer-supplied element identifiers as the fix for matching problems in layout-graph comparison - [Althomali 2022](https://etheses.whiterose.ac.uk/31157/), as recorded in the earlier onionskin report

### Inferences
- A key rule that all these tools share and onionskin can adopt as is: a key value pairs two elements only if it occurs exactly once in each capture; an element with a key never pairs with an element that has a different key; duplicate keys fall through to the next step and are reported.
- The order of key attributes should be the developer's choice, with a default such as `data-testid`, then `id`. Generated ids (framework ids such as `:r1:` or hashed names) are common, so an id that is missing on the other side should demote the element to heuristic matching and not mark it as removed.
- Role plus accessible name is a good second-tier key where it is unique (a `button` named "Save"). Playwright ranks it first for tests, and `aria-label` was stable in 82% of pairs. It needs the capture to record role and name, which a script can read only in part without the browser's accessibility tree.
- Keys also anchor the unkeyed. With idiomorph's id sets or GumTree's container step, each keyed element identifies its ancestors, so a few keys on landmarks (header, nav, main, each card) go a long way.
- Borrow: Playwright's configurable test id attribute; StyleProof's first-token rule for attributes that also carry state; "replaced key forbids pairing". Avoid: keys unique only among siblings; treating class names as keys.

### Gaps
- No empirical study of how long `data-testid` or similar attributes survive across releases was found. Playwright's "most resilient" is a documentation claim. ReproBreak may allow such a study but its abstract gives no breakdown by locator type.
- Storybook was not researched. It names components and states, not elements, so it is likely out of scope, but this was not checked.
- How Playwright's ARIA snapshot treats role-less wrappers was not confirmed. If generic containers are left out of the accessibility tree, a snapshot would be unaffected by a new wrapper `div`; this is an inference only.

## 9. Evaluating a matching and reporting it to the user

### Takeaway
The literature separates three outcomes, correct pair, wrong pair and no pair, and treats a wrong pair as the worst, since it fails silently. The most useful reporting practices are to refuse to pair when the evidence is ambiguous, to say which rule made each pair, and to list unmatched nodes and structural changes as their own entries.

### Cited Findings
- [Preprint of PR] Erratum reports correct, mismatch and no-match rates separately and argues a no-match is preferable because it alerts the developer. In its labelled sample, most of Erratum's no-match answers were confirmed as correct by the labellers - [Erratum, Section 6.1, Table 3, Figure 12](https://arxiv.org/abs/2106.04916)
- [PR] Similo always returns a candidate, so a wrong match surfaces only later in the test. The follow-up work scores pairs between 0 and 1 and applies thresholds (0.28 for Similo, 0.40 for VON Similo, each tuned on its benchmark); the Similo library warns on low scores - [Similo, Section 6](https://arxiv.org/abs/2208.00677); [VON Similo, Section V](https://arxiv.org/abs/2301.03863); [Kluge and Stocco, Sections 2.3 and 3.5](https://arxiv.org/abs/2505.16424)
- [PR] Vista's taxonomy names the silent failure "mis-selection" and shows it is rare (38 of 733) but hard to detect - [Vista, Section 2](https://people.ece.ubc.ca/amesbah/resources/papers/fse18-vista.pdf)
- [PR] GumTree names its mappings by the phase that made them: anchor (identical subtree), container (shared descendants above a threshold) and recovery. Its own quality measures are the number of mappings and the size of the edit script, a proxy for the effort of reading a change - [ASE 2014, Sections 3 and 5](https://www.labri.fr/perso/xblanc/data/papers/ASE14.pdf)
- [PR] Edit-script size is an imperfect proxy: differential testing found inaccurate mappings in 20 to 36% of file revisions for three algorithms, confirmed by experts. In the ICSE 2024 user study, 90% of the smaller scripts were judged better, so smaller is usually but not always better - [Fan et al., arXiv 2103.00141](https://arxiv.org/abs/2103.00141); [ICSE 2024 slides](https://www.labri.fr/perso/falleri/img/slides/icse24.pdf)
- [PR] People disagree about matchings: 78.3% consistency between human matchers on pairs of different pages - [Flexible Tree Matching, Section 9](https://www.timroughgarden.org/papers/ijcai11.pdf)
- [Docs, Code] sosie's checks on its own matcher: every unmatched node is reported as `Extra_node`; a pair with different tags produces `Tag_mismatch`; wrappers and moves are informational diffs; the result must be injective, symmetric and ancestor-preserving, verified on all pairs of trees up to 5 nodes; and round-trip tests apply known changes (wrap, reorder, change text) to a tree and check that the matcher recovers the known pairing - [sosie design doc](https://github.com/cuihtlauac/sosie/blob/main/sosie-design.md); [gumtree.mli](https://github.com/cuihtlauac/sosie/blob/main/lib/gumtree.mli)
- [Docs] StyleProof fails closed: ambiguous signatures stay unpaired, a visible added or removed element needs review, and a report line names the element by path and class with the property's old and new value - [StyleProof CHANGELOG, #472](https://github.com/BenSheridanEdwards/StyleProof/blob/main/CHANGELOG.md); [StyleProof re-nesting proof](https://github.com/BenSheridanEdwards/StyleProof/blob/main/docs/proof/re-nesting/README.md)
- [Preprint] Asking for reasons helps check a match. Xu et al. test whether the reasons a model gives for a pair agree with the data, and found the agreement correlated with correct matching, strongly for WATER's candidates (r = 0.84) and moderately for Vista's and edit distance's (0.51 and 0.49). The GPT-4 study classified the model's reasons into context, meaning and plain comparison - [arXiv 2312.05778, Section 8](https://arxiv.org/abs/2312.05778); [arXiv 2310.02046, Section VI-C](https://arxiv.org/abs/2310.02046)
- [Preprint of PR] Synthetic mutation is the standard way to get ground truth: SFTM and Erratum mutate real pages (wrap, unwrap, remove, duplicate, swap, change attributes and text) and know the true pairing by construction. The authors warn that synthetic mutations may miss real changes - [SFTM, Sections 5.1 and 6](https://arxiv.org/abs/2004.12821)

### Inferences
- A confidence number is less useful to a developer than the rule that fired. A rule-based matcher can attach to each pair one of a few named reasons, in falling order of trust: same key; identical subtree; same position under paired parents; container with a stated share of paired descendants; unique tag and text; same tag and box. The share of paired descendants (GumTree's dice or Chawathe ratio) is the one natural score and can be shown as "412 of 430 descendants paired".
- What the diff should print about matching: counts of pairs per rule; the unpaired elements on each side, grouped by subtree so that one removed section is one line; wrappers added and removed; moves (paired elements whose parents are not paired with each other, XyDiff's definition); and any pair made by a fallback rule, flagged as such.
- When the unpaired share is high, the diff should say that the markup changed too much to compare, and not list thousands of removed and added elements. The threshold is a design choice with no published value.
- Tests onionskin can run on its own matcher without a browser, following sosie and SFTM: mutate a captured tree with known operations and check the pairing; check that a capture matched with itself pairs every node by the first rule; check symmetry and ancestor order; enumerate all small trees.
- Avoid: a single percentage as the verdict, silently dropping unpaired nodes, and "best guess" pairs that look like certain ones in the report.

### Gaps
- No user study was found on how developers read or trust element-matching explanations in visual or style diff tools.
- No published threshold says when a matching is too poor to report as a diff.
- Healenium's scoring and its default score cap could not be confirmed from primary documentation; secondary guides describe an LCS-based tree comparison with a score threshold near 0.5 (unconfirmed).

## 10. Complexity and engineering notes for 500 to 6,000 elements

### Takeaway
Hash-based subtree matching, key joins and child alignment under matched parents all run in linear or near-linear time and take milliseconds at 6,000 nodes; GumTree-style container matching is quadratic only in the worst case; exact edit distance and all-pairs similarity are the families to avoid. The known worst case for the fast family is a long run of identical subtrees.

### Cited Findings

| Family | Stated cost | Known worst case or limit | Source |
|---|---|---|---|
| Pair by key or id | one pass per tree | duplicates must be skipped | [IdMatcher.java](https://github.com/GumTreeDiff/gumtree/blob/main/core/src/main/java/com/github/gumtreediff/matchers/heuristic/IdMatcher.java) |
| React, morphdom (children of matched parents) | O(n), single pass | cannot follow a node to another parent; a new wrapper rebuilds the subtree | [React docs](https://legacy.reactjs.org/docs/reconciliation.html); [morphdom README](https://github.com/patrick-steele-idem/morphdom) |
| truediff (hash equality, no scores) | linear, proved | none stated in the sources read | [truediff paper](https://www.pl.informatik.uni-mainz.de/files/2021/06/truediff.pdf) |
| XyDiff (signatures, heaviest first) | O(n log n) | quality traded for speed | [XyDiff paper](https://www.csd.uoc.gr/~hy561/Data/Papers/detecting.pdf) |
| Chawathe et al., ChangeDistiller | O(ne + e^2) | quadratic when large subtrees move | [XyDiff paper, Section 3](https://www.csd.uoc.gr/~hy561/Data/Papers/detecting.pdf) |

### Inferences
- A design that fits the constraints (no dependencies, a few hundred lines, 500 to 6,000 elements), in the order of trust:
  1. Rebuild both trees from the captured paths. The node list is in document order, so its reverse visits children before parents. Give each node a signature made from its tag and its children's signatures, interned as small integers through a map so that equality is exact.
  2. Fast path: if the two roots have the same signature, the markup did not change. Pair every node by path, as today, and stop.
  3. Keys: pair elements whose key (test id, then id, as configured) occurs once in each capture.
  4. Identical subtrees: pair subtrees whose signature occurs once on each side, largest first, with all their descendants. For a signature that occurs the same number of times on both sides, pair the occurrences in document order, above a minimum height only. (GumTree instead ranks every pair in such a group by how well the parents match.) Leave other repeats for step 6.
  5. Containers: in post-order, pair an unpaired element with the unpaired element of the same tag that holds the largest share of its paired descendants, found by walking up from those descendants' partners, if the share passes GumTree simple's size-dependent threshold. Always pair the two roots.
  6. Children: under each pair, align the remaining children by a longest common subsequence on signature, then on tag, then pair children whose tag is unique among the leftovers on both sides.
  7. Optional fallbacks among leftovers, each requiring uniqueness on both sides: same tag and own text; same tag and box.
  8. Report: pairs by rule, unpaired nodes, wrappers, moves.
- Path equality must not be an early pairing rule once the shapes differ. After a wrapper is added, the wrapper has the path the old element had, often with the same tag, and pairing by path would pair the old element with the wrapper and mispair everything below it. Path is safe in step 2 and as a tie-breaker between candidates with equal signatures.
- A case to test: a section whose children are identical cards, all wrapped in one new `div`. No card signature is unique, so a matcher that only anchors unique signatures leaves the cards to the child-alignment rules, and those fail here: the wrapper is not identical to a card, and `div` is not unique among the leftovers. GumTree pairs such groups in its top-down phase by ranking all candidate pairs. The equal-count rule in step 4 is a cheaper way to the same result: it pairs the cards in order, and the section then finds its partner through them.
- Cost of this design: steps 1 to 4 and 6 are linear or n log n (the alignment in step 6 is quadratic in the number of leftover children of one parent, which is small except for very long lists). Step 5 touches each paired descendant once per unpaired ancestor, so it is bounded by nodes times depth, and DOM trees are shallow. Nothing compares all pairs. At 6,000 nodes this should take milliseconds to tens of milliseconds in Clojure; this is an estimate, with sosie's claimed 50 to 500 ms at 5,000 nodes as the only outside reference.
- The worst case to design for is repetition: a table of 1,000 identical rows, or hundreds of identical icon buttons. Pairing every identical subtree with every other, as GumTree's ambiguous step does, costs a million pairs for 1,000 items. Pairing repeated signatures in document order when the counts agree (step 4) keeps this linear and is also the natural answer: the i-th identical row is the i-th identical row. When the counts differ, the alignment in step 6 runs on one parent's children, and a long list should use a linear-space diff or a prefix and suffix trim first.
- A second worst case is a signature that is too weak. Without attributes or text, many different elements share the signature "empty div". `minHeight = 2` and the unique-on-both-sides rule limit the damage, but the real fix is to capture a little more per element. Key attributes can go into the signature. Own text is better used as a separate rule (step 7), because text inside the signature makes a text edit break identity for the element and all its ancestors.
- The capture has to change before matching can improve much: at minimum the configured key attributes and `id`, and for the text rule a hash or short form of the element's own text. Tag and child order are already in the path.
- Onionskin's diff output keys every change by `:path`. After matching, a change needs both paths (`:path` before and after) when they differ.

### Gaps
- No timing was measured for any of this in Clojure or ClojureScript; all speed statements for onionskin are estimates.
- truediff's and GumTree simple's worst cases were not found in the sources read.
- No benchmark of real before-and-after page pairs from CSS or component refactors exists in the literature surveyed. SFTM's mutated pages, Similo's archived home pages and ReproBreak's locator breaks are the nearest public data.
