# Prior art backs onionskin's design and names its risks

onionskin should be grounded in four bodies of work. Galen's spec language and Quixote's descriptor arithmetic show what developer-written layout expectations look like in practice. The responsive layout graph behind ReDeCheck, and the layout graphs from Halfond's group (GWALI, MFix), show how to turn measured boxes into relational facts and diff them between versions. Allen's interval algebra, the rectangle algebra and RCC-8 give relation definitions that are exact, exhaustive and consistent across granularities. The CSS refactoring papers of Mazinanian, Tsantalis and Mesbah, together with the 2026 tool sosie, show what "visually neutral" can and cannot mean. The evidence supports onionskin's core choice: relations between rendered boxes survive harmless changes that move absolute positions and pixels. X-PERT moved cross-browser testing from coordinates to relative layout, and pixel-perfect comparison marked more than 84% of the page as changed in WebSee's study. **Among the tools surveyed, no maintained one joins developer-written relation checks with fact diffs between versions.** Galen, the closest, last released in March 2019, and the two active computed-style diff tools (StyleProof and sosie) are a few months old and have no relation layer. The research also shows where the risk moves: most GUI test breakage comes from element locators and render timing, published tolerance constants change results noticeably, and a computed-style diff can only vouch for the pages, states, widths and browser engines it captured. One gap matters most. No study has measured whether relational layout assertions need fewer changes than exact ones; that benefit is inferred from oracle and locator research, not measured.

Peer-reviewed papers are named with their venue in the text (ICSE, ISSTA, TOSEM and so on). Tools, specifications, vendor documentation, theses, preprints and blog posts are labelled as such where they support a claim, and the reference list at the end groups every source by type. Tool maintenance data was checked on 2026-11-03.

## Among maintained tools, none joins relation checks with version diffs

**Galen** is the nearest prior art for the expectation side. Its spec language names objects by CSS, XPath or id locator and states relations between them: `near`, `left-of`, `above`, `inside` with the sides that must hold (`inside container 10px left right`), `aligned horizontally` or `vertically` by edge or centre with a tolerance, `centered`, sizes as absolute values or as a percentage of another object, `count`, `text` and `css` ([Galen spec guide](http://galenframework.com/docs/reference-galen-spec-language-guide/)). Ranges can be exact, `50 to 200 px`, one-sided or approximate (`~ 100 px`). The approximation is widened by a setting that the shipped template sets to 2 px and the docs show as 3 px ([Galen config template](https://github.com/galenframework/galen/blob/master/galen-core/src/main/resources/config-template.conf)). Tags such as `@on mobile` select checks per device. Version 2.4 (November 2018) added three ideas onionskin can reuse: a generator that writes relations from a page dump, a `mutate` command that shifts or resizes each object by a few pixels and reports the changes the spec failed to catch, and an HTML report that draws the measured distance for each check ([Galen 2.4 release post](http://galenframework.com/post/2018-11-03-released-version-2.4-spec-generator-and-mutation-testing/), author's blog). Galen has had **no release since 2.4.4 on 15 March 2019** and no commit since 10 March 2019, and it runs on Java and Selenium ([Galen releases](https://github.com/galenframework/galen/releases)). Its problems are on record. The Thoughtworks Radar placed it in Trial in 2016 and 2017 but noted the brittleness and slowness typical of end-to-end tests ([Thoughtworks Radar](https://www.thoughtworks.com/radar/tools/galen)). Its author, Ivan Shubin, advised against complete page specs, because specs of several hundred lines become unmaintainable and get thrown away; his remedy was short custom rules over groups of elements ([TestGuild podcast #144](https://testguild.com/podcast/144-automated-responsive-design-testing-using-galen-ivan-shubin/)), shipped in galen-extras as phrases such as "aligned horizontally next to each other with equal distance" ([galen-extras](https://github.com/galenframework/galen-extras)). Galen's own guide says to use `css` checks sparingly because they tie tests to CSS.

**Quixote**, by James Shore, expresses layout as arithmetic on descriptors: the edges, centre and size of an element, the viewport or the page, combined with `plus`, `minus`, `times` and `to` (the span between two edges). An assertion reads like `navbar.top.should.equal(logo.bottom.plus(10))` ([Quixote README](https://github.com/jamesshore/quixote)). Failure messages name the edge, the direction and size of the miss, and the descriptor the expected value came from: for example, that a navbar's top edge should be 13 px higher to match the header's bottom edge at 50 px. Values within a fixed **0.5 px** count as equal ([Quixote QElement docs](https://github.com/jamesshore/quixote/blob/release/docs/QElement.md)). Shore built it so that CSS could be refactored under unit tests that run in milliseconds, after judging screenshot tools such as BBC's Wraith slow and brittle, and Hardy's custom step syntax and Selenium dependency cumbersome ([Shore 2014](https://www.letscodejavascript.com/v3/blog/2014/09/announcing_quixote), blog post). Quixote has no relation layer (no inside, no overlaps), and its **last release, 1.0.1, is from April 2020** ([npm quixote](https://www.npmjs.com/package/quixote)).

Mobile test frameworks settled on similar vocabularies with sharper definitions. Android's Espresso splits each direction into completely and partially. Completely-left-of means A's right edge is at or before B's left edge, so touching passes and any overlap fails; partially-left-of means the boxes overlap and A starts first. Its edge alignment uses exact integer equality with no tolerance ([Espresso PositionAssertions](https://github.com/android/android-test/blob/main/espresso/core/java/androidx/test/espresso/assertion/PositionAssertions.java)). Jetpack Compose went the other way: its bounds assertions take a tolerance that defaults to **0.5 dp**, and the old overloads without one are deprecated ([Compose BoundsAssertions.kt](https://github.com/androidx/androidx/blob/androidx-main/compose/ui/ui-test/src/commonMain/kotlin/androidx/compose/ui/test/BoundsAssertions.kt)). On the web, cypress-layout-inspector offers leftOf, above, inside, aligned, overlapping and overflowing with a configurable threshold, but has been inactive since December 2022 ([cypress-layout-inspector](https://github.com/msmps/cypress-layout-inspector)). Playwright deprecated its layout selectors (`:left-of`, `:near` within 50 px) and warns that matching by layout can give unexpected results ([Playwright other locators](https://playwright.dev/docs/other-locators)). LinkedIn's LayoutTest-iOS lays a view out over generated data combinations and sizes and flags overlapping views without any spec ([LayoutTest-iOS](https://github.com/linkedin/LayoutTest-iOS)). jsdom-based matchers cannot help, because jsdom does no layout and returns dummy geometry ([jsdom README](https://github.com/jsdom/jsdom)).

On the comparison side, the 2013 to 2018 computed-style tools (Hardy, css-wrangler, computed-style-diff) are all unmaintained ([Hardy](https://github.com/thingsinjars/Hardy); [css-wrangler](https://github.com/moefinley/css-wrangler); [computed-style-diff](https://github.com/m3g4p0p/computed-style-diff)). Two 2026 tools now aim at onionskin's second use, showing that a refactor changed nothing visible. **StyleProof** (npm, Playwright, v9.0.0 on 29 October 2026, 3 GitHub stars) records resolved longhands, pseudo-elements, layout boxes and forced `:hover`, `:focus` and `:active` states for declared UI states at real breakpoint widths, on the base branch and on the pull request. Its certify mode fails on any difference and is meant for refactors that should change nothing, such as a move to Tailwind ([StyleProof README](https://github.com/BenSheridanEdwards/StyleProof)). Much of its machinery exists to bound what a green result means: it fails when a declared state was not captured, and its README says that StyleProof "certifies only what it captured". **sosie** (OCaml, opam 0.1.2 on 24 August 2026, 1 star) reads `getBoundingClientRect` and `getComputedStyle` from a real browser and compares two captures structurally ([sosie README](https://github.com/cuihtlauac/sosie)). Its design document ranks equivalence from semantic (the accessibility tree) through layout and layout plus visual properties (its target) to pixels. It treats the property whitelist as the explicit trust boundary, counts missed regressions as fatal and spurious diffs as tolerable, runs normalisation (bounds rounded to 0.5 px, canonical colours and fonts, masked text) as a pure snapshot-to-snapshot step, and matches the two trees with a simplified GumTree algorithm so that an added or removed wrapper element does not break the pairing ([sosie design doc](https://github.com/cuihtlauac/sosie/blob/main/sosie-design.md)). The design document lists about 20 whitelisted properties and the 0.1.2 API docs list 52, so the set is still moving ([sosie whitelist docs](https://ocaml.org/p/sosie/0.1.2/sosie.shared/Sosie_shared/Property_whitelist/index.html)). Neither tool has published reports from users.

Pixel tools all end up with the same three controls: a per-pixel colour threshold (0.2 in YIQ space by default in Playwright, 0.063 in Chromatic), a budget for how many pixels may differ, and selectors to hide or mask ([Playwright LocatorAssertions](https://playwright.dev/docs/api/class-locatorassertions); [Chromatic threshold docs](https://www.chromatic.com/docs/threshold/)). PhantomCSS recorded the lessons in its README before it was archived: full-page screenshots are a bad idea, because 2 px of footer padding failed 50 page tests, and anti-aliasing differs between machines ([PhantomCSS](https://github.com/HuddleEng/PhantomCSS)). The commercial Applitools "Layout" match level, which checks only that the relative positions of elements stay consistent, is the closest commercial analogue to onionskin's symbolic tier, but its algorithm is not published ([Applitools match levels](https://applitools.com/docs/eyes/concepts/best-practices/match-levels)).

**What onionskin should take from the tools.** Galen's relation list (directions with sides and distance, inside and partly inside, edge and centre alignment with tolerance, centred, relative size, count, presence) is a tested checklist, and each Galen line maps onto an EDN vector or map with no parser. Espresso's completely and partially split gives exact edge semantics. Quixote's descriptor arithmetic and failure messages suit the fine-grained tier. Galen 2.4 contributes fact generation from a capture, and mutation runs that show which elements a suite leaves unconstrained. sosie contributes the whitelist as a stated boundary, normalisation as a pure function, and wrapper-tolerant element matching; StyleProof contributes captured UI states and a loud report of what was not captured. **What it should avoid**: long page specs, dependence on a browser driver that can disappear (PhantomJS ended PhantomCSS), exact equality on fractional geometry, geometry as a way to find elements, and whole-page absolute positions, where one shift near the top changes every fact below it.

## Research moved from pixels to relation graphs that carry viewport ranges

Peer-reviewed work on layout failures started with screenshots and moved to relations. WebDiff (ICSM 2010) compared each element's screenshot region across browsers with colour histograms and a distance measure that ignores small shifts, after a second screenshot had found and neutralised changing content ([Roy Choudhary et al. 2010](https://doi.org/10.1109/ICSM.2010.5609723), as described in [Althomali 2022](https://etheses.whiterose.ac.uk/31157/), PhD thesis). CrossCheck (ICST 2012) trained a decision tree on features such as size ratio, displacement and element area ([Roy Choudhary et al. 2012](https://doi.org/10.1109/ICST.2012.97)). X-PERT (ICSE 2013) introduced the alignment graph: parent-child edges for containment, and sibling edges labelled with relative position (above, below, left, right) and shared edges, so that layout was compared as relations rather than coordinates ([Roy Choudhary et al. 2013](https://doi.org/10.1109/ICSE.2013.6606616); definition restated in [Walsh et al. 2020](https://doi.org/10.1002/stvr.1748)). The XFix tool paper, citing X-PERT's study, reports that layout issues are the most common kind of cross-browser issue, found on **over 56% of websites** ([Mahajan et al. 2017b](https://doi.org/10.1145/3092703.3098223)). XFix repaired them by searching for CSS that minimised a weighted sum of position, size and neighbour displacement, and resolved 86% of reported issues and 99% of those humans could see on 15 pages ([Mahajan et al. 2017a](https://doi.org/10.1145/3092703.3092726)). Browserbite took the opposite route, image processing without the DOM ([Saar et al. 2016](https://doi.org/10.1002/spe.2387)).

The Sheffield line of work (Walsh, McMinn, Kapfhammer, later Althomali) extended the alignment graph into the **responsive layout graph**, starting at ASE 2015 ([Walsh et al. 2015](https://doi.org/10.1109/ASE.2015.31)). Every node's visibility and every edge's set of relations carries the inclusive range of viewport widths where it holds, so one edge can record that one element is above another below 768 px and left of it from 768 px ([Walsh et al. 2020](https://doi.org/10.1002/stvr.1748)). Extraction samples widths and binary-searches between samples wherever a relation set changes. Of the sampling strategies compared, a uniform grid plus widths on both sides of every media-query breakpoint gave the best trade-off; the journal paper reports 80 px steps, while the tool paper and Althomali's thesis use 60 px ([Walsh et al. 2020](https://doi.org/10.1002/stvr.1748); [Walsh et al. 2017b](https://doi.org/10.1145/3092703.3098221)). In regression mode, nodes are matched by identical absolute XPath, and each mismatch is classed as a bounds difference (same relations, different width range), an attributes difference (same range, different relations) or both. On 15 real pages with seeded HTML and CSS changes, the method missed none of 60 mutants and raised one false positive. In a pool of 450 mutants, checking single widths missed 20 of 36 subtle changes that the range-based diff caught ([Walsh et al. 2020](https://doi.org/10.1002/stvr.1748)). Without any oracle, ReDeCheck looks for five failure signatures: element collision, an element protruding from its parent, an element protruding from the viewport, wrapping, and small-range layouts that hold only for a few pixels of width. It found failures in **16 of 26 production pages**, and 197 of its 328 reports were true positives ([Walsh et al. 2017a](https://doi.org/10.1145/3092703.3092712); counts from [Althomali et al. 2021](https://doi.org/10.1002/stvr.1756)).

The details matter as much as the idea. ReDeCheck's code treats edges as aligned within 3 px and a child as filling its parent within 5 px, counts boxes as overlapping only when the overlap exceeds 1 px on both axes, and drops elements smaller than 5 px. Its "above" holds when A's bottom is at or above B's vertical midpoint, a lenient reading; the strict edge-to-edge version is in the code but commented out ([ReDeCheck Sibling.java](https://github.com/redecheck/redecheck/blob/d3f2364960aa7398f7085a502576da70759f5ed0/src/main/java/shef/layout/Sibling.java)). Althomali's thesis warns that changing the tolerance can change the tool's output significantly, and that fractional coordinates force arbitrary choices ([Althomali 2022](https://etheses.whiterose.ac.uk/31157/)). Many reports were true of the DOM but invisible on screen. In one manual classification about 70% were non-observable, for example elements protruding invisibly from their container, although the thesis gives inconsistent counts for that study. The follow-up tool Viser (ICST 2019) checks each report against the screen by changing element opacity and comparing pixels in the affected area, and agreed with human judgement in **86.3%** of cases ([Althomali et al. 2019](https://doi.org/10.1109/ICST.2019.00027), figures from the thesis). Layout DR (ICST 2022) then repairs failures by copying layout rules from a neighbouring failure-free width ([Althomali et al. 2022](https://doi.org/10.1109/ICST53961.2022.00025)). The thesis also lists the model's weak points: it takes the tightest enclosing box as an element's container, which fails for fixed and floating elements, and it cannot follow JavaScript that changes elements. The authors propose developer-supplied element identifiers as the fix.

Halfond's group at USC built similar graphs for other kinds of failure. GWALI (ICST 2016) compares a page with its translation using a complete graph over element boxes and separate text boxes, labelled with direction (north, south, east, west), alignment and containment or intersection, all with strict edge comparisons ([Alameer et al. 2016](https://doi.org/10.1109/ICST.2016.36)). To keep reports focused it compares only edges among each node's k nearest neighbours, and it filters expected change with named rules: it drops alignment changes on edges that involve text, drops direction changes when the bearing between centres moved less than 45 degrees, and groups inline tags into one text node. It reached **91% precision and 100% recall** on 30 pages with failures and 24 without. IFix measured each violated relation as the number of pixels needed to restore it ([Mahajan et al. 2018a](https://doi.org/10.1109/ICST.2018.00030)). MFix (ICSE 2018) scored layout distortion as the change in relation labels between groups of elements, but within a group it counted only new intersections, which encodes the rule that elements may reflow inside a group as long as they do not collide ([Mahajan et al. 2018b](https://doi.org/10.1145/3180155.3180262)). WebSee (ICST 2015) shows why the group left pixels behind for layout: simulated pixel-perfect comparison marked **over 84% of the page** as different for several subjects, and image comparison became usable only with a tuned perceptual threshold and tester-declared regions for dynamic content ([Mahajan and Halfond 2015](https://doi.org/10.1109/ICST.2015.7102586)).

Two lines of work use explicit, developer-written layout properties, which is where onionskin's expectations sit. Hallé and colleagues' Cornipickle (ICST 2015, JLAMP 2016) is a declarative language of constraints over DOM and CSS properties with a vocabulary users can extend ([Hallé et al. 2015](https://doi.org/10.1109/ICST.2015.7102635); [Hallé et al. 2016](https://doi.org/10.1016/j.jlamp.2016.04.001)). Althomali's review criticises it as one more language, on top of HTML and CSS, that testers must write by hand ([Althomali 2022](https://etheses.whiterose.ac.uk/31157/)); its actual syntax was not examined for this report. Panchekha and colleagues' VizAssert (PLDI 2018) states properties in a visual logic: universally quantified formulas over the rendered boxes, built from box edges, box type, foreground and background colour, and navigation to parent, children, siblings and ancestors, limited to linear arithmetic ([Panchekha et al. 2018](https://doi.org/10.1145/3192366.3192407)). It encodes 14 accessibility rules, among them no overlapping text, no horizontal scrolling, text at least 14 px tall and headings that form a visual hierarchy. It proves them for all widths from 1024 to 1920 px, heights from 800 to 1080 px and default font sizes from 16 to 32 px. Across 502 page and assertion pairs on 62 professionally designed pages it verified 414, found 64 true violations and 13 false positives, and timed out on 11. It builds on Cassius, which formalised a large part of CSS layout for SMT solvers ([Panchekha and Torlak 2016](https://doi.org/10.1145/2983990.2984010)), and it does not handle JavaScript, tables, vertical alignment or right-to-left text.

**What onionskin should take from this research.** The responsive layout graph's idea of a fact with a validity range is the most useful single idea: store each derived fact with the set of widths where it holds, and a two-version diff becomes set arithmetic on ranges with three kinds of change. Widths should come from a grid, both sides of each breakpoint, and binary search at change points. GWALI's filters and MFix's intra-group rule show how to offer named, opt-in "expected change" filters, and WebSee's special regions show that excluding dynamic regions must be a first-class option. VizAssert supplies a vocabulary for invariants over all boxes and a list of rendering parameters worth varying (width, height, default font size). IFix's pixels-to-restore is the right magnitude for failure messages, and ReDeCheck's five signatures can ship as opt-in default checks. **What to avoid**: undocumented lenient definitions (ReDeCheck's midpoint "above" contradicts GWALI's strict one), containment inferred from the tightest enclosing box rather than from the DOM parent or containing block, version matching by absolute XPath alone, and treating box overlap as a visible defect when most such reports were not visible. onionskin should derive "overlaps" from boxes and keep "visibly overlaps" as a separate check that looks at paint. Every published system fixes one granularity; letting the developer choose it per check is the part onionskin adds.

## Allen's 13 relations per axis make every coarse fact a set lookup

The theory of qualitative spatial relations gives onionskin definitions that are exact and mutually consistent. Allen's interval algebra has **13 basic relations** between two intervals: before, meets, overlaps, starts, during, finishes, equals, and the inverses of the six that are not symmetric. They are jointly exhaustive and pairwise disjoint, so exactly one holds for any pair of intervals, and each is a conjunction of comparisons between the four endpoints ([Allen 1983](https://doi.org/10.1145/182.358434)). Applied to the x and y projections of two boxes they describe one axis completely: before is "left of, with a gap", meets is "touching", starts is "left edges aligned and A narrower", during is "strictly within B's horizontal span". The rectangle algebra takes one Allen relation per axis, which gives 13 x 13 = 169 basic relations between axis-aligned rectangles ([Liu et al. 2010](https://doi.org/10.1016/j.artint.2010.05.006)). The reasoning theory is mature. The Ord-Horn class is the maximal tractable subclass of Allen's algebra ([Nebel and Bürckert 1995](https://doi.org/10.1145/200836.200848)), and in 2024 Bodirsky and colleagues proved that the strongly preconvex class of Balbiani and colleagues is the single maximal tractable class of the rectangle algebra that contains the basic relations ([Bodirsky et al. 2024](https://doi.org/10.1137/22M1534304); [Balbiani et al. 1999](https://ijcai.org/proceedings/1999/64)). For a test library this matters less than the vocabulary, because onionskin computes relations from measured boxes instead of inferring them. Composition is still useful for checking that a set of expectations does not contradict itself before it runs.

Coarser calculi are unions of these basic relations. Ligozat's lattice ordering of the 13 relations makes the convex relations (the intervals of that lattice) exactly the disjunctions that can be written as endpoint comparisons without "not equal", and convex relations compose with two table lookups ([Bécher et al. 2005](https://arxiv.org/abs/cs/0610004), CNRS technical report). Freksa's semi-interval relations are single or paired edge comparisons ([Freksa 1992](https://doi.org/10.1016/0004-3702(92)90090-K)), and they match the words onionskin wants: head-to-head is left-aligned (equal start edges), tail-to-tail is right-aligned, precedes is "left of, touching allowed", and contemporary is "horizontally overlapping". The names in the secondary table used for this report appear to contain slips, which is one more reason to define onionskin's names by edge conditions and not by borrowed labels. RCC-8 covers topology: disjoint, touching, partially overlapping, equal, inside and touching the boundary, strictly inside, and the two inverses ([Cohn and Renz 2008](https://doi.org/10.1016/S1574-6526(07)03013-1); [Renz and Nebel 1999](https://doi.org/10.1016/S0004-3702(99)00002-8)). A short derivation in the research notes shows that for boxes RCC-8 is a function of the rectangle-algebra pair, so it needs no separate computation. Cardinal directions split the plane around a reference box into nine tiles ([Frank 1996](https://doi.org/10.1080/02693799608902079); [Goyal and Egenhofer 2001](https://doi.org/10.1007/3-540-47724-1_3)); the direction-relation matrix records which tiles the other object touches, with 218 basic relations for connected regions and 511 for regions that may be disconnected ([Liu et al. 2010](https://doi.org/10.1016/j.artint.2010.05.006)). The disconnected form fits an inline element broken across lines into several rectangles. Euzenat formalised how relations convert between granularities and the constraints that such conversions must satisfy ([Euzenat 2001](https://doi.org/10.1111/0824-7935.00170)).

Put together, these give a ladder of granularity levels. The table is a synthesis for this report, not a structure proposed by any source, and its counts other than 13 and 169 are derived.

| Level | Per axis | Two dimensions | Typical expectation |
|---|---|---|---|
| 0, metric | edge, centre and size values | values on both axes | gap 4 to 8 px; width 0.5 x B's width |
| 1, basic | 13 Allen relations (25 with a size comparison) | 169 pairs | x meets, y during |
| 2, coarse | named edge conditions (left-aligned, precedes, overlapping); 6 band classes | RCC-8; 36 cardinal tile sets; alignments | inside, touching, overlaps, left-aligned |
| 3, sketch | before, overlapping, after | 9 (eight compass directions plus overlapping) | left-of, above |

The rule that follows is simple. Compute the level 1 relation once per pair of boxes and answer every coarser question by set membership. Levels then agree by construction, because a pair satisfies a coarse relation exactly when its fine relation belongs to the set, and every failure can be explained as edge comparisons.

Real boxes need slack. The literature offers three models: thick boundaries, which Aiello and Smeulders added to 13 x 13 rectangle relations so that reading-order detection on document images tolerates noise ([Aiello and Smeulders 2004](https://doi.org/10.1016/j.ins.2003.05.015)); fuzzy Allen relations that return a degree between 0 and 1 ([Schockaert et al. 2008](https://doi.org/10.1109/TFUZZ.2007.895960)); and rough or indeterminate boundaries ([Bittner and Stell 2002](https://doi.org/10.1023/A:1015291525685)). A test needs pass or fail, which turns a fuzzy degree back into a threshold, so the simplest sound choice is a crisp three-way comparison with a tolerance e at every edge comparison: before if x < y - e, at if |x - y| <= e, after otherwise. A derivation in the research notes, for which no published source was found, shows that the 13 relations stay exhaustive and disjoint under this rule as long as both intervals are longer than 2e. A box narrower than 2e, such as a 1 px rule or an empty span, needs point semantics or a clear error. The cost is that "at" stops being transitive: A within e of B and B within e of C lets A and C differ by 2e, the situation Luce analysed as a semiorder ([Luce 1956](https://doi.org/10.2307/1905751)). Group alignment should therefore be checked as a spread (largest edge minus smallest edge at most e), not as a chain of pairs, and onionskin should never infer new facts transitively from tolerant ones.

Constraint-based layout supplies the quantitative half. Cassowary solves the linear equalities and inequalities that arise in UI layout, such as one window left of another or a pane taking the leftmost third of a window ([Badros et al. 2001](https://doi.org/10.1145/504704.504705)). Constraint hierarchies separate required from preferred constraints ([Borning et al. 1992](https://doi.org/10.1007/BF01807506)), and Constraint Cascading Style Sheets proposed the same model for CSS ([Badros et al. 1999](https://doi.org/10.1145/320719.322588)). Apple's Auto Layout guide (vendor documentation) gives the compact practical form: one attribute of one item equals, is at most, or is at least a multiplier times one attribute of another item plus a constant. Attributes are edges, centres, width, height and baselines, and the rules forbid relating size to position, horizontal to vertical, or scaling a position ([Apple Auto Layout guide](https://developer.apple.com/library/archive/documentation/UserExperience/Conceptual/AutolayoutPG/AnatomyofaConstraint.html)). Read as a check instead of something to solve, this form covers every quantity onionskin needs: a gap between 4 and 8 px is two inequalities, "same width" is multiplier 1 and constant 0 within tolerance, and "half the width" is multiplier 0.5. Auto Layout's priorities (1000 for required, lower for optional) map onto severity, failure versus warning. One more result bears on generated facts. InferUI synthesises Android ConstraintLayouts from measured view positions, and it needs explicit robustness properties and a probabilistic model of developer choices to pick among candidate constraints ([Bielik et al. 2018](https://doi.org/10.1145/3276526)). A capture alone does not reveal which relations the designer intended.

**What onionskin should take from the theory.** One fine relation per axis plus centre and size comparisons, computed once with one tolerance; coarse relations defined as sets of fine ones; names only for families that partition all pairs (directions, RCC-8) and for single edge conditions (aligned, left-of); quantities in the Auto Layout form; and failure messages that report the observed fine relation and, using Freksa's idea of conceptual neighbours, which edge has to move and by how much. **What to avoid**: coding each coarse predicate separately, which lets levels disagree; relation labels borrowed without their edge conditions; chained tolerant comparisons; and treating generated facts as the designer's intent.

## Selectors and render timing, not assertions, cause most test breakage

Studies of why GUI tests break point at finding elements rather than checking them. Hammoudi, Rothermel and Tonella classified 1,065 breakages of record-and-replay web tests across 453 versions of web applications, and a blog summary of the paper reports that **locators caused over 73%** of them ([Hammoudi et al. 2016](https://doi.org/10.1109/ICST.2016.16); [Colyer 2016](https://blog.acolyer.org/2016/05/30/why-do-recordreplay-tests-of-web-applications-break/), blog post). In open-source Android projects, about 70% of changes to GUI test methods came from GUI fragility ([Coppola et al. 2019a](https://doi.org/10.1109/TR.2018.2869227)). Better locators help a lot. Robula+ cut locator fragility by 90% compared with absolute XPaths ([Leotta et al. 2016](https://doi.org/10.1002/smr.1771)), and Yandrapally and colleagues located elements by nearby labels because small layout changes broke many tests ([Yandrapally et al. 2014](https://doi.org/10.1145/2610384.2610390)). Writing web tests as code with reusable element definitions took 32% to 112% more time than capture-replay, but saved 16% to 51% in maintenance and paid off after one to three releases ([Leotta et al. 2013](https://doi.org/10.1109/WCRE.2013.6671302)).

Image-based tests break more often, for visual reasons. On a hybrid mobile app over 25 releases, 60% of visual test methods needed changes against 47% of layout-based ones. Visual tests broke on graphic changes and rearranged widgets, layout-based ones mostly on text changes, and the visual suite still caught a display defect the layout suite missed ([Coppola et al. 2019b](https://doi.org/10.1145/3340433.3342824)). In industry, Alégroth and colleagues found 58 distinct problems when two companies moved system tests to visual GUI testing, and still judged it cost-effective ([Alégroth et al. 2015](https://doi.org/10.1007/s10664-013-9293-5)). Spotify dropped visual GUI testing after several years for an internal test interface that was more robust but no longer tested the GUI as users see it ([Alégroth and Feldt 2017](https://doi.org/10.1007/s10664-016-9497-6)).

For tests that read layout, timing is the main threat. In 235 flaky UI tests from 62 projects, **waiting for asynchronous work caused about 45%**. The largest subcategories were acting before resources finished rendering (61 tests) and animation timing (26), and ten more were layout differences between environments, such as a dropdown cut off because browsers have different default window sizes ([Romano et al. 2021](https://doi.org/10.1109/ICSE43902.2021.00141)). At Google, 4.56% of test failures in the TAP system came from flaky tests ([Luo et al. 2014](https://doi.org/10.1145/2635868.2635920)), and a Google Testing Blog post reported WebDriver tests flaky at 10.45% against 1.65% for all tests, with test size a better predictor than the tool ([Listfield 2017](https://testing.googleblog.com/2017/04/where-do-our-flaky-tests-come-from.html), blog post). Parry and colleagues survey the wider literature ([Parry et al. 2022](https://doi.org/10.1145/3476105)). Two browser facts make timing concrete for onionskin: getComputedStyle returns the value at the current point of a running animation ([MDN getComputedStyle](https://developer.mozilla.org/en-US/docs/Web/API/Window/getComputedStyle)), and `document.fonts.ready` resolves only once fonts have loaded and layout is done ([MDN FontFaceSet.ready](https://developer.mozilla.org/en-US/docs/Web/API/FontFaceSet/ready)).

Oracle research frames the trade-off between symbolic and exact checks. Memon, Banerjee and Nagarajan ran 660,000 GUI test runs with 11 oracle types and found that detailed oracles detect faults earlier and with fewer tests, but cost more per test ([Memon et al. 2003](https://doi.org/10.1109/ASE.2003.1240304)). Huo and Clause define a brittle assertion as one that depends on values derived from inputs the test does not control, and found 164 tests with brittle assertions among more than 4,000 ([Huo and Clause 2014](https://doi.org/10.1145/2635868.2635917)). A pixel offset that comes from font metrics, browser defaults or viewport size is exactly such a value, which gives a citable argument for asserting relations instead of measured values. Relations that must hold across many valid renderings behave like metamorphic relations ([Chen et al. 2018](https://doi.org/10.1145/3143561)), and ReDeCheck's consistency across widths is a layout example. Thresholds do not rescue whole-output comparison: on state pairs drawn from 493,000 page pairs across more than 6,000 sites, no near-duplicate detector told meaningful changes from insignificant ones without losing coverage, even at its best threshold ([Yandrapally et al. 2020](https://doi.org/10.1145/3377811.3380416)). Barr and colleagues give the general survey of the oracle problem ([Barr et al. 2015](https://doi.org/10.1109/TSE.2014.2372785)).

Fact diffs between versions are a form of snapshot testing and inherit its known faults. About 38% of 1,487 Jest projects use snapshots ([Fujita et al. 2023](https://doi.org/10.1109/ICSME58846.2023.00041)). A review of 50 grey-literature documents found fragility the most cited drawback (28%), followed by missing context and large snapshots, and recommended small snapshots that are reviewed like code ([Cruz et al. 2023](https://doi.org/10.1016/j.jss.2023.111797)). The related MSc dissertation adds that snapshots should never be updated automatically in CI, because blind updates hide regressions ([Cruz 2024](https://homepages.dcc.ufmg.br/~mtov/diss/2024-victor.pdf)). A 2026 preprint finds that snapshot tests and conventional tests cover different code, and that suites with snapshots killed 1.3 times more mutants ([Fujita et al. 2026](https://arxiv.org/abs/2610.29549)), which supports having both an expectation mode and a diff mode.

**What onionskin should take.** A separate selector layer where each element is named once through a stable test hook (id, data attribute or role); a settle step before capture (fonts ready, animations and transitions off, boxes stable across consecutive frames); viewport size and device pixel ratio as required parameters; relational expectations by default, and exact values only where a requirement fixes the value; diff entries per element and property with their context; and a small opt-in pixel check for places where exact appearance matters. **What to avoid**: visible text or structural paths written inline in each assertion, fixed sleeps, one global threshold, and automatic baseline updates. Because no study has measured relational layout assertions directly, the claim that "X is left of Y" needs fewer changes than "X is 12 px left of Y" rests on this indirect evidence.

## CSS refactoring research defined neutrality but never checked it by rendering

The peer-reviewed work on CSS refactoring defines presentation statically. Mazinanian, Tsantalis and Mesbah (FSE 2014) define it as the property values finally applied to each element. They protect it with a precondition: a refactoring must keep every order dependency, meaning every pair of declarations of one property with equal specificity and importance whose selectors match a common element in DOM states captured by the Crawljax crawler ([Mazinanian et al. 2014](https://doi.org/10.1145/2635868.2635879)). Across 38 sites they found that on average 66% of declarations were duplicated. They name their own main threat: dynamic applications have practically unbounded DOM states, so a refactoring can break presentation in states that were never visited. Mazinanian and Tsantalis (ASE 2016) tested their migration to Less with an oracle on longhands: compile back to CSS and check that each rule's map from longhand to final value is unchanged, counting equivalent spellings such as `red` and `#F00` as equal ([Mazinanian and Tsantalis 2016](https://doi.org/10.1145/2970276.2970348)). Those tests caught a real bug: a shorthand set to `none` assigns `none` to only one longhand and resets the others to their initial values, which their own inference got wrong. The authors called comparing the rendered pages before and after the ideal test, but rejected it as too slow and error-prone. That rendering-based comparison is what onionskin's diff mode would do.

Work on unused and redundant CSS sharpens what such a comparison can claim. CILLA (ICSE 2012) evaluates selectors against crawled DOM states and found on average **60% of selectors unused** across 15 systems ([Mesbah and Mirshokraie 2012](https://doi.org/10.1109/ICSE.2012.6227174)); the same matching gives a coverage measure. Hague, Lin and Ong showed that testing cannot soundly prove a rule redundant, and modelled HTML5 applications as tree-rewriting systems to do it soundly ([Hague et al. 2015](https://doi.org/10.1145/2814270.2814288)). Hague, Lin and Hong's SATCSS counts two style sheets as equivalent when they assign the same declarations to any node of any DOM, and keeps declaration order within a rule significant because of fallbacks, such as a plain colour followed by an `rgba()` colour ([Hague et al. 2019](https://doi.org/10.1145/3310337)). Tree-logic analyses by Genevès, Layaïda and colleagues also reason over all documents ([Genevès et al. 2012](https://doi.org/10.1145/2187836.2187946); [Bosch et al. 2014](https://doi.org/10.1145/2644866.2644885)). One consequence follows for any browser-based diff: a modern engine picks the same winner whether or not a fallback is present, so **a single-engine diff cannot validate changes to fallbacks, vendor prefixes or `@supports` branches**.

What the browser returns is less clean than "computed style" suggests. The CSSOM specification (W3C editor's draft) defines getComputedStyle's output as resolved values: used values for colours, used values in px for width, height, margins and padding when the element is rendered, used values for the insets of positioned elements, and computed values for everything else ([CSSOM resolved values](https://drafts.csswg.org/cssom/#resolved-values)). A style diff is therefore partly a layout diff, since a changed `width` can mean a changed declaration or a changed ancestor. The spec lists longhands in alphabetical order, while MDN says shorthands also appear, and sosie found that some shorthands do not serialise reliably, so shorthand handling has to be tested per engine ([CSSOM getComputedStyle](https://drafts.csswg.org/cssom/#dom-window-getcomputedstyle); [MDN getComputedStyle](https://developer.mozilla.org/en-US/docs/Web/API/Window/getComputedStyle)). Serialisation already normalises sRGB colours to `rgb()` or `rgba()`, which does the value-equivalence work of the 2014 and 2016 papers, but a move to `oklch()` serialises differently even when it looks the same, and browsers may misreport `:visited` styles on purpose. `computedStyleMap()` returns true computed values such as `50%`, but MDN marks it as not Baseline, so it is not available in every major browser ([MDN computedStyleMap](https://developer.mozilla.org/en-US/docs/Web/API/Element/computedStyleMap)). Geometry is fractional. WebKit lays out in units of 1/64 px and snaps at paint time ([WebKit LayoutUnit wiki](https://trac.webkit.org/wiki/LayoutUnit?format=txt)), and VizAssert had to compare its results with Firefox to within a sixth of a pixel ([Panchekha et al. 2018](https://doi.org/10.1145/3192366.3192407)). The Chrome DevTools Protocol can force `:hover`, `:focus` and other pseudo-classes when it computes styles, so interactive states can be listed as data ([CDP CSS domain](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/CSS.pdl)).

These findings suggest three levels of neutrality, reported separately: style-neutral (every whitelisted resolved longhand equal on every matched element and its pseudo-elements), layout-neutral (boxes equal within a tolerance) and pixel-neutral. This is the ladder sosie uses. Style-neutral is stricter than appearance in places, for example a colour change on an element with no text, and weaker in others, since properties outside the whitelist, images, canvas and other engines go unchecked. Every verdict should be scoped to the matrix it covers: pages, UI states, widths, user default font sizes and engines. VizAssert's use of default font size as a parameter matters for refactors such as px to rem, which can be neutral at 16 px and not at 20 px.

**What onionskin should take.** Match elements, not rules, so renamed or merged selectors do not matter; compare whitelisted longhands, and label each as computed or layout-dependent so that one root cause appears as one change; use CILLA-style selector coverage to report rules that matched nothing in any captured state as unverified rather than neutral; take test widths from the breakpoints in both the old and the new style sheets; and force pseudo-classes through the DevTools Protocol where it is available. **What to avoid**: comparing shorthands, matching by selector, claiming neutrality beyond the captured matrix, and using one engine to approve changes to fallbacks or prefixes. No study has measured how often a style-neutral refactor looks different, or the reverse, so the trade-off between the three levels is unknown.

## Twenty design choices that follow from the evidence

The table collects the points above into one list. Two defaults should differ by mode. Developer-written expectations aim to rarely change, so they should lean lenient: coarse relations, a small tolerance near the 0.5 px used by Quixote and Compose, and opt-in strictness. Version diffs aim to catch every change, so they should lean strict, as sosie argues: near-exact geometry within one engine and machine, and false alarms preferred to misses. No source justifies any tolerance value with data, so every default should be documented and easy to override, and every failure should print the measured deviation.

## Conclusion

The prior art makes onionskin's contribution narrower and easier to defend than "symbolic layout testing", which Galen, Cornipickle and ReDeCheck already did in different forms. What none of them offers is a single fact model in which the developer picks the granularity per check, from a coarse relation down to an exact value, with every level derived from the same fine relation and the same tolerance so that levels cannot disagree, and with that one model serving both expectations and version diffs. Each published system fixed one granularity and one use. A decomplected design follows almost directly: capture, normalisation, fact derivation, checking, diffing and reporting as separate functions over plain data, with the selector layer and the capture matrix as their own concerns.

The largest unknowns are empirical, not technical. Nobody has measured how often relational layout expectations need editing compared with exact ones, how often a style-neutral refactor still looks different, or which tolerance values work in practice; the published constants (0.5 px, 2 to 3 px, 3 and 5 px) come without data. onionskin is in a position to produce that evidence from its own use: Galen-style mutation runs over its suites would show how tight they are, and running both diff levels on real refactors would show how often style-neutral and layout-neutral disagree.
